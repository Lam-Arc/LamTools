## 1. 结论与真实故障证据

**这是架构缺陷，同时包含局部实现错误。**

最近测试的会话为 `72e20a183a7a4ba6af7e3de1a6e5488c`，证据保存于 `data/core-agent/latest-interruption-review.zip`。服务端日志收到两次暂停和中间一次恢复，未收到终止请求。第二次暂停发生于审批续跑，出现状态版本冲突，随后取消兜底把执行编号当作回合编号写入了终态。

同一归档内同时存在：

| 载体 | 实际内容 |
| --- | --- |
| runtime state | 原会话 `paused` |
| 原逻辑回合 | `running` |
| 由 execution id 编造的回合 | `cancelled` |
| 会话快照总状态 | `cancelled`，显示“已中断” |

这不是按钮误操作，也不能解释成“真正有另一个进程在操作”。日志中的“another running process”是版本冲突保护的通用错误文案；本次已观察到的是本机多条收尾路径之间的竞争。

### 根因与代码证据

1. **生命周期存在多个写入权威。** `kernel/loop.py` 的外部暂停/取消收尾、`app/live_operations.py` 的应用收尾、`app/approval_resolution.py` 的审批收尾都能保存状态或产生结束事件。`SQLiteWriteCoordinator` 只串行化单次数据库写入，不能使这几步构成同一个领域操作。
2. **统一协调器未真正接管。** `live_operations._mirror_turn_started` 每次临时创建 `TurnCoordinator`，只做事后镜像；`_mirror_turn_status` 还有直接保存状态的兜底。旧控制路径绕过了协调器，epoch 也未成为所有写入的强制门槛。新增一张镜像表并不等于单一权威。
3. **身份仍能互换。** `_execute_continuation_job` 在取消兜底调用 `_persist_cancelled_terminal(turn_id=run_id)`；快照归约器又允许据此建立回合。缺少“该执行必须属于该已存在回合”的约束。
4. **取消执行被当作用户终止。** `CancelledError` 可以来自暂停、终止、关闭、超时或执行器失联，异常本身并不包含用户意图。当前兜底在暂停尚未完成落盘时推断为取消。
5. **同一控制动作没有覆盖整组执行的持久边界。** 子代理管理器缓存、单独 SQLite 记录、交互池与主回合各自收敛，造成重启漏恢复、终止后可复活、暂停后问题卡消失。
6. **续跑入口重复装配。** 普通恢复、批准、拒绝、提问、子代理恢复分别构造执行环境，因此消息确认、控制信号和运行登记会遗漏。
7. **执行器阻塞能拖住控制面。** 前序 ChatT 故障中，插件在 Python 异步入口同步重试积压上报，整个后台无法响应。只修改状态机不能解决同进程阻塞。

旧文档 `turn-control-architecture-review.md` 中“完成（镜像）”只证明读模型存在，不能证明生命周期已收口。本设计以删除旧写入权、真实入口的边界验收为迁移完成标准。

## 3. 新架构的唯一权威

目标结构：

```text
唯一按钮 / 多窗口 / CLI
          ↓ 带身份和请求号的命令
ControlService（唯一生命周期写入者）
          ├─ 单事务：控制意图 + 状态 + 回执 + 待执行动作 + 事件 outbox
          ├─ 进程监督：主执行器 / 子执行器 / 插件工具执行器
          └─ 权威快照与增量事实 → 前端

Python 模型与工具执行器
          └─ 只上报执行事实与历史增量，不自行宣布回合暂停或终止
```

### 身份必须分层

| 身份 | 含义与约束 |
| --- | --- |
| `session_id` | 用户会话，不随回合变化 |
| `execution_group_id` | 本次由用户控制的一组主子执行；父回合结束后仍可控制存活子代理 |
| `turn_id` | 一次逻辑任务；恢复不变；必须先存在，结束事件不能创建它 |
| `run_id` | 一次执行尝试；恢复或决策续跑创建新编号，不能放进 turn_id 字段 |
| `generation` | 控制代次；用于拒绝旧执行的生命周期回报 |
| `command_id` | 一次用户动作的幂等身份；重传复用，新的动作重新生成 |
| `interaction_id` / `tool_call_id` | 用户决策和具体工具调用身份，各自独立 |

Rust 使用不同的新类型而非同一种 String 别名；Python 边界使用有校验的结构。数据库对运行、回合、会话关系设置组合外键或等价事务校验。缺失身份应拒绝并记录，不从 run_id 猜 turn_id，不回退到“最新回合”。

### 写入权归属

- **只有 ControlService** 能修改生命周期、交互有效性、执行组策略、续跑命令状态及相应权威事件。
- Kernel、工具、插件、supervisor 只能报告 `RunQuiesced`、`RunCompleted`、`ToolResultCommitted` 等事实。
- `RuntimeTaskRegistry` 只保留进程内任务句柄和信号，不决定持久状态。
- 前端 reducer 只投影权威生命周期事件；工具条目、子代理条目不能改变父回合状态。
- 对账器发送修复命令，不能绕过控制服务直接保存状态。
- 协调器必须是稳定服务实例；真正的排序和所有权由数据库事务约束，不能仅靠某个实例的 asyncio.Lock。

## 4. 命令与状态机

命令至少携带 `command_id, session_id, execution_group_id, turn_id?, expected_generation, kind, payload`。作用域必须明确是某回合、某成员还是某执行组。终止确认框绑定打开时的目标；切换会话后不重新解析目标。

关键状态为 `queued / running / waiting / pausing / paused / terminating / completed / failed / terminated`。暂不执行时可以显示处理中，但不能把“已接受暂停”冒充“已暂停”。

### 暂停

1. 在一个事务中验证目标、记录暂停意图、推进 generation、关闭新模型调用和新工具调用入口，写执行器动作与事件 outbox。
2. 事务提交后向执行器发信号；执行器按工具能力协作停止或被监督器结束。
3. 只有目标成员都已退出或被确认隔离，才提交 `paused`。无法停止时保持“正在暂停”并提供真实原因，不能虚报完成。
4. 已有完整工具结果保留；未提交的流式草稿不作为最终答复；待回答问题可以延后展示，但不得丢失。
5. 重复暂停返回原回执或当前状态，不能重复关闭卡片。

### 恢复

1. 只允许恢复同一组内真正暂停的目标；明确终止、自然完成或失败的目标不能被普通恢复复活。
2. 原执行尚在收尾时，恢复命令持久排队依赖该暂停命令完成；不能持有会话锁一直等待，从而挡住后来的终止。
3. 分配新的 run_id 和 generation；原任务、已提交历史、补充输入、附件均按独立输入身份恢复，不用 `extra_text or original_text` 代替输入列表。
4. 从持久执行组登记重建所有暂停成员；不能依赖 `_SUPERVISORS` 缓存。
5. 一个命令号只产生一次执行，回执丢失后查询或重传原命令。

### 终止

1. 同事务持久记录终止意图、撤销未开始的续跑、结束有效交互、禁止新步骤；随后停止目标组的主子执行器。
2. 明确区分 `suspended_by_user`、`interrupted_by_crash` 和 `terminated_by_user`。终止不能复用可恢复的 interrupted。
3. 用户明确终止后，目标提醒、成员唤醒和自动回答不得恢复该执行组。之后用户可以显式创建新的任务。
4. 终止不等于回滚已发生的文件或外部修改；未确认的工具调用必须保留不确定结果。

### 竞争规则

- 事务提交给操作一个明确顺序，而不是依赖哪个后台收尾最后落盘。
- 暂停先提交，之后旧执行的完成不能覆盖暂停；完成先提交，对已完成回合的暂停是无操作。
- 终止先提交，之后恢复、批准或回答不能重新启动；恢复先提交、终止后提交，终止必须覆盖刚启动的新尝试。
- 暂停过程中已经开始的工具允许上报对应调用的真实结果，但不能凭旧 generation 修改回合生命周期；应走受限的结果入账接口。
- `CancelledError` 只能表示执行被取消。控制服务读取已提交命令决定是暂停、终止还是异常中断；工作线程不得自行补写 cancelled。

## 5. 统一执行与决策管线

统一入口 `RunLauncher.launch(ExecutionEnvelope)`，所有首次执行、恢复、批准、拒绝、回答问题、子代理恢复都使用它。Envelope 必须包含身份、代次、控制令牌、权限快照、消息接收/确认入口、检查点和事件出口。

- 用户选择首先成为持久决策，再生成一次可执行续跑动作；决定已接受不等于工具已执行。
- 暂停时收到有效答复可以只保存决定，返回“已保存，等待恢复”，不得隐式启动模型或工具。
- 批准与工具启动之间再次检查实时权限、generation 和控制意图。
- 后台 job 的状态变更必须验证 claim token、租约所有者和 generation；旧执行器不能完成别人的新租约。
- 续跑消费者不能将整个模型回合作为可无条件重试单元。重试前先判定是否已经执行工具，不能因为 job 还未 completed 就从头执行。
- 执行结果、输入检查点和确认回执关联到同一事实提交；接收子代理通知的回合仅 accepted 时，不能清空持久邮箱。
- 问题的“延后”“已保存答案”“已结束”与回合“暂停/终止”分开，不通过删除问题来模拟暂停。

## 6. 持久化、隔离与 Rust 方案

**优先采用 Rust 承担控制状态机与进程监督，Python 保留模型、现有可靠工具与上下文处理。** Rust 的目的在于独立的控制服务、受约束的身份、穷举状态转换和进程隔离，而不是把同样的多写者代码翻译一遍。

已有落点为 `core/runtime-rs`。当前审查未发现可直接复用的 Python→该 Rust 控制服务桥接，因此桥接、命令通道和监督器都是待实施项，不能声称现有 crate 已覆盖桌面控制。

- 最终由桌面壳监督独立 ControlService，控制命令经独立通道送达；不能仍把所有控制请求排在可能阻塞的 Python 事件循环后。
- 复用 `core.db`，明确控制表唯一写入者，意图、状态、交互、续跑动作、回执、outbox 的变更在同一个事务中提交。不要同时新增另一个可争夺权威的控制数据库。
- Python 的历史/工具结果以受校验的事实提交，控制检查点与生命周期关联必须事务化；跨进程调用丢失使用稳定事实号重传。
- 子代理邮箱与生命周期逐步从独立 `sub_agents.sqlite3` 迁到同一控制存储。旧记录迁移使用稳定键，切换后原库只读；每次切换只有一个写入者。
- 每个执行组使用 Windows Job Object 或等价的进程组机制；协议动作先持久化，再施加进程动作。控制服务重启时先确认旧执行器所有权和存活状态，再重新发出动作。
- 同步或不可信的插件调用放入受监督执行器；单个插件阻塞不能阻塞控制通道。
- 具有跨回合生命周期的用户持久服务必须记录范围。终止确认说明是否包含它们，不能擅自杀掉其他任务或系统进程。
- 所有等待都有业务结束条件、故障状态和重试上限；到时未停止不能被标记成停止成功。

外部工具不能普遍保证 exactly-once：网络端写成功后、客户端收到结果前就可能退出。新架构必须保存 `prepared / started / result_committed / uncertain` 调用账本，按工具的幂等能力处理；未知副作用不得自动重放。

## 7. 唯一按钮的目标契约

此表是新设计，未修改当前界面。

| 状态 | 短按 | 长按/右键 |
| --- | --- | --- |
| 空闲，有内容 | 开始新任务 | 没有活动目标时不提供终止 |
| 运行中，空内容 | 暂停当前执行组 | 固定目标后确认终止 |
| 运行中，有内容 | 将消息加入队列 | 仍可从同一按钮访问暂停/终止控制；保留草稿 |
| 已暂停，空内容 | 恢复 | 确认终止 |
| 已暂停，有内容 | 标明“继续并发送”，恢复并追加输入 | 确认终止，保留未发送草稿 |
| 正在暂停 | 显示进度；恢复按屏障排队，不重复发送暂停 | 允许升级为终止 |
| 正在终止 | 显示进度，不接受恢复 | 同目标终止幂等 |
| 父已结束、子仍运行 | 暂停该执行组中的活动成员 | 终止目标组，不能重开父回合 |

按钮动作由权威快照中的 `primary_action / can_pause / can_resume / can_terminate / target / version` 产生。前端保留草稿相关显示，但不能另推导生命周期。手势期间目标、版本或会话改变时取消手势；终止确认保持原目标或作废。
