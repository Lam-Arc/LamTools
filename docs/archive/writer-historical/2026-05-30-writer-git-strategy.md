# Writer Git 策略设计稿

> 目标不是限制 Writer 的所有 git 行为，而是把 git 变成可恢复、可审计、可压缩的事实边界。

## 目标

- 让 Writer 在任务开始时建立稳定基线。
- 让 Writer 的修改、试错、回退都留在自己的分支体系里。
- 让每个关键节点都有可追溯的 git 落点。
- 让用户原有改动不被混入 Writer 的提交和回退。
- 让上下文压缩后仍能从 git 记录恢复任务状态。

## 核心思路

- 不把 git 当作权限控制器。
- 把 git 当作运行时监控、节点落点和恢复机制。
- Writer 可以绕过单一工具路径，所以策略要基于状态变化来判断，而不是只靠命令白名单。

## 会话基线

任务开始必须记录：

- 当前分支
- 当前 HEAD
- `git status`
- 用户已有未提交文件
- untracked 文件
- Writer 本轮开始时间

作用是把“用户原本的改动”和“Writer 本轮造成的改动”分开。

## 影子主线

- Writer 接手任务时，自动创建或同步 `writer/main`。
- `writer/main` 的内容要和接手时的当前分支一致。
- 之后所有新建分支、回退、试验都基于 `writer/main` 或它的后代分支进行。
- `writer/main` 是 Writer 自己的稳定主线，不直接代表用户项目主线。

## 分支策略

什么时候必须分支：

- 非只读任务且会修改文件。
- 中等以上任务。
- 跨多个文件的任务。
- 生成项目类任务。
- 进入决策点之后的新路线。

什么时候可以不分支：

- 纯分析、纯 review、纯解释。
- 用户明确要求只读。
- 单文件、很小的修改，且用户明确允许在当前分支完成。

分支规则：

- 当前不在 `writer/...` 分支时，创建 `writer/{category}/{slug}`。
- 当前已经在本任务对应的 Writer 分支时，允许继续用。
- 工作区已有用户脏改动时，先记录，不直接覆盖，不混入提交。

## 决策点

Writer 到达决策点时，必须先提交并分支。

典型决策点包括：

- 架构路线分叉
- 新依赖选择
- 接口或数据结构变更
- 测试连续失败后需要换方案
- 任务范围扩大
- 用户要求确认方向

处理方式：

1. 先提交当前状态，形成决策锚点。
2. 再从这个锚点创建分支。
3. 每个候选方案可以各自独立推进。
4. 最终选中的方案再合回任务主线。

## 提交策略

什么时候提交：

- 一个逻辑阶段完成并验证通过后。
- 关键重构前，先做 checkpoint。
- 上下文即将大压缩前，已有稳定改动时。
- 任务完成且验证通过后，必须形成最终提交。

不要提交：

- 测试没跑或验证失败的半成品。
- 明显临时代码、空文件、stub。
- 用户原本的脏文件。
- 权限不明确的文件。
- 只是读文件或生成计划。

提交备注要求：

- 简单明了
- 一眼能看懂
- 细节写进会话记忆，不堆进 commit message

## 回退策略

什么时候回退：

- 当前方案验证失败。
- LLM 写偏了，改动超出任务范围。
- 用户明确要求撤回。
- 自动修复循环连续失败。
- 计划切换方向，需要清理旧方案。

怎么回退：

- 优先回退 Writer 自己的改动。
- 优先按文件或 patch 回退。
- 尽量不用全局 `reset --hard`。
- 有 checkpoint commit 时，优先回到安全提交。
- 不回退用户在本轮开始前已有的改动。

## 合并策略

合并分三类：

- 任务分支合并回 `writer/main`
- 决策分支合并回任务分支
- `writer/main` 交付到用户真实分支

规则：

- 任务内合并可以自动化。
- 决策分支合并可以自动化。
- 合并到用户原始分支前必须确认。
- 涉及用户脏改动时必须确认。
- 冲突不能静默处理。

优先顺序：

- `fast-forward`
- `clean merge`
- `cherry-pick`
- `revert` 或回到 checkpoint

## 监控和记忆联动

每次 Git 动作都要更新会话内事实：

- 当前 branch
- 当前 HEAD
- Writer 本轮改过哪些文件
- 哪些文件属于用户原有改动
- 当前 step 关联哪些 diff
- 哪些错误由哪些 diff 引入或修复
- 最近稳定 checkpoint 是哪个 commit

目的不是堆历史，而是让压缩后还能回答三个问题：

- 现在在哪里
- 改了什么
- 下一步该继续、回退还是合并

## 必要输出

什么时候必须告诉用户：

- 创建或切换分支时
- 发现用户已有未提交改动时
- 准备提交时
- 准备回退时
- 验证失败但准备继续修时
- 任务完成时
- 需要 push、merge、rebase、删除分支时

平时不需要把每次 `git status` 都刷给用户，避免噪声。

## 最终约束

- Writer 的 git 时间线必须可恢复。
- Writer 的 git 行为必须可审计。
- Writer 的 git 边界必须能压缩进记忆。
- 用户的工作区改动必须和 Writer 的改动隔离。
