# LamTools 修复方案与效果文档

> 生成时间：2026-06-16
> 范围：Writer 主循环 / Core 共享层 / 跨模块集成（已排除 Novel 相关）
> 原则：每个模块先调研 3 种市场认可方案，择优推荐

---

## 总体目标

修复完成后，LamTools 将实现：

1. **安全可信**：AI Agent 的文件操作、命令执行均在沙箱内，用户确认机制生效，无路径穿越/注入/XSS 漏洞
2. **流式可靠**：SSE 流式模式下工具调用、token 统计、事件推送全部正确工作
3. **状态一致**：前端无数据丢失、无竞态闪烁、无双重数据源不一致
4. **连接韧性**：MCP 服务崩溃自动恢复，坏 JSON 不杀死连接
5. **记忆准确**：搜索不污染原始分数，中文 token 预算准确，时区不再崩溃
6. **技术栈统一**：Vite 8 + TypeScript 6 + vue-tsc 3 + Python 3.14，三端一致

## 模块一：前端-安全

### 修复项

| ID | 问题 | 推荐方案 |
|----|------|---------|
| F-SEC-01 | Markdown XSS | DOMPurify 后置净化 |
| F-SEC-02 | 短密钥误判 | 正则匹配遮蔽格式 |

### 方案选型

**F-SEC-01 Markdown XSS**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. DOMPurify 后置净化 | Cure53 安全团队维护 10 年+，16k stars，默认安全 | 额外 ~20KB | **采用** |
| B. marked 内置 sanitize | 无额外依赖 | 已在 v0.7.0 废弃移除，官方推荐 DOMPurify | 淘汰 |
| C. 自定义正则过滤 | 零依赖 | 正则无法可靠解析 HTML，业界一致否定 | 淘汰 |

标准管线：`marked.parse() → DOMPurify.sanitize() → v-html`

**F-SEC-02 短密钥误判**：将 `key.includes('...') && key.length <= 15` 改为正则 `/^[a-zA-Z0-9]{4}\.\.\.[a-zA-Z0-9]{4}$/`，精确匹配遮蔽格式。

### 修复后效果

- AI 回复中的恶意 HTML 被自动剥离，用户不会遭受 XSS 攻击
- 短 API Key 可以正常更新，不再被误判为遮蔽密钥
- 安全基线达到行业标准（marked 官方推荐方案）

## 模块二：前端-状态管理

### 修复项

| ID | 问题 | 推荐方案 |
|----|------|---------|
| F-STA-01 | fetchSteps 覆盖其他会话步骤 | 按 Key 合并（$patch fn） |
| F-STA-02 | 共享 loading 竞态 | 计数器模式 |
| F-STA-03 | 双数据源不一致 | 单一 Store + computed 视图 |
| F-STA-04 | 步骤详情缓存永不过期 | 运行中步骤跳过缓存 |
| F-STA-05 | 消息排序不稳定 | 加入 id 作为第二排序键 |
| F-STA-06 | mermaid 模块级状态污染 | 移入组件实例 |
| F-STA-07 | rebuildMessages 竞态 | 统一到 rebuildMessages |

### 方案选型

**F-STA-01 Store 数据覆盖**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. 按 Key 合并 | 增量更新不丢数据，不改数据结构 | 需遍历比对 | **采用** |
| B. 会话作用域 Map | 天然隔离 | 重构数据结构，迁移成本高 | 淘汰 |
| C. computed 过滤 | 不改数据结构 | 只解决视图层不解决数据层 | 淘汰 |

**F-STA-02 Loading 竞态**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. 每操作独立 ref | 精确 | ref 数量爆炸，全局 loading 需聚合 | 淘汰 |
| B. 计数器模式 | 天然支持并行，业界验证最多 | 无法区分哪个操作 | **采用** |
| C. Promise.allSettled | 语义清晰 | 要求操作同时发起 | 淘汰 |

**F-STA-03 双数据源**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. 单一 Store + computed | 消除根因，normalize state 模式 | 需合并 store 职责 | **采用** |
| B. Store 间同步 | 改动小 | 补丁方案，根因未消除 | 淘汰 |
| C. 事件驱动 | 解耦 | 引入新抽象层，调试困难 | 淘汰 |

### 修复后效果

- 多会话切换时步骤数据不再丢失
- 设置页加载指示器准确反映所有请求状态
- 新建会话后侧边栏和主内容区信息一致
- 运行中步骤的详情实时更新
- 同一毫秒内的消息顺序稳定
- 多条 mermaid 图表消息全部正确渲染
- 发送消息后列表不再闪烁

## 模块六：后端-安全/权限

### 修复项

| ID | 问题 | 推荐方案 |
|----|------|---------|
| B-SEC-01 | 硬编码 API 密钥 | Pydantic Settings + SecretStr + keyring |
| B-SEC-02 | 自动批准所有危险操作 | 风险分级能力权限 + 关键操作交互审批 |
| B-SEC-03 | 搜索路径无边界 | pathlib.resolve() + is_relative_to() |
| B-SEC-04 | 正则注入 | re.escape() 优先 + regex timeout 兜底 |
| B-SEC-05 | normalize_work_root 不安全 | resolve() + is_relative_to() 四层防御 |
| B-SEC-06 | 路径前缀碰撞 | is_relative_to() 替代 startswith |
| B-SEC-07 | 命令黑名单太弱 | 能力声明 + 风险分级 |
| B-SEC-08 | validate_path 前缀碰撞 | 同 B-SEC-06 |
| B-SEC-09 | git_diff 路径穿越 | 添加 _validate_path 校验 |
| B-SEC-10 | Prompt 注入 | 三层纵深防御 |
| B-SEC-11 | 默认监听 0.0.0.0 | 改为 127.0.0.1 |
| B-SEC-12 | CORS null origin | Electron 自定义协议 + 动态白名单 |
| B-SEC-13 | 日志泄露敏感内容 | 过滤 payload 日志 |
| B-SEC-14 | f-string SQL | 参数化查询或白名单校验 |
| B-SEC-15 | 标记匹配误报 | 全词匹配或正则边界 |
| B-SEC-16 | https 误判远程运行时 | 只匹配可执行协议 |

### 方案选型

**B-SEC-03/05/06 路径穿越**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. resolve() + is_relative_to() | 标准库零依赖，CWE-73 推荐四层防御 | Windows 大小写需注意 | **采用** |
| B. Chroot 沙箱 | OS 级硬隔离 | 需管理员权限，Windows 不兼容 | 淘汰 |
| C. 白名单/UUID 间接引用 | 根本消除遍历 | 不适合动态文件操作 | 淘汰 |

**B-SEC-02 命令执行安全**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. 能力权限 | 默认拒绝，最小权限 | 前期设计成本 | **采用（基础层）** |
| B. 交互式审批 | 人类在环 | 审批疲劳 | **采用（关键操作层）** |
| C. OPA 策略引擎 | 声明式策略，可热更新 | 对小项目过重 | 淘汰 |

推荐 A+B 混合：只读操作自动执行，范围写操作需确认，破坏性操作必须人工审批。

**B-SEC-04 ReDoS**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. re.escape() + 全匹配 | 标准库，零依赖 | 仅适用于搜索文本场景 | **采用（优先）** |
| B. regex timeout | 兜底防护 | 第三方 C 扩展 | **采用（兜底）** |
| C. 正则白名单 | 从源头消除 | 维护成本高 | 淘汰 |

**B-SEC-01 硬编码密钥**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. 环境变量 + Pydantic Settings | FastAPI 官方推荐，SecretStr 脱敏 | .env 可能被提交 | **采用（基线）** |
| B. HashiCorp Vault | 动态凭证，审计日志 | 运维复杂度过高 | 淘汰 |
| C. Python keyring | OS 安全存储 | CI/CD 不可用 | **采用（增强）** |

**B-SEC-12 CORS null**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. 移除 null + 自定义 Header | 最简单 | Header 可伪造 | 淘汰 |
| B. Electron 自定义协议 | 官方推荐，真实 Origin | 仅适用 Electron | **采用（桌面端）** |
| C. 动态 Origin 校验 | 灵活 | 实现复杂 | **采用（后端）** |

**B-SEC-10 Prompt 注入**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. 输入清洗 + 分隔符 | 降低攻击面 | 无法可靠防御 | **采用（Layer 1）** |
| B. 上下文分离 | 降低 67% 注入率 | 模型自注意力无硬隔离 | **采用（Layer 2）** |
| C. 输出守卫 | 唯一被证明零泄露的防线 | 需定义检测规则 | **采用（Layer 3）** |

三层纵深防御，安全边界在应用代码中强制执行。

### 修复后效果

- API 密钥不再出现在源代码中，日志自动脱敏
- AI Agent 写文件、执行命令前需要用户确认，破坏性操作必须人工审批
- 文件搜索/读取/写入全部限制在 work_root 内，符号链接和 `..` 无法逃逸
- 恶意正则表达式不会导致服务卡死
- 桌面应用有真实 Origin，不再依赖不安全的 `null` origin
- Prompt 注入攻击被三层防御拦截，输出守卫确保敏感信息不泄露
- 服务默认只监听本机，局域网设备无法访问

### 方案选型

**MCP 连接韧性**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|

## 模块十：后端-内存系统

### 修复项

| ID | 问题 | 推荐方案 |
|----|------|---------|
| B-MEM-01 | 搜索污染原始分数 | 独立分数映射（SearchResult 包装） |
| B-MEM-02 | 时区不匹配崩溃 | 全局强制 UTC + Pydantic 校验 |
| B-MEM-03 | 单条损坏全丢 | 逐条 try-except + 降级 |
| B-MEM-04 | 访问计数不持久化 | get() 后调用 _save() |
| B-MEM-05 | 前 200 字符去重误删 | 增加内容哈希作为辅助键 |
| B-MEM-06 | 中文 token 预算低估 | 字符类型启发式（CJK×1.5, Latin×0.25） |
| B-MEM-07 | total 语义错误 | 返回匹配总数而非截断后数量 |

### 方案选型

**B-MEM-01 分数污染**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. 深拷贝 | 一行代码 | 性能差 10-100x | 淘汰 |
| B. 独立分数映射 | 零污染，概念最正确 | 需重构返回类型 | **采用** |
| C. frozen dataclass | 类型系统杜绝修改 | 改动大，GC 压力 | 淘汰 |

**B-MEM-02 时区**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. 全局强制 UTC | 最简单可靠 | 调试需心算 | **采用（运行时）** |
| B. 强制 timezone-aware 类型 | 编译时保障 | 不解决"时区对但不是 UTC" | **采用（校验层）** |
| C. 适配层归一化 | 最防御 | 代码量最大 | 淘汰 |

推荐 A+B 组合：所有内部时间用 UTC，Pydantic validator 拒绝 naive datetime。

**B-MEM-06 CJK Token 预算**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| A. 字符类型启发式 | 零依赖，误差 ±15% | 不精确 | **采用** |
| B. tiktoken 精确计数 | 与 OpenAI 一致 | 只覆盖 OpenAI，Rust 扩展 | 可选增强 |
| C. 保守乘数 | 最简单 | 纯英文严重高估 | 淘汰 |

### 修复后效果

### 方案选型

**C-KRN-01 流式 tool_calls**（3 方案对比）：

| 方案 | 优势 | 劣势 | 结论 |
