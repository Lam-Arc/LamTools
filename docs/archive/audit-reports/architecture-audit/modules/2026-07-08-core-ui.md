# Core UI 共享工作台

## 一句话结论

Core UI 的外部 seam 基本方向正确：用共享 Shell、插槽、通用消息和运行面板支撑 Writer/Artist。但当前实现把消息展示投影、运行状态解释、工具语义、样式规则大量压进 `ChatThread.vue` 和 `layout.css`，共享层已经从产品中立的工作台外壳滑向“Writer 风格 Agent 过程渲染器”。

## 路径覆盖

- `core/ui/src`
- `core/ui/tests`
- `core/ui/package.json`
- 调用方：`members/writer/frontend/src/views/CoreWorkbenchView.vue`
- 调用方：`members/artist/frontend/src/views/CoreWorkbenchView.vue`
- 背景：`PRODUCT.md`、`docs/architecture-audit/2026-07-08-structure-organization-plan.md`

当前热点：

- `core/ui/src/components/ChatThread.vue`：约 3896 非空行。
- `core/ui/src/styles/layout.css`：约 2609 非空行。
- `core/ui/tests/chat-thread-process.test.ts`：体量偏大，并包含源码字符串断言。

## 主要职责和入口

- 工作台外壳：`WorkspaceShell` 提供左右抽屉、主区、浮动输入区、右栏和插槽。
- 会话导航：`SessionSidebar` 渲染分组、会话、状态、重命名、删除。
- 对话线程：`ChatThread` 渲染用户/助手消息、过程、工具、diff、测试结果、decision、sub-agent、compaction。
- 输入与辅助控件：`ComposerBar`、`AttachmentTray`、`CommandPalette`、输入语法解析。
- 设置/主题/预设：主题编辑、provider preset、全局样式。

两个调用方差异明显：Artist 使用方式较轻，接近共享工作台模型；Writer 页面承担了模型选择、附件、命令 palette、队列输入、滚动跟随、右栏资源状态等大量产品协调，Core UI 只提供壳和线程渲染。

## 可靠

- `WorkspaceShell` 的插槽式外壳是可靠方向。调用方只需要填 `sidebar-body`、`main-header`、`thread-content/main-content`、`composer-*`、`right-panel`，Writer 和 Artist 都能复用。
- `CoreMessage + MessagePart` 作为共享消息输入面是合理的，比让各产品传 DOM 或产品专用结构更稳。
- `RuntimePanel` 保持简单，仅吃 `panelGroups` 和 `stepGroups`，没有把 Writer/Artist 业务写死。
- `ChatThread` 的对外接口仍小：`messages`、`assistantLabel`、`processExpandedIds`、过程展开事件、decision 事件。外部 seam 小，本身值得保留。
- `core/ui/tests` 至少覆盖了 slot contract、消息过程渲染、decision、diff、sub-agent、compaction 等高风险展示行为。

## 存疑

- `SessionSidebar` 名义上是通用会话分组，但接口叫 `projectGroups`，字段含 `workRoot`，事件含 `select-project/delete-project`。Artist 也被迫把本地分组映射成“project”。这是可用但语义不干净。
- `useCoreWorkbenchController` 对 Artist 有帮助，对 Writer 基本只是辅助；它的接口像“最小 demo 控制器”，不应被当成完整工作台主线。
- `MessagePartType` 已经包含 `plan/todo_update/decision/sub_line/agent_summary/compaction` 等 Agent 语义。作为通用 Agent UI 可以接受，但需要防止继续膨胀成 Writer 协议镜像。
- `index.ts` 把组件、helpers、theme helpers、data、composables、样式全部导出/注入。短期方便，长期会让内部实现难以下沉。
- provider preset 放在 Core UI 有共享价值，但模型事实变化快；更像共享配置数据，不一定应长期绑在 UI 包主入口。

## 债务

- `ChatThread.vue` 把展示投影、状态解释、工具分类、diff 格式化、agent timeline 转换、decision payload、metrics 文案、局部样式放在一个文件里。它不是外部接口过大，而是内部实现没有 locality。
- `layout.css` 是全局样式大杂烩，包含 shell、settings、provider、model、agent、project、composer、runtime、thread 等多类规则。共享样式所有权不清，会误伤成员页。
- Core UI 仍有产品语义痕迹：`WorkspaceShell` 根类仍是 `writer-shell`，主区是 `writer-main`；测试也断言这些类存在。
- `SessionSidebar.vue` 和 `types.ts` 各自声明 `SessionItem/ProjectGroup`，容易漂移。
- `ChatThread` 通过工具名正则识别 `run_command/write_file/edit_file/browser_check/sub_agent` 等行为。这是展示启发式，不是稳定协议。
- `chat-thread-process.test.ts` 有读取 Vue 源码并匹配 CSS 字符串的测试，说明样式行为缺少更合适的可观测接口。
- `ChatThread.vue` 内联样式约 1300 行，同时 `layout.css` 又承载线程样式，样式边界重复。

## 重构/优化建议

### P0

- 保留公开 seam：`WorkspaceShell`、`ChatThread`、`SessionSidebar`、`RuntimePanel`、`AttachmentTray`、`CommandPalette`、核心 types。不要先新增外部抽象。
- 把明显产品命名清掉：`writer-shell/writer-main` 改为中立类名；`ProjectGroup/projectGroups` 后续改为 `SessionGroup/sessionGroups`，可先兼容别名。
- 收窄 `index.ts` 公共导出：先确认外部引用，再把只供内部组合的 helpers/theme/composables 从主入口降级到内部或子入口。
- `layout.css` 先删/迁移不属于共享工作台的规则：provider、model routing、agent settings、new-project popover 等若只服务 Writer/设置页，应回到 member 或具体组件样式。
- 合并重复类型定义：`SessionItem/ProjectGroup` 只保留一个来源。

### P1

- 把 `ChatThread` 内部拆成私有投影层和私有渲染块：线程输入仍是 `CoreMessage[]`，但内部先归一成稳定展示模型，再渲染普通消息、过程、工具、decision、agent、compaction。
- 工具分类不要散落在模板辅助逻辑里；收成内部表驱动规则，保留默认展示，未知工具只按通用 tool card 显示。
- 样式按所有权拆分：shell/sidebar/composer/runtime/thread/settings 分文件；线程专属样式跟随线程内部模块，不再混在全局 layout。
- 测试从“匹配源码字符串”改为“挂载后观察行为和布局类”，减少重构阻力。

### P2

- 如果未来 Writer/Artist 都需要更强右栏，可扩展 `RuntimePanel` 的通用展示模型；现在不需要提前做 dashboard 框架。
- 如果多产品都需要不同语言/文案，再做 label dictionary；现在先把中文业务文案集中，不要为了 i18n 提前加层。
- 不建议现在引入复杂 UI registry 或插件式 renderer。当前只有两个主要调用方，先把内部债务拆干净更划算。

## 不建议现在做

- 不建议把 Writer 的模型选择、队列输入、附件发送、滚动跟随全部下沉 Core；这些仍是 Writer 工作流协调。
- 不建议把 `ChatThread` 的每种卡片都变成外部公开组件；这会把内部渲染债务变成公共接口债务。
- 不建议重写工作台 Shell。Shell seam 可用，问题主要在命名、样式和线程内部实现。
- 不建议把 Artist 迁就成 Writer 的项目模型。Artist 当前本地分组能工作，但共享层命名应回到中立会话分组。

## 需要主线程核对的证据

- `WorkspaceShell.vue` 使用 `writer-shell`、`writer-main`，与 Core UI 产品中立要求冲突。
- `SessionSidebar.vue` 暴露 `projectGroups` 和 project 事件；Artist 调用方也被迫适配该命名。
- `ChatThread.vue` 对外 props 很小，但内部混入工具、命令、sub-agent、decision 解释。
- `layout.css` 覆盖 provider、agent、project 等多类业务 UI。
- `index.ts` 主入口导出和注入范围过宽。
- `chat-thread-process.test.ts` 存在源码字符串断言，后续拆分前要先替换成行为断言。
