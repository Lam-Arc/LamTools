# opencode 执行说明：从旧运行文件到成员运行骨架

## 执行目标

把 Writer 和 Artist 从各自的大运行文件，逐步收敛为统一成员运行骨架。

目标不是简单搬文件，也不是只追求删除行数。目标是让核心负责稳定运行流程，让成员只保留身份、固定节点任务、专家清单、工具清单。

这份说明覆盖从现在到最终目的的路线。当前优先级不是立刻做新成员脚手架，而是先把 Writer 和 Artist 这两个现有成员整理干净，解决遗留小毛病，再把稳定下来的结构沉淀成模板。

## 总原则

不要恢复双轨运行。

不要恢复旧开关。

不要让服务或命令行入口重新绕过 CoreLoopKernel + RuntimeKit。

不要自动提交 git。

不要大范围重命名无关文件。

不要处理历史数据迁移里的兼容逻辑，本任务只处理运行路径和大文件职责。

每一阶段必须能跑指定测试，不能只做静态移动。

## 禁止事项

禁止在主应用代码里恢复以下语义：

- Writer 运行路径可通过环境变量切换。
- Artist 运行路径可通过环境变量切换。
- CoreKernel 只是实验路径。
- 服务入口保留两套运行逻辑。
- 命令行入口保留另一套旧运行逻辑。

如果发现测试仍在验证这些旧语义，应改成验证默认单轨，而不是让代码重新兼容旧语义。

## 目标结构

核心提供：

- 通用运行流程。
- 状态推进。
- 工具执行。
- 专家调度。
- 事件发布。
- 产物记录。
- 错误恢复。
- 最终验收入口。

成员提供：

- 身份。
- 固定节点任务。
- 专家清单。
- 工具清单。

必要时成员可以扩展状态、事件和产物，但不能复制完整运行循环。

## 阶段一：先拆 Artist

Artist 比 Writer 更适合先拆，因为主入口已经走统一核心，剩下的大文件主要是辅助能力和旧循环混在一起。

### 要做的事

把 Artist 大运行文件里的这些内容拆出去：

- 身份提示词。
- 依赖对象。
- 运行结果和步骤模型。
- 回复整理。
- 图片上下文。
- 生图执行准备。
- 视觉验收和视觉记忆。
- 图片关系和产物登记。

拆出去后，Artist 的主运行文件只应保留：

- 收集入口参数。
- 调用统一核心。
- 把核心结果转成 Artist 事件。
- 把核心结果转成服务需要的响应。

旧执行循环如果无法一次删除，必须单独隔离，不允许继续和新主路径混在同一个主运行文件里。

### 阶段一必须运行

```powershell
$env:PYTHONPATH='E:\LamTools\core\src;E:\LamTools\members\Artist\backend'
py -3.14 -m pytest members\artist\backend\tests\test_artist_core_kernel_adapter_unit.py -q
```

如果改了 Artist 更多测试覆盖到的行为，也要补跑对应测试。

### 验收点一：必须等待 Codex 验收

完成阶段一后停止，不要继续阶段二。

提交给 Codex 验收的信息：

- 拆出了哪些业务块。
- Artist 主运行文件还剩什么职责。
- 是否还有旧执行循环。
- 测试结果。
- `git diff --stat`。
- `git status --short`。

Codex 验收通过后，才能继续阶段二。

## 阶段二：再拆 Writer 的纯业务能力

Writer 文件更大，不能先动主循环。先拆纯业务能力，降低风险。

### 要做的事

优先拆这些不应该留在运行文件里的内容：

- 任务大小判断。
- 计划确认。
- 规划提示。
- 最终验收提示。
- 工具失败分类。
- 失败恢复建议。
- 上下文长度控制。
- 工具结果摘要。
- 文件工具和测试工具的旧重复实现。

拆出后，测试应直接验证新业务模块或 CoreKit 工具，而不是继续通过 Writer 大运行类访问这些能力。

不要优先动复杂的 git 分支、架构设计决策、记忆写回。那些放到后续阶段。

### 阶段二必须运行

```powershell
.\scripts\test.ps1 core

$env:PYTHONPATH='E:\LamTools\core\src;E:\LamTools\members\writer\backend'
py -3.14 -m pytest members\writer\backend\tests\test_writer_core_kernel_adapter.py members\writer\backend\tests\test_writer_core_http.py -q
```

如果迁移了 Writer 旧单测，也要补跑相关单测。

### 验收点二：必须等待 Codex 验收

完成阶段二后停止，不要继续阶段三。

提交给 Codex 验收的信息：

- Writer 拆出了哪些纯业务能力。
- 哪些测试已从旧大运行类迁移。
- Writer 主运行文件减少了哪些职责。
- 测试结果。
- `git diff --stat`。
- `git status --short`。

Codex 验收通过后，才能继续阶段三。

## 阶段三：收敛服务和命令行入口

这一阶段只做入口检查和补漏。

### 要做的事

检查服务和命令行入口是否只走统一核心。

检查测试是否仍在证明旧路径是正确行为。

检查主应用代码中是否还有旧路径残留。

如果发现入口层有旧路径，不要加兼容分支，直接改到统一核心。

### 阶段三必须运行

```powershell
.\scripts\test.ps1 core

$env:PYTHONPATH='E:\LamTools\core\src;E:\LamTools\members\writer\backend'
py -3.14 -m pytest members\writer\backend\tests\test_writer_core_kernel_adapter.py members\writer\backend\tests\test_writer_core_http.py -q

$env:PYTHONPATH='E:\LamTools\core\src;E:\LamTools\members\Artist\backend'
py -3.14 -m pytest members\artist\backend\tests\test_artist_core_kernel_adapter_unit.py -q
```

还必须执行主应用扫描：

```powershell
rg -n "LAMWRITER_CORE_KERNEL|LAMARTIST_ARTIST_CORE_KERNEL|core_kernel_experimental|_core_kernel_enabled|_experimental_core_kernel_mode|runtime\.run\(|from app\.core\.writer\.runtime import|WriterRuntime\(|WriterRuntimeDeps" members\writer\backend\app members\writer\backend\writer_cli members\Artist\backend\app core\src scripts
```

扫描结果里只允许出现仍未迁移的旧大文件内部自引用，不能出现在服务入口、命令行入口或 CoreKit 新路径中。

## 完成标准

阶段完成不是看文件是否变多，也不是看行数是否大幅下降，而是看职责是否清楚。

合格标准：

- 服务和命令行入口只有统一核心路径。
- 成员主运行文件不再承担所有业务。
- 工具、专家、上下文、验收、产物登记各有明确归属。
- 测试验证默认单轨。
- 主应用代码不再出现旧开关语义。
- 工作区改动可以用 `git diff --stat` 清楚解释。

不合格标准：

- 只是移动代码，没有改变依赖方向。
- 新文件继续变成另一个大垃圾桶。
- 固定节点任务里重新写完整运行循环。
- 工具里偷偷调用模型并决定主流程。
- 专家里直接修改主状态。
- 为了让旧测试过，又恢复旧路径兼容。

## 输出格式

每个阶段完成后只输出：

- 本阶段改动摘要。
- 测试结果。
- 剩余风险。
- `git diff --stat`。
- `git status --short`。
- 是否需要 Codex 验收。

不要提交 git。Codex 验收后再决定是否提交。

## 后续阶段四：定义成员四件套

前三阶段完成后，不要马上做新成员脚手架。先把 Writer 和 Artist 已经验证过的做法整理成稳定结构。

### 要做的事

正式定义成员需要填写的四类内容：

- 身份。
- 固定节点任务。
- 专家清单。
- 工具清单。

这四类内容必须是业务声明，不是新的运行循环。

身份说明成员是谁、做什么、不做什么、输出风格和默认原则。

固定节点任务说明在核心运行流程的固定位置做什么，比如准备上下文、工具结果整理、最终验收、完成后写回。

专家清单说明成员可以调用哪些专家，以及每个专家适合解决什么问题。

工具清单说明成员可以使用哪些能力、参数边界、权限边界和失败形态。

### 交付物

- 一份核心层面的成员四件套说明。
- Writer 的四件套草案。
- Artist 的四件套草案。
- 当前 CoreKit 与四件套之间的缺口清单。

### 验收点三：必须等待 Codex 验收

完成阶段四后停止。

提交给 Codex 验收的信息：

- 四件套边界是否清楚。
- Writer 和 Artist 是否都能用这套语言表达。
- 哪些能力应该进核心。
- 哪些能力应该留在成员。
- `git diff --stat`。
- `git status --short`。

Codex 验收通过后，才能继续阶段五。

## 后续阶段五：完善 Writer 和 Artist

新结构落地后，首要目标是完善现有 Writer 和 Artist，不是马上造新成员。

### Writer 完善重点

解决工程执行中的遗留小毛病：

- 上下文里该出现的项目规则、测试入口、最近失败要稳定出现。
- 最终验收不能只看模型说完成，要看产物、测试、未解决问题。
- 工具失败要有清晰恢复建议。
- 文件读写和测试工具要统一走工具清单，不再散落在旧运行文件。
- 命令行和服务表现要一致。
- 事件展示要减少重复和旧字段依赖。
- 旧测试要逐步迁移到业务模块和核心路径。

### Artist 完善重点

解决视觉创作中的遗留小毛病：

- 当前主图、参考图、父图、根图关系要稳定进入上下文。
- 修改上一张图时不能误变成重新画一张。
- 视觉验收要能区分硬失败和可接受瑕疵。
- 视觉记忆要记录用户偏好，但不能把无关偏好塞进每一轮。
- 生图结果、图组、分支、验收结论要统一登记为产物。
- 命令行和服务表现要一致。
- 旧循环测试要逐步迁移到核心路径和业务模块。

### 交付物

- Writer 遗留问题清单和修复结果。
- Artist 遗留问题清单和修复结果。
- 关键路径测试结果。
- 主入口扫描结果。

### 验收点四：必须等待 Codex 验收

完成阶段五后停止。

提交给 Codex 验收的信息：

- Writer 修了哪些遗留问题。
- Artist 修了哪些遗留问题。
- 哪些问题仍需后续处理。
- 测试结果。
- `git diff --stat`。
- `git status --short`。

Codex 验收通过后，才能继续阶段六。

## 后续阶段六：核心能力沉淀

只有当 Writer 和 Artist 都证明某些能力是共性时，才把它们沉到核心。

### 应沉到核心的能力

- 固定运行流程。
- 固定节点任务协议。
- 工具注册和权限边界。
- 专家注册和调度。
- 标准事件。
- 标准产物。
- 标准状态推进。
- 记忆候选检索和上下文预算。
- 最终验收入口。

### 不应沉到核心的能力

- Writer 专属工程规则。
- Artist 专属视觉判断。
- 单一成员才需要的工具参数习惯。
- 单一成员才需要的产物解释。
- 还没有被两个以上成员验证过的抽象。

### 交付物

- 核心能力清单。
- 成员保留能力清单。
- Writer / Artist 依赖方向检查。
- 核心测试结果。

### 验收点五：必须等待 Codex 验收

完成阶段六后停止。

提交给 Codex 验收的信息：

- 哪些能力沉到了核心。
- 为什么这些能力是共性。
- Writer 和 Artist 是否仍能表达自己的差异。
- 测试结果。
- `git diff --stat`。
- `git status --short`。

Codex 验收通过后，才能继续阶段七。

## 后续阶段七：样板和脚手架

只有在 Writer 和 Artist 都稳定后，才开始更新新成员模板。

### 要做的事

把已经验证过的结构整理成新成员模板。

新成员默认只填写：

- 身份。
- 固定节点任务。
- 专家清单。
- 工具清单。

如果新成员需要特殊状态、事件或产物，可以扩展，但不应该复制运行循环。

### 交付物

- 新成员模板。
- 新成员创建说明。
- 一个干跑示例。
- 验证命令。

### 最终验收点：必须等待 Codex 验收

提交给 Codex 验收的信息：

- 新成员是否真的不需要复制运行循环。
- 模板是否只暴露必要内容。
- Writer 和 Artist 是否仍是首批样板。
- 干跑结果。
- `git diff --stat`。
- `git status --short`。

Codex 验收通过后，才可以考虑提交归档。

## 总路线

当前路线分为七段：

1. 先拆 Artist，让 Artist 主运行文件变轻。
2. 再拆 Writer 的纯业务能力，避免一上来碰最复杂主循环。
3. 收敛服务和命令行入口，确保默认单轨。
4. 定义成员四件套，让 Writer 和 Artist 都能用同一套语言表达。
5. 优先完善 Writer 和 Artist，解决遗留小毛病。
6. 把被两个成员验证过的共性能力沉到核心。
7. 最后再更新样板和脚手架，让新成员只填模板。

最终目的不是“删掉两个文件”，而是让 LamTools 的成员体系变成：核心稳定、成员轻量、差异清楚、现有产品更可靠、新成员更容易创建。
