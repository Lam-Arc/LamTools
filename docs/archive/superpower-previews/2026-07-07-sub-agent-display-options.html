Writer Sub Agent 显示方案预览

目标是把“一个主会话委托一个可复用 sub session”的 MVP 讲清楚：用户要能看出谁在跑、编号是多少、做了什么、结果如何，同时不把界面重新扩张成复杂 Agent 管理台。

范围 GUI + CLI 显示方案 2026-07-07
最低认知成本 用户不用理解 agent 系统，也能知道这是一次委托。
日志可查 编号 `001/002` 必须在 GUI 或 CLI 中稳定可见。
不鼓励并行误解 MVP 只有顺序委托，显示不能暗示多 agent 池。
可渐进扩展 未来多个执行方时能自然扩展，不推翻当前结构。
方案一：内联委托行 方案二：子时间线 方案三：右栏运行账本 方案四：结果优先 方案五：CLI 镜像
01最小改动 / 推荐起点

内联委托行

把 sub agent 当成一条更聪明的工具调用显示。主时间线不新增结构，只在工具行里补 `001 · worker`、模型、子会话 ID。

  • 适合当前 MVP，最少 UI 改动。
  • 风险复杂子任务的内部步骤会显得拥挤。
  • CLI一行 start、一行 done，和普通工具输出一致。

02推荐定稿方向

子时间线

主 Writer 时间线中打开一个 scoped child chat，但不新增一套视觉样式。标题是 sub name；Writer 发给它的委托内容显示为这条子时间线里的用户信息；子 agent 的思考、工具、结果继续使用 Writer 本身的时间线样式。

  • 适合准确表达“委托方 / 执行方”的产品语义。
  • 风险需要控制缩进和标题，避免层级过深。
  • CLI普通模式用缩进镜像子时间线，`--raw` 保留完整事件。

03长任务监控

右栏运行账本

主时间线保持安静，右侧栏显示当前父会话下的 sub session 账本：编号、名字、模型、最近状态。适合长任务，但比 MVP 多一点信息架构。

  • 适合用户频繁查状态、看多个历史委托。
  • 风险右栏刚刚做过减法，容易重新变重。
  • CLI`writer status` 可补一个 Sub sessions 小节。

04阅读优先

结果优先 handoff

把子 agent 的最终交付放在最前面，内部过程退到“查看证据”。适合 Writer 的主阅读流，用户先看到结论，再决定是否展开细节。

  • 适合主会话结果质量比过程审计更重要。
  • 风险如果失败，需要额外露出诊断入口。
  • CLI默认输出 done 摘要，`--verbose` 展开 evidence。

05CLI / GUI 同构

事件日志镜像

GUI 直接采用接近日志的表格化事件流，CLI 与 GUI 字段完全一致。它最利于排查，但产品感最“工程化”。

  • 适合内部调试、开发者模式、验收报告。
  • 风险普通用户会觉得噪声偏多。
  • CLI同一套事件字段，不再单独设计文案。

建议选择

按你的方向，建议定稿为“方案二：子时间线”。主 Writer 时间线只承担委托和接收结果；sub timeline 标题显示 `001 · subName`，Writer 发给它的委托作为子时间线里的用户信息，子 agent 的思考、工具调用、工具结果和最终回复尽量复用主 Writer 的展示组件。右栏账本先不做，避免重新增加信息架构负担。
