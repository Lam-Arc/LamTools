# 压缩架构审查

审查对象：当前工作区相对 f8ac4a27 的未提交压缩改动，以及它依赖的自动压缩、手动 /compact、保存恢复和右侧资源卡片。只做代码及隔离测试，没有运行真实模型、修改真实会话或运行全量测试。

## 用户设计和验收口径

用户原文：“压缩信号有两条路径来触发：一条是自动压缩，另一条是手动/compact”。自动路径按上下文占用超过阈值触发，占用优先使用真实 usage，没有则使用兜底估算。卡片显示同一个占用值。

补充原文：“慢一拍的话是可接受的，因为提前留了 20% 的阈值给他，主要是要保证优先使用真实 usage”。

据此，**上一轮真实 usage 优先于更大的本地估算，且允许一拍延迟，不作为缺陷**。不建议以 max(真实值, 估算值) 替换用户规则。早期审查中的“新增内容增长而旧 usage 较小”测试已按补充说明改为正常行为验收，并已通过。

这里的 context window 按用户原意指“当前占用”，与模型总容量分别记录即可，不需要强迫用户改变叫法。代码中的 context_window_tokens 实际表示容量，estimated_prompt_tokens / context_usage_prompt_tokens 表示占用，内部命名应避免混淆。

## 是否实现了原设计

| 要求 | 结论 |
| --- | --- |
| 自动、手动压缩进入同一处理流程 | 基本实现：都调用 ContextCompactionController；保存结果的代码仍分叉 |
| 有真实 usage 就优先使用它 | 已实现主要分支；较大估算不会覆盖真实值，允许的一拍延迟验收通过 |
| 无真实 usage 则估算 | 首次无 usage 可正常兜底；后续响应缺失 usage 时旧值不清除，可能无限沿用 |
| 卡片显示同一个占用值 | 未完整实现；卡片会从历史消息捞旧 usage，覆盖最新快照的估算 |
| 再次超过阈值仍可压缩 | 未实现；同一 run 只允许成功压缩一次 |

## 高优先级问题

### 1. 压缩后新增工作的检查点不再落盘（既有架构问题，P1）

位置：kernel/loop.py:4300、2508–2512、2524–2542。

压缩改写内存 history 后将 _persisted_len 置为 None；之后 _save_checkpoint 调用的 _flush_history_delta 直接返回。新助手消息和工具结果直到正常退出/取消时的全量替换才持久化。进程崩溃或断电不会执行这条收尾路径。

例子：压缩完成后继续修改文件并收到成功结果，程序写了运行状态检查点，但断电重启后，加载的上下文缺少这些后续成功记录，可能重复执行工作。隔离测试通过真实保存接口执行检查点，再从存储读取，已确认新增记录缺失；未实际强杀用户应用。

自动路径会全量替换历史，手动路径只保存摘要和过滤集合，二者持久化语义不同。history 重写和摘要状态保存也不是同一事务。文档所说“只改变派生上下文、不改原历史”与自动路径实际行为不符。追加式 dialogue 记录目前不是这条恢复路径的权威来源，不能消除上述缺口。

### 2. 同一轮任务压缩一次后永久跳过再次压缩（既有架构问题，P1）

位置：kernel/loop.py:4181–4182。

_context_compaction_run_id 等于当前 run_id 就直接返回，即使真实 usage 已再次超过阈值。多个文件加入的“可无限次压缩”说明没有改变这条规则。

例子：长任务在第 20 步压缩一次，第 60 步又达到阈值；没有新用户回合就无法再压缩。主代理和 KernelSubAgentRunner 共用 CoreLoopKernel，二者都受影响。

应以“上下文是否已更新、上次压缩是否确有缩减”防止空转，而不是禁止整轮任务再次压缩。

### 3. 新 usage 存储位置没有完整的失效规则（本次改动引入，P1）

位置：kernel/loop.py:4009–4017、4130–4146；app/command_execution.py:534–545。

新实现从旧的 context_usage_anchor 改为 runtime_context_metrics.context_usage_prompt_tokens。但响应 usage 缺失或为 0 时直接返回，不清除旧字段；手动压缩仍只删除旧 anchor 键，保留新字段。不是用户接受的一拍延迟，而是测量可能长期没有更新。

例子：旧请求 usage 为 9000，手动压缩成 1000，旧 9000 仍保留，接着可能立即再触发自动压缩。接口此后持续不返回 usage，也不会回到估算分支。有效性规则需要同时覆盖自动、手动、换模型和恢复。

### 4. 触发、拟合和摘要请求没有使用同一套估算单位（本次改动引入，P1）

位置：context_compaction_budget.py:270–275；context_compaction/controller.py:362–374。

触发时估算乘 2.5，但传给规划和最终拟合的回调没有乘。隔离测试中相同输入触发测得 250，拟合测得 100。因此按同一安全标准，占用为 15000 的结果可能被当作 6000 而接受，不能声称已满足硬上限。

保留用户要求的 2.5 倍估算，将其放在统一测量边界；真实 usage 不乘倍率。

### 5. 已拟合的请求随后被增大，最后只做粗估（f8ac4a27 引入，P1）

位置：kernel/loop.py:4303–4353。

摘要和历史已经拟合后才重建系统提示词、追加完整运行时快照。末尾只在替换过第一条系统消息时做 fast=True 检查；估算异常还被当作 0 放行。

隔离测试把系统提示词重建为 20000 个中文字符，最终细估 13939，窗口 10000，函数仍正常返回。不是一拍 usage 延迟的问题，而是“检查合格后又改内容”缺少最终检查。

### 6. 卡片复用了已失效的历史 usage（本次前端改动保留的问题，P1）

位置：core/ui/src/runtime/resources.ts:38–65。

遍历全部历史快照时，只在读到数值时更新 providerPromptTokens；新快照没有 usage，不会清空历史读数。后端换模型后正确进入估算分支，卡片仍可能显示旧模型的 usage。

隔离测试：旧模型 usage 7000；新模型最新快照估算 2000、容量 10000。卡片显示 70%，应为 20%。这与接受一拍延迟无关，是后端已经提供新快照后前端仍使用旧来源。

## 建议的最小架构

保留现有摘要、规划和拟合算法，收口三个边界即可：

1. **一个占用快照。** 后端负责选择真实 usage 或兜底估算，同时提供数值、来源、模型、对应的请求/上下文版本。自动判断和卡片都消费这个快照；卡片不再独立搜索历史重算。明确允许一拍延迟，真实值不被较大的估算覆盖。
2. **一个压缩入口。** 自动超阈值与手动 /compact 产生同一种压缩信号。手动只跳过阈值判断，后续压缩、结果检查、测量更新和保存完全一致。同一轮可以多次压缩。
3. **原始记录持续追加，压缩只更新视图。** 摘要、覆盖边界和版本一次性提交；后续消息始终正常保存。全部系统提示词、工具和快照变化合入后，再对最终请求做统一检查。

Rust 可渐进承接占用快照、压缩状态提交和版本校验。Python 的模型调用与可靠算法可保留。只换成 Rust 不会自动消除这些状态和事务问题。

## 0.3.22 重构结果

用户随后要求“去重构吧”“做完打包，发布，写wiki”。保留真实 usage 优先与一拍延迟的原设计，完成以下收口：

- 自动和手动共用占用测量、压缩 Controller、视图加载和提交。
- 原始历史只追加；摘要保存覆盖集合，后续检查点继续正常写入，不再等待整轮结束。
- SQLite 原子提交摘要与新增运行时基线；注入提交失败时两者一起回滚。
- 系统提示与快照先准备、先计入最终预算，合格后才发布；取消不会污染旧基线。
- 取消 run_id 对第二次压缩的封锁，重复压缩累计覆盖范围。
- 真实值缺失时回到估算，完成压缩清除旧 usage；本地估算统一乘 2.5。
- 卡片直接显示后端最新占用；旧模型和同一回复旧片段不再覆盖新快照。
- 旧数据库迁入追加表后清除旧副本，零尾部不会重新加载已摘要的原文。
- 保留可靠 Python 模型调用和 SQLite 事务所有者，没有增加另一套 Rust/Python 并行控制服务。后续迁移 Rust 时可替换共享边界，不需更改用户规则。

最终新增验收：后端 20 项通过（架构 17 项、估算 3 项）；前端 8 项通过。包括完整自动/手动压缩、同轮二次压缩、数据库重新打开、取消、事务回滚、旧数据库空尾部、压缩期间子代理结果到达等情形。仅运行本轮新增相关测试，没有运行全量测试。
