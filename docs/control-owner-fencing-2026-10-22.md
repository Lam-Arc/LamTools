# 暂停与成员恢复：所有权和旧结果写入约束

user:“修 问题严重的话 就重新设计”+(修复已复现的控制缺陷，并重新划分对账、执行和结果提交的责任)。

## 判断与实施范围

本次四项问题有共同的架构原因：持久状态对账对象被当作执行所有者，异步收尾没有绑定原执行，结果写回没有验证它是否仍有权修改状态。本次重做这段 Python 控制链路，保留已有模型、工具与检查点实现。

这不是完整 Rust 控制服务迁移。现有 Rust runtime 没有直接接管桌面 Python 回合的桥接；把状态机另写一份会增加第二个写入者。独立 Rust 控制通道、执行器进程隔离、意图/回执/outbox 单事务和全部 127 项边界仍按原迁移方案实施，不用本次测试冒充完成。

## 新约束及代码落点

1. `live_operations._PauseTarget` 固定逻辑回合、登记表执行、运行时执行和代次。等待任务退出后重新验证目标；运行时修改在原子 patch 内再次验证。恢复、新执行或终止使旧代次失效。
2. 暂停的短状态提交通过会话控制锁串行，关卡片和取消续跑工作限定到目标回合。耗时退出等待位于锁外。成员暂停拿到自己的锁后再次验证目标，防止等待锁时恢复已经发生。
3. 暂停事件只写存在的逻辑回合，携带真实执行编号。父已完成但子仍运行时只暂停成员，不重开父回合。镜像的比较写入失败后直接放弃，不再无条件覆盖。
4. 成员登记表只接纳可执行的监督器，并保留现有所有者。对账复用它；冷启动无所有者时，临时投影对象只修复持久记录。关闭的所有者从索引移除。
5. 恢复、暂停和终止在无缓存时使用生命周期工厂构造真实运行器。运行器继承所属会话的工作目录和权限。恢复必须完成实际执行，而不是只短暂显示 running。
6. 成员持久记录增加 `execution_token`。启动、内联审批、暂停、终止都会更新凭据；后台运行与审批结果必须匹配它。SQLite 条件更新同时验证凭据与非终态，防止另一连接已提交的终止被覆盖。
7. 终止覆盖 running、pending、paused、suspended、interrupted 成员。迟到的成功、等待、失败和取消结果均不得覆盖 terminated；重建同名成员后，旧凭据也不得写入。
