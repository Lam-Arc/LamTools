# 资料库与方案：设计与使用

一份**方案**是一次需求的可交付文档：需求与边界、取舍、分步清单、目标与完成判据、风险、还没定的问题。
它是一篇**存放在项目文件夹里、会被保存、被编辑、被另一台机器执行的 Markdown 文档**，不是一段聊完就滚走的回答。

一句话记住它的边界：**方案是文档，会话清单是这一轮正在做的事。** 方案可以没有任何人执行；会话清单一旦建立就代表有人正在做。

---

## 一、它用来干什么

- 把用户一句话里没说清的东西问出来，写成别人**不用再问作者**就能开工的文档。
- 手机起草、桌面核对后开工：方案是项目「方案/」文件夹里的普通文件，桌面和手机各自看到自己项目文件夹里的那份。
- 让"开工"这个决定**与"想清楚"分开**：定稿（就绪）之前，方案只是文档，什么都不会被执行。

它不负责：

- 不负责执行本身。开工之后真正干活的是会话（见第六节）。
- 不负责保存长篇正文之外的版本历史。文件就是当前唯一的真相；改错了直接改回来，项目自带的版本管理也在。
- 不是待办清单的替代品，也不是目标（goal）的替代品——它只是把这两样**在你决定开工时**交出去。

---

## 二、它不是什么：方案 vs. 会话清单

| | 方案（文档） | 会话清单（checklist / goal） |
|---|---|---|
| 是什么 | 一篇文档，描述"打算怎么做" | 当前这一轮正在做的状态 |
| 谁来用 | 人来看、来改、来批准 | 执行中的助手每步更新 |
| 谁创建 | 助手起草，或人直接写文件 | 助手用会话内的清单能力建立 |
| 是否执行 | 不执行；就绪也只是"可以开工了" | 建立即代表正在做 |
| 时间跨度 | 跨会话、跨天、随项目文件夹存在 | 只属于当前这一次会话 |
| 生命周期 | 草稿 → 就绪 → 执行中 → 完成 | 随会话存在，会话结束即上下文 |

关键差别有三点：

1. **方案是被批准的对象，清单是被执行的对象。** 开工是把方案里的目标与步骤装进会话清单（见第六节），装进去之后清单才是"活的状态"，方案仍是"那份文档"。
2. **方案可以没有清单。** 草稿阶段步骤为空是正常的；而清单为空就没有意义。
3. **写清单不等于写方案。** 助手当前这一轮的步骤用会话内的清单工具；把一次需求变成可交付的方案走的是方案起草技能。

---

## 三、怎么用：一段用户视角的流程

以"用户想在手机上记一个想法，回到电脑上让助手做"为例：

1. **用户开口。** 在手机上对助手说一句想法，比如"我想让设置页里的下载能续传"。这句话本身不构成方案。
2. **助手闲聊着把想法问全。** 助手不急着产出一份完整文档，而是先接住用户的话，再把用户脑子里有、嘴上没说的点逐一补问（做完了是什么样、哪些这次不做、有没有不能碰的东西）。一次最多问两三个，问的是**会改变方案的事**；能按常规决定的直接决定，并记成"假设"让用户看得见。
3. **草案逐步成形，允许口语化、允许不完整。** 早期草案写得像用户自己的话，缺步骤、缺取舍都正常，因为它只是给用户确认的。写下来的位置是项目根目录的「方案/」文件夹。
4. **用户确认的是业务表现。** 助手让用户确认的是"做完了用户会看到什么、这次不做什么"，而不是技术选型——除非用户自己主动提了技术要求。
5. **一件件补齐，直到清单成立。** 随着用户补充，需求、取舍、步骤、目标与完成判据、风险被填上；步骤写的是"改了什么、怎么知道改完了"。
6. **用户说"就这么办"。** 助手把文件开头的状态从草稿改成**就绪**（就绪至少要有一步），并说明还没执行。
7. **回到桌面核对后开工。** 用户在桌面的资料库里点开这份方案，点"开工"；助手对照本机仓库现状核对（路径是否存在、前提是否成立），把出入先记下结论并更新方案文件，再把目标与步骤装进当前会话清单，逐步开工。
8. **收尾。** 完成判据满足并有证据之后，助手把方案状态改为完成。

## 四、文件形态

每份方案是「方案/」文件夹里的一个 Markdown 文件（如 `方案/导出显示进度.md`）：

```markdown
---
状态: 草稿
摘要: 一句话，列表里能显示的那种
---

# 标题

## 需求与边界
- 复述：……
- 完成后能看到：……
- 这次不做：……
- 假设：……

## 取舍
- 选定：……，因为……
- 被否：…… — ……

## 步骤
1. 改什么 — 验证：怎么知道做完了

## 目标与完成判据
- 目标：……
- 判据：……

## 风险
- …… — 可能性 — 对策

## 未答问题
- …… — 卡住哪一步
```

约定：

- 文件开头的小块只有 `状态` 和 `摘要` 两项；状态取 草稿 / 就绪 / 执行中 / 完成。
- **业务小节保持业务语言**（需求与边界、取舍、目标与完成判据、风险、未答问题）；**只有步骤可以出现实现层词汇**。
- 就绪是**对一致的宣告**：用户确认过复述、成功与边界来自用户、至少一个可验证的步骤、会改变方案的未答问题都已回答。没有任何机制拦着，只有起草者守住它。
- 文件没有隐藏历史；想自己改，用任何编辑器都行，改完资料库里看到的就是新的。

## 五、起草姿态（产品负责人的明确要求）

起草技能不只是"把用户的话整理成文档"，它被要求采用**闲聊式收集 + 主动补问**的姿态：

| 要求 | 具体表现 |
|---|---|
| 用闲聊姿态收集想法 | 先接住用户的原话，在对话里把想法聊出来，而不是把用户的一句话直接加工成完整方案 |
| 主动补问，补齐用户脑中的想法 | 用户说出来的往往只是他想到的一小部分；助手要主动把没说的补问出来（做完是什么样、哪些不做、有没有不能碰的），一轮最多三个 |
| 早期草案可以口语化且不完整 | 草案是给人确认的草稿，允许用用户的原话、允许缺项，不必一开始就齐整 |
| 草案确认的是**业务表现**，不是技术方案 | 让用户拍板的是"用户能观察到什么、这次不做什么"；技术选型除非用户主动提出，否则不拿来让用户确认 |
| 只有最后的步骤可以带实现技术词汇 | 业务语言贯穿草案与确认过程；到步骤这一层才允许出现文件、命令、组件等实现层词汇 |
| 反例 | **用户说一句就产出一份完整方案**——这正是本姿态要避免的失败形态 |

## 六、资料库界面

入口在左栏的一排图标里（搜索、资料库、长期安排、插件）。点开资料库，聊天区域整体切换为资料库；返回或 Esc 回到会话。

| 能力 | 说明 |
|---|---|
| 列表 | 列出「方案/」文件夹里的方案：标题、一句话摘要、状态标、更新时间，按更新时间排序；助手刚写完方案时列表自动刷新 |
| 阅读 | 点开读全文，用与聊天同款的排版渲染，读起来像一篇文档 |
| 开工 | 就绪的方案可开工：它把当前会话输入区填入开工指令并发出——要求助手先用文件读取读回方案、对照仓库现状核对并把结论写回方案文件，再按执行技能的流程把目标与步骤装进当前会话的清单，然后逐步开工。必须已选中一个会话 |
| 编辑 | 在文件编辑页直接打开方案文件修改 |
| 删除 | 二次确认后删除该文件 |
| 空态引导 | 没有方案时，界面直接告诉你："在聊天里说出你的想法，助手会把方案写进「方案/」文件夹" |

手机与桌面是同一套界面：手机的命令坞/页脚同样有资料库入口，读到的是手机自己项目文件夹里的方案；两端不自动互相同步。

---

## 七、命令行

任何界面能力都有对应的命令行：

```bash
lamtools plan-library list --work-root <项目目录>     # 列出方案
lamtools plan-library show --work-root <项目目录> <文件名>   # 打印一份方案
lamtools plan-library delete --work-root <项目目录> <文件名> # 删除一份方案
```
