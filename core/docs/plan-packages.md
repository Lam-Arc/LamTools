# 方案（plan package）：设计与使用

一份**方案**是一次需求的可交付文档：需求与边界、取舍、要写的文档、分步清单、目标与完成判据、风险、还没定的问题。
它是一份**会被保存、被修订、被另一台机器执行的文档**，不是一段聊完就滚走的回答。

一句话记住它的边界：**方案是文档，会话清单是这一轮正在做的事。** 方案可以没有任何人执行；会话清单一旦建立就代表有人正在做。

---

## 一、它用来干什么

- 把用户一句话里没说清的东西问出来，写成别人**不用再问作者**就能开工的文档。
- 手机起草、桌面核对后开工：方案在手机和桌面各自本地保存，同一份内容两端可读、可改、可开工。
- 让"开工"这个决定**与"想清楚"分开**：定稿（就绪）之前，方案只是文档，什么都不会被执行。

它不负责：

- 不负责执行本身。开工之后真正干活的是会话（见第六节）。
- 不负责保存文档正文。方案里只记路径（`docs`），正文以项目目录里真实存在的文件为准。
- 不是待办清单的替代品，也不是目标（goal）的替代品——它只是把这两样**在你决定开工时**交出去。

---

## 二、它不是什么：方案 vs. 会话清单

这是最容易混淆的地方，两者的区别如下。

| | 方案（plan package） | 会话清单（checklist / goal） |
|---|---|---|
| 是什么 | 一份文档，描述"打算怎么做" | 当前这一轮正在做的状态 |
| 谁来用 | 人来看、来改、来批准 | 执行中的助手每步更新 |
| 谁创建 | 助手起草，或人在工作台里写 | 助手用会话内的清单能力建立 |
| 是否执行 | 不执行；就绪也只是"可以开工了" | 建立即代表正在做 |
| 时间跨度 | 跨设备、跨会话、跨天 | 只属于当前这一次会话 |
| 生命周期 | 草稿 → 就绪 → 执行中 → 完成 → 归档 | 随会话存在，会话结束即上下文 |

关键差别有三点：

1. **方案是被批准的对象，清单是被执行的对象。** 开工是把方案里的目标与步骤装进会话清单（见第六节），装进去之后清单才是"活的状态"，方案仍是"那份文档"。
2. **方案可以没有清单。** 草稿阶段步骤为空是正常的；而清单为空就没有意义。
3. **写清单不等于写方案。** 助手当前这一轮的步骤用会话内的清单工具；把一次需求变成可交付的方案走的是方案起草技能。工具描述里也明写了这条界线，避免助手把两者混用。

## 三、怎么用：一段用户视角的流程

以"用户想在手机上记一个想法，回到电脑上让助手做"为例：

1. **用户开口。** 在手机上对助手说一句想法，比如"我想让设置页里的下载能续传"。这句话本身不构成方案。
2. **助手闲聊着把想法问全。** 助手不急着产出一份完整文档，而是先接住用户的话，再把用户脑子里有、嘴上没说的点逐一补问（做完了是什么样、哪些这次不做、有没有不能碰的东西）。问题一次一个，问的是**会改变方案的事**，能自己判断的直接按常规决定，并记成"假设"让用户看得见。
3. **草案逐步成形，允许口语化、允许不完整。** 早期草案写得像用户自己的话，缺步骤、缺取舍都正常，因为它只是给用户确认的。
4. **用户确认的是业务表现。** 助手让用户确认的是"做完了用户会看到什么、这次不做什么"，而不是技术选型——除非用户自己主动提了技术要求。
5. **一件件补齐，直到清单成立。** 随着用户补充，需求、取舍、文档路径、步骤、目标与完成判据、风险、待答问题被填上；步骤写的是"改了什么、怎么知道改完了"。
6. **用户说"就这么办"。** 助手把状态从草稿改成**就绪**（就绪至少要有一步），并说明还没执行。
7. **回到桌面核对后开工。** 用户在桌面上打开同一份方案，助手对照本机仓库现状核对（路径是否存在、前提是否成立），把出入先记下结论并更新方案，再把目标与步骤装进当前会话清单，逐步开工。
8. **收尾。** 完成判据满足并有证据之后，把方案标为完成；之前的修订仍可回看。

同步说明：手机和桌面**各自本地保存**自己的那份方案。它们不自动互相同步；界面上的版本与回滚操作的是当前这台机器上的历史。

## 四、状态与生命周期

状态只有五个，允许的流转由契约固定，界面只提供契约允许的目标状态：

| 状态 | 含义 | 由谁设置 |
|---|---|---|
| `draft` 草稿 | 还没定稿，人可以改、可以补充 | 起草时默认；从就绪退回时也回到这里 |
| `ready` 就绪 | 可以开工了；**至少需要一个步骤**才能进入 | 作者（助手或工作台里的人）显式设置 |
| `executing` 执行中 | 已经被交给会话执行 | 执行方在开工时显式保存设置 |
| `done` 完成 | 完成判据满足并有证据 | 执行方在收尾时显式保存设置 |
| `archived` 归档 | 不再活跃 | 除归档自身外，任意状态都可进入 |

允许的流转：`draft → ready / archived`；`ready → draft / executing / archived`；`executing → done / archived`；`done → archived`；`archived` 无出口。

两条要点：

- **就绪是一道闸门。** 步骤为空就不允许定稿（界面会直接拦下并说明原因）。
- **执行中与完成没有自动开关。** 代码里没有"开工即自动改状态"的联动；它们由执行方显式保存设置（详见第九节关于 `record_execution` 的说明）。

## 五、起草姿态（产品负责人本次明确要求）

起草技能不只是"把用户的话整理成文档"，它被要求采用**闲聊式收集 + 主动补问**的姿态：

| 要求 | 具体表现 |
|---|---|
| 用闲聊姿态收集想法 | 先接住用户的原话，在对话里把想法聊出来，而不是把用户的一句话直接加工成完整方案 |
| 主动补问，补齐用户脑中的想法 | 用户说出来的往往只是他想到的一小部分；助手要主动把没说的补问出来（做完是什么样、哪些不做、有没有不能碰的），一次问一个 |
| 早期草案可以口语化且不完整 | 草案是给人确认的草稿，允许用用户的原话、允许缺项，不必一开始就齐整 |
| 草案确认的是**业务表现**，不是技术方案 | 让用户拍板的是"用户能观察到什么、这次不做什么"；技术选型除非用户主动提出，否则不拿来让用户确认 |
| 只有最后的清单可以带实现技术词汇 | 业务语言贯穿草案与确认过程；到步骤/清单这一层才允许出现文件、命令、组件等实现层词汇 |
| 反例 | **用户说一句就产出一份完整方案**——这正是本姿态要避免的失败形态 |

与现有技能文本的关系（如实说明）：`draft-plan` 技能当前已写明"一次一个、最多五个问题，只问会改变方案的事"、"其他按行业常规决定并记为假设"、"用户报了什么技术栈就沿用它，否则选保守方案并在理由里说明"。上面表格里"闲聊姿态、草案口语化、业务表现优先、技术词汇只留到最后清单"这几条，是本次明确要求持有的起草姿态；技能文本尚未逐句写出这些措辞，因此以本节为准。

## 六、界面：共享的「方案」工作台

入口在共享界面右栏的模式切换里，与运行 / 文件 / 成果并列；**桌面与手机是同一份界面**（手机复用同一套组件），所以能力一致。

工作台能做的事：

| 能力 | 说明 |
|---|---|
| 列表与筛选 | 列出方案，显示状态、进度（已完成步数 / 总步数）、未答问题数；可按项目、按状态筛选，可切换是否显示已删除 |
| 查看与编辑 | 打开一份方案后逐块编辑：标题、状态、摘要、需求、取舍、文档、步骤、目标与完成判据、风险、未答问题 |
| 步骤状态流转 | 每个步骤可设 待办 / 进行中 / 已完成 / 受阻 / 跳过 / 被替代 |
| 回答待答问题 | 在问题框里写下答案即视为已答；未答的问题会挡在定稿之前 |
| 保存与并发保护 | 保存只提交改动过的字段，并带上读到的修订号；若这份方案已被另一端改过，界面不会覆盖，而是提示并重新载入最新版本 |
| 版本与回滚 | 列出每一次修订，可把某一版回滚（生成一个新修订，历史只增不改）；当前版本标为"当前" |
| 删除与恢复 | 删除是软删除：列表默认不再显示，记录与历史都保留，可恢复 |
| 开工 | 见下 |

**"开工"如何把方案交给会话执行：** 它不引入任何新协议，而是把方案转成**当前会话的一条普通消息**——消息里点明方案标题与编号，要求助手先用方案工具读回这份方案、对照仓库现状核对并把结论写回方案，再按执行技能的流程把目标与步骤装进当前会话的清单，然后逐步开工。

开工按钮的可用条件（界面上会给出不可用的原因）：

- 必须已经选中一个会话；
- 方案状态必须是**就绪**；
- 方案不能是已删除的；
- 没有未保存的改动（先保存再开工）。

## 七、参考：数据契约（字段）

唯一真相（contract of record）是 `core/protocol/plan-package-v1-fixtures.json`（`schema_version: 1`，示例集 29 个用例）。共享界面的类型镜像见 `core/ui/src/plans/types.ts`。

契约把字段分成两类：**两端比较的字段**（换设备后必须一致）与**宿主本地字段**（各端自己管）。

两端比较字段：

| 字段 | 含义 |
|---|---|
| `schema_version` | 契约版本 |
| `plan_id` | 方案编号；平台生成，调用方可显式给定，缺省形如 `plan_<hex>` |
| `title` | 标题，必填 |
| `status` | 五个状态之一 |
| `summary` | 一句话摘要 |
| `requirement.restatement` | 把需求用自己的话说一遍（必填） |
| `requirement.success_looks_like` | 做成之后用户能观察到什么 |
| `requirement.non_goals` | 明确这次不做的 |
| `requirement.assumptions` | 没问、按常规决定的事项，每条都可被证伪 |
| `open_questions[]` | 待答问题：`id` / `question` / `status`(open/answered) / `answer` |
| `approach.chosen` | 选中的做法（必填） |
| `approach.why` | 为什么是它 |
| `approach.rejected[]` | 被否决的方案：`option` / `why` |
| `checklist.design_summary` | 设计摘要 |
| `checklist.steps[]` | 步骤：`id` / `description`（必填）/ `deliverables[]` / `status` |
| `checklist.files[]` | 涉及的文件 |
| `goal.objective` / `goal.completion_criteria[]` | 目标与完成判据 |
| `risks[]` | 风险：`risk` / `severity`(low/medium/high) / `mitigation` |
| `docs[]` | 文档：`path`（项目内相对路径、正斜杠）/ `kind`(research/spec/design/plan/tasks/notes) / `title` |
| `execution` | 执行信息：`thread_id` / `revision` / `started_at`；未执行时为 `null` |

宿主本地字段（导出到另一端时由导入方重新指定）：

| 字段 | 含义 |
|---|---|
| `revision` | 每次被接受的保存 +1；调用方不能指定，只能用修订号做并发检查 |
| `source` | 当前修订由哪一端写入（mobile / desktop）；由主机决定，载荷里给的值被忽略 |
| `project_id` | 所属项目（宿主本地标识），必填 |
| `created_at` / `updated_at` | 时间 |
| `deleted_at` | 软删除标记；非空表示已删除 |

契约里几条会实际影响使用的规则：

- **字符串一律去首尾空白**，列表里的空白项直接丢掉。
- **保存是补丁**：方案已存在时，载荷里没出现的字段保持存储值；方案不存在时按新建处理，缺失字段取缺省值。
- **并发**：给了期望修订号就必须与存储的修订号一致，不一致会被拒绝；没给则不做并发检查（界面总会给，模型工具可以不给）。
- **必填**：标题、所属项目、`requirement.restatement`、`approach.chosen`。
- **步骤**：必须有描述；编号不可重复；状态必须在允许集合内。
- **文档路径**必须是项目内的相对路径：正斜杠、不以 `/` 开头、不含 `..` 段。
- **定稿（就绪）至少要有一步。**
- **回滚**以目标修订号的内容生成一个新修订（历史只增不改）。
- **删除是软删除**，列表不再返回，记录与历史都保留，可恢复。
- **列表顺序**：创建时间倒序，同一毫秒内以编号倒序兜底。
- **历史顺序**：修订号升序，每个被接受的保存都留一版。

## 八、参考：操作与命令

同一个动作有两条入口：界面/助手用的后端操作，以及命令行子命令（本仓库规矩：界面能力必须有对应的命令行）。命令行的子命令是 `lamtools_core.cli ... plan <子命令>`。

| 后端操作 | 命令行对应 | 作用 |
|---|---|---|
| `plan.save` | `plan save`（可配 `--from-file`、各字段开关） | 新建或修订一份方案（补丁式保存） |
| `plan.get` | `plan describe <plan_id>` | 读回一份方案 |
| `plan.list` | `plan ls`（`--project` / `--status` / `--include-deleted`） | 列出方案 |
| `plan.delete` | `plan delete <plan_id>` | 软删除 |
| `plan.restore` | `plan restore <plan_id>` | 恢复已删除的方案 |
| `plan.revert` | `plan revert <plan_id> <revision>` | 把某一版回滚成新修订 |
| `plan.revisions` | `plan revisions <plan_id>` | 列出修订历史 |

补充：

- 命令行另有 `plan export <plan_id> [--out]`，把一份方案导出为文件（例如从手机导出、在桌面导入），与 `save --from-file` 配成一对。
- 助手的工具入口是 `plan_package`，动作只有三个：`save` / `get` / `list`（对齐上面的读与写；删除、恢复、回滚、看历史由界面或命令行完成）。
- **"开工"没有对应的命令行子命令**，因为它不是新的后端能力：它只是往当前会话里发一条普通消息，走既有的对话执行路径，手机与桌面同一条路。

## 九、参考：同一份契约，三处实现，各自的测试入口

三处实现跑**同一份契约文件**；任何一侧改了字段、缺省值或拒绝措辞，都会在另一侧的测试里失败。

| 实现 | 文件 | 契约测试入口 | 测的是什么 |
|---|---|---|---|
| Python 后端（桌面/服务端） | 规则：`core/src/lamtools_core/runtime/plan_package.py`；操作：`core/src/lamtools_core/app/plan_operations.py`；存储：`core/src/lamtools_core/app/core_db.py`（`core_plans` / `core_plan_revisions` 表） | `core/tests/test_plan_packages.py`（`pytest`）：`test_shared_fixtures_hold_for_the_in_memory_store`、`test_shared_fixtures_hold_through_the_sqlite_store` | 全部 29 个契约用例依次跑在内存存储与 SQLite 存储上；另有生命周期、并发冲突、软删除、回滚、命令行等用例 |
| Rust 独立运行时（手机 Tauri 宿主内的存储） | `core/runtime-rs/src/plan_package.rs`（crate `lamtools-runtime`）；宿主命令在 `core/mobile/src-tauri/src/lib.rs`，数据落在手机的 `plans.db` | `plan_package.rs` 内的 `#[cfg(test)] mod tests`（`cargo test`）：`shared_fixtures_hold_for_the_mobile_store` 等 | 用 `include_str!` 载入同一份契约文件，确认契约用例在 Rust 存储上得到同样结果；另测重开后历史仍在、删除与恢复 |
| 手机端桥 | `core/mobile/src/standalone/StandalonePlans.ts`（`planRpc`）与 `core/mobile/src/native/rustAgent.ts` | `core/mobile/tests/standalone-plans.test.ts`（`vitest run`） | 桥本身：契约里出现的每个动作都能通过 `plan.*` 到达宿主、载荷与大小写两种拼法都被接受、缺 id 与非法修订号在到达宿主前就被挡下 |

界面侧另有契约测试：`core/ui/tests/plan-library.test.ts`（`npm run test:contract`，即 `vitest run`），覆盖补丁只提交改动字段、并发拒绝不覆盖、只提供契约允许的状态流转、空步骤不能定稿，以及工作台的列表/编辑/开工/窄屏契约。

关于 `executing` 的如实说明：共享运行时里有一个"记录执行信息"的能力（写入 `execution` 的会话编号、执行的修订号与开始时间，且**不消耗修订号**），但它目前只被测试调用，生产路径没有调用方；也就是说，执行中/完成这两个状态实际由执行方**显式保存**设置，而不是由开工动作自动写入。
