# Office Skills 内测审查（2026-09-10）

## 范围

基线为 `.tmp/office-skills-evaluation/2026-09-10` 下 7 组真实办公任务。本文记录首次产物的视觉问题、CLI/Agent 执行过程、日志体积根因、通用改动及代表场景复测审计。用户确认后完成 Microsoft FY25 Q4 与客户交接复测；新人入职复测按指示未启动。

对应改动已写入共享 `office-design-system.md`，并由 `office-slides`、`office-pdf`、`office-documents`、`office-charts`、`office-infographics` 在精细排版时显式读取。默认流程改为生成前确定版式和内容预算，一次批量生成、一次批量预览；未修改的预览不重复读取，也不默认委派子 Agent 做常规视觉复核。

## 高步数与过程错误根因

96–101 步任务同时包含多种格式、多个自建生成器和大量页面。其高步数不是由 Skill 加载导致，主要来自：

1. 按页面或局部片段反复 `write_file`/`edit_file`，而不是先固定共享组件再一次生成。
2. 生成、渲染、读取、修改、再生成形成多轮循环；同一预览被读取 2–5 次。
3. 大型写文件参数在流式工具调用中被截断，Microsoft 场景有 6 次 `write_file` 失败。
4. shell/path 约定不稳定，14 次 `run_command` 失败包括退出码、跨出 work root 和错误的内联脚本参数。
5. 新人入职任务为视觉检查指定了宿主不支持的模型，子 Agent 失败后再次尝试。
6. checklist 更新共 54 次，虽不是主要成本，但进一步切碎了回合。

`tooling-contract.md` 已加入执行收敛规则：批量读取并复用解析结果；同一格式使用稳定生成脚本；大脚本按职责拆分；命令保持在 work root；相同参数失败不盲重试；checklist 只在阶段变化时更新；普通视觉检查不默认使用子 Agent，也不指定未经确认可用的模型。

## 1.67 GB 日志根因与修正

日志膨胀不是业务正文造成。七组日志中，`runtime.part` 占每组约 93%–98%；其中累计工具参数字段 `runtime.part.arguments_text` 单项占主要体积。模型每生成一小段工具参数就产生一个 transient 事件，而事件同时保存“本次 delta”和“截至当前的完整累计参数”，使大脚本近似平方级重复。

其次，`read_file` 返回 PNG 时，完整 `data:image/png;base64,...` 同时出现在 artifact metadata 和 metadata 中，并在重复读取页面时再次保存。

本轮代码修正：

- `run-local` 与应用持久化保持一致，不再收集仅用于实时 UI 的 transient 事件。
- 对保留的 `tool_input_delta` 只记录字符数、字节数和 SHA-256，不保留累计参数正文。
- 事件日志中的嵌入式 data URL 改为媒体类型、大小和 SHA-256 摘要。
- 超过 16 KiB 的工具参数字符串改为长度、哈希和短前缀，保留审计能力但不复制全文。
- `summary.json` 新增 LLM 回合、工具调用分布、失败率、精确重复率和事件类型分布，后续无需扫描整份事件文件即可比较。

将新规则离线应用到现有 7 组事件后，预计日志由 1,749,224,523 B 降至约 12,621,785 B，减少 99.28%。这是对旧日志的确定性重编码测算，不是新 Agent 运行结果。

## 复测范围与方法

复测保持同一输入和验收口径，比较步数、工具失败率、精确重复率、日志大小、Token、耗时及产物视觉质量。代表场景只覆盖 Microsoft FY25 Q4（复杂 PPT/PDF、原 96 步）和客户交接（低步数基准、原 24 步）；新人入职（原 101 步）未运行，因此没有该场景的复测结论。

财报视觉方面，基线中正值柱状图向下增长的问题已消失，图表方向、数值标签和季度/全年口径更清楚；复测版也增加为 8 个原生可编辑图表和 4 个工作表。不过人工检查发现第 2–8 页及第 10 页的长来源脚注侵入右下页码区域，PPTX 与同版 PDF 均受影响，而运行时几何报告仍声称“0 重叠”。这说明首次图表布局规则有效，但页脚保留区约束尚未被生成器落实，且程序化几何检查没有覆盖页脚与页码冲突。

## 过程审计评分

按直接性与任务规划、失败或途中问题、速度与效率、指令遵循率四个维度，对两次复测的可观测日志和交付结果评分；总分为四项评分的综合判断，不是自动化验收分数。

| 评分维度 | 得分（10 分） | 主要依据 |
|---|---:|---|
| 直接性与任务规划 | 5.8 | 财报在第 23 轮（相对墙钟 131.560 秒、20.5%）才开始正式计划/清单；交接在第 15 轮（82.627 秒、34.2%）才开始。前置能力探测、反复试探和后续修补拉长了进入主线的时间。 |
| 失败或途中问题 | 6.4 | 财报记录 6/95 次工具失败，交接 3/51 次；财报另有公式行映射、验证器预期、两处缺失导入和最终检查语义等隐藏过程故障，且 `python ... | tail` 可能把 Python 失败掩盖为退出码 0。交接失败主要是能力探测和控制台编码。 |
| 速度与效率 | 5.5 | 财报墙钟/模型/工具分别为 641.384/540.08/47.66 秒；交接为 241.735/206.27/10.80 秒。财报较基线略快，交接从 140.720 秒退化至 241.735 秒，且步数、工具调用和 Token 均上升。 |
| 指令遵循率 | 8.9 | 按可明确检查的业务要求及内部 Skill 路由要求约 89% 达成；仍漏选财报 `office-pdf` 与交接 `office-email`，因此未评满分。 |
| **综合** | **6.7** | 产物大体完成且缓存/日志修正有效，但规划进入偏晚、过程故障和交接效率回退仍明显。 |

复测期间清单邻近回合的缓存命中率总体保持在 95%–99%，与日志中 97.57%（财报）和 95.07%（交接）一致，支持“将压缩指令追加为 user 指令”的缓存前缀修正有效。两组日志分别降至 2,399,955 B 和 1,038,366 B，较基线显著缩小。过程证据见两组复测目录下的 `run/summary.json` 与 `run/events-redacted.json`。
