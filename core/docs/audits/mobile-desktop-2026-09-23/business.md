# Mobile capability parity audit (business capability / RPC reachability)

Scope: static code inventory, mobile standalone versus desktop Core Python RPC/tool assembly, plus mobile paired `RemoteTransport` path. Security, persistence correctness, and model-runtime details are assigned to other audits. No code or tests changed. Evidence is repository source, with line references.

## Executive findings

1. **Standalone RPC is a distinct, deliberately partial implementation.** Its dispatcher routes Settings/Extensions/Study/Workflow plus a few session/turn methods, returns successful empty `command.catalog`, and errors for queue create/steer; all remaining desktop RPCs fall through to `{ok:false,error:...}`. Mobile project UI uses a separate `CoreProjectClient` and does have local CRUD/file operations. The clearest user-reachable gaps are queue/steer while a turn is active, Arrange, session export over HTTP, manual update check, and standalone Files/Content search; many other missing operations have no mobile UI route established here.
2. **Plugin/skill catalogs overstate mobile execution.** `plugin.list` advertises five hard-coded plugins, each with empty tools/operations/commands; only Study tools and Study skills are assembled into the native agent. Core skills are listed in mobile but no generic `load_skill` runtime is assembled. Workflow is callable through Rust and can be surfaced by raw workflow RPC, but plugin UI deliberately hides its mode. `plugin.widget.list` is a successful empty stub.
3. **Settings are partial, and mobile state is not desktop configuration source of truth.** Mobile has its own config/settings store and supports provider/model basic CRUD, generic settings namespaces, Sub Agent preferences, hooks/MCP JSON. Desktop config operations additionally expose model groups, import/resolved/runtime capabilities, agents instructions, loadtools, memory/context, retry/imagegen/websearch settings, etc. No equivalence is implied by generic mobile settings namespaces.
4. **Project operations use a separate client; other session RPCs remain partial.** The mobile app injects a `CoreProjectClient` that implements local CRUD, sessions, AGENTS.md, and project files; missing standalone `project.*` RPC branches have no demonstrated UI impact. Android project storage is app-private, which limits direct browsing from Android Files but does not disable in-app project operations.
5. **Paired remote mode is a pass-through tunnel, not a local parity backend.** `RemoteTransport` forwards all RPC requests unchanged to the paired desktop host, so capability behavior is host-defined. Do not attribute standalone gaps to remote mode; separately verify UI does not hide functionality based on the device-local catalog when remote is active.

## Tool assembly and device constraints

- Desktop Python builds dynamic core and plugin tool specs/handlers, MCP, skills, active-mode filtered plugin roots, disabled tools, image generation, shell/command, git, search, documents, memory, and durable tools (`core/src/lamtools_core/app/default_agent.py:2617-2787`; `core/src/lamtools_core/tool/default_toolbox.py:2032-2112`).
- Android Rust explicitly assembles `ProjectFileTools` + MCP for all turns, Study/skill tools only when `study_tools`, and Sub Agent runtime when enabled (`core/mobile/src-tauri/src/lib.rs:531-578`). Android capabilities set `project_files/network/notifications=true`, while other flags default false (`lib.rs:1446-1454`; capability fields `runtime-rs/src/lib.rs:27-38`). This is evidence of omitted shell/git/device capabilities, but not evidence that Android OS makes them impossible. Treat as product implementation choices/migration gaps pending capability policy.
- Native project file tools expose list/read/write in app-private project storage (`core/runtime-rs/src/project_tools.rs:31-95`). The source explicitly warns Android project root cannot be browsed in the Android Files app; external file access needs Android document picker/SAF export/import adaptation. In-app project tools are present.
- Mobile `StandaloneTransport.handleHttp` accepts only local sessions and attachments; unknown paths return 403 (`StandaloneTransport.ts:407-445`). The POST path reads only multipart filename/content-type/byteLength, returns a generated metadata record, and does not persist bytes; the separately-owned runtime audit also found those references later become text-only user input. This transport-level boundary does not establish that authenticated remote project/file APIs are absent.
- Remote path: `RemoteTransport.request` directly invokes `MultiplexedTunnelTransport.request` (`core/mobile/src/connection/RemoteTransport.ts:70-81`); tunnel assigns RPC IDs and transmits requests without method rewriting (`core/mobile/src/connection/TunnelTransport.ts:386-406`). It should inherit desktop host RPC support.

## UI and capability signaling risks

- `SearchShell` conditionally shows session/document tabs based on `plugin.list` (`core/ui/src/components/SearchShell.vue:127,438`); mobile's hard-coded `websearch`/plugin entries plus empty `plugin.ui` surface do not establish a search implementation.
- Plugin editor and skills editor use `plugin.list`/`skill.list` (`CorePluginsEditor.vue:474`; `CoreSkillsEditor.vue:170`): mobile returns placeholder plugin metadata, and skill rows for core skills have no corresponding generic runtime skill loader.
- `plugin.ui.list` hides Workflow based on a now-stale comment while native workflow RPC is implemented (`StandaloneExtensionsStore.ts:173-176`; `StandaloneTransport.ts:187,264`; `lib.rs:1094-1115`).
- `command.catalog` returns success with `[]`; `plugin.widget.list` returns success with `[]`; unknown RPCs return `{ok:false,error}` instead of a protocol-level unsupported error. These need explicit unsupported state/capability signaling so product UI doesn't interpret empty success as complete-but-empty functionality.

## Prioritized bounded implementation packages

1. **RPC truthfulness + core workbench parity**: establish a capability/method inventory and make every unsupported RPC explicit; remove empty-success command catalog, implement command execution/catalog, queue methods, thread read/outline/start, attachments/artifact operations as product priority. Confirm UI either gates or routes these to the host.
2. **Plugin/skill executable parity**: derive plugin catalog from actual native runtime and implement the missing Git/imagegen/websearch handlers and generic core skill loader. Explicit unavailable states can prevent false claims during migration; hiding entries or removing skills is not fulfillment of the user's no-capability-loss acceptance requirement. Keep Study skill loader as the current implemented special case.
3. **Settings/config parity**: map desktop model groups, import/resolved/runtime capabilities, agent instructions, loadtools, memory/context, retries, image generation, and websearch to native-compatible implementations or explicitly gate them. Keep mobile local config semantics clear and avoid reporting success for unconsumed namespaces.
4. **Workflow/UI parity**: expose Workflow mode now that the Rust RPC/backend exists, and validate a real user entry path from `plugin.ui.list` through mode selection into workflow UI.
5. **Reachable standalone RPCs**: prioritize queue/steer, Arrange, session export HTTP, manual update check, and workspace search because shared mobile UI calls them today. Project CRUD is implemented through `CoreProjectClient`; do not add duplicate project RPCs just to mirror desktop. Use Android SAF/document picker only where external import/export is required.
6. **Device capability policy**: decide shell, git, notifications, imagegen, external network/search against explicit product requirements. Current false capability flags / absent runtimes are code choices; no blanket Android OS prohibition was established in this pass.

## Coverage caveats

This is a source-level, bounded business RPC/tool/UI reachability audit. It did not execute the app or enumerate every component call site; it inventories the canonical desktop operation groups, mobile RPC dispatchers and native tool assembly, and key shared UI gates. Security/persistence and model runtime parity are explicitly outside this ownership. Paired remote tunnel remains a host RPC forwarder and must be assessed against paired desktop host behavior rather than standalone handlers.



## Additional reachability validation: search, Workflow, and mobile shell

### Search has a reachable standalone failure

`SearchShell` is reachable from the mobile top bar (`core/mobile/src/App.vue:27`, top bar actions defined in `core/ui/src/components/MobileTopBar.vue:80-87`) and always includes Files/Content tabs; Sessions/Documents are conditionally gated on `lamtools-rag` (`core/ui/src/components/SearchShell.vue:123-126,430-448`). The Files/Content tabs call `workspace.search` (`SearchShell.vue:361-365`), which desktop registers in config operations (`core/src/lamtools_core/config/operations.py:535-614`) but the standalone dispatcher has no handler (`StandaloneTransport.ts:180-235`) and therefore returns its unsupported-method result. Trigger: local/standalone mobile → open Search → enter query on Files or Content. SearchShell catches and displays the backend error (`SearchShell.vue:342-356`), so this is a **P2 visible capability gap**, not silent false success. In standalone, Sessions/Documents are hidden because the hard-coded catalog lacks `lamtools-rag`; Study search tab appears only in Study mode and `study.search` is implemented natively. The paired remote transport forwards calls to desktop, so this standalone finding does not apply when connected to a desktop host.

### Workflow document storage and built-in runner exist; desktop scheduling and external execution do not

Native Rust has durable canonical V2 workflow documents, scoped list/get/save/delete, revision checking, ComfyUI import/export, compile/semantic, and built-in-node `workflow.run` (`core/runtime-rs/src/workflow_store.rs:58-72,117-205`; `workflow_ops.rs:237-345`). The native dispatch explicitly returns unsupported for other `workflow.*` operations (`workflow_ops.rs:339-341`). Its runner rejects requested runtime permissions and resumed/partial executions, and validates only against `NoExternalNodes` (`workflow_ops.rs:103-140`). Thus “workflow backend missing” was too broad; a document/storage + built-in runner slice is present.

Desktop Python Workflow additionally provides create/update/rename, activation/deactivation/list, schedule/event activation, signal/human-task handling, run cancel/resume, queue/history, exposed tools, node catalog/object info, and external executors. Evidence: operation implementations in `core/src/lamtools_core/plugins/bundled/workflow/backend/operations.py:336-652,758-900,903-1193,1239-1478`; schedule activation calls Core Arrange (`activations.py:147-177`; operations.py:758-802); command execution permissions are checked by a permission service (`runtime.py:4426-4482`). Exact mobile trigger: any client submits these unsupported `workflow.*` methods to the existing `StandaloneTransport` prefix dispatcher; Rust returns an explicit unsupported error. In current local UI, Workflow mode is omitted by `plugin.ui.list` (`StandaloneExtensionsStore.ts:169-180`) and no mobile Workflow editor caller was found, so most of these missing methods are **RPC gaps without a demonstrated current UI entry path**. The RPC plugin entry remains visible in plugin management with no matching UI mode (same file lines 16-22, 169-180); this is a discoverability/configuration mismatch. Desktop pairing forwards to desktop implementation.

### Responsive shell, safe insets, and lifecycle

Code-only inspection found a deliberate breakpoint split: top command dock activates at `(max-width: 640px)` (`core/mobile/src/useMobileCommandDockAvailability.ts:3-5`), and `LamToolsApp` shows its sidebar footer fallback for mobile when the dock is unavailable (`core/ui/src/app/LamToolsApp.vue:821-822`). Mobile mode state always includes all modes returned by `plugin.ui.list` (`LamToolsApp.vue:3496-3504`); selecting a mode checks it remains present (`3479-3493`). This means Workflow’s omission is a mode catalog issue, not a narrow-screen-only issue. I found no source-backed tablet-only reachability defect.

Native window-inset bridge returns all four edges (`core/mobile/src/native/windowInsets.ts:3-8,34-44`) and refreshes across rotation/viewport resize (`:54-91`); the host currently applies only the top inset to CSS (`core/mobile/src/App.vue:963-968`). Main UI uses CSS safe-area env for composer bottom and shell (`core/ui/src/styles/workspace-shell.css:45`; `useComposerLayout.ts:60,131`) and the account overlay uses top/bottom CSS safe-area padding (`App.vue:1058-1068`). Because `viewport-fit=cover` is present (`core/mobile/index.html:5`), ignored native left/right/bottom bridge values alone are not sufficient evidence of a defect; no new safe-inset issue is raised from source alone.

Lifecycle recovery is wired: resume listener invokes remote reconnection/session refresh (`App.vue:971-976,828-840`); startup restores local DB, legacy state, account, trusted devices and surfaces initialization failures as status text (`App.vue:842-899`). Failed remote sync selection attempts restoration of the previous remote session and returns errors into panel state (`App.vue:604-619,625-649`). Source inspection did not reveal a new reproducible restoration or exception-state defect.
