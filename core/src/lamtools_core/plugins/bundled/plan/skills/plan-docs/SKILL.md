# 方案文档（plan-docs）

一句话：先把方案归到一类，再按那一类的核心内容写；类型是给人查、给 Agent 读的检索键，不是审批关卡。

方案就是项目 `方案/` 文件夹里的一篇 Markdown。这个技能只管「写什么、算什么类型、算什么状态、怎么验收」，具体起草、修订、执行的对话手法仍由 `draft-plan`、`refine-plan`、`execute-plan` 三个技能承担。

## 1. 九种方案，各回答一个问题

| 类型 | 中文 | 回答的问题 |
| --- | --- | --- |
| PRD | 产品需求文档 | 为什么做、做什么、达到什么效果 |
| SPEC | 技术规范 | 机制、接口、协议、行为与边界是什么 |
| DESIGN | 设计方案 | 视觉、交互、布局与体验长什么样 |
| RESEARCH | 调研方案 | 事实是什么、现状如何、能得出什么结论 |
| EXP | 实验方案 | 假设是否成立、哪条路更优 |
| PLAN | 实施方案 | 分几步做、依赖什么、怎样算交付 |
| AUDIT | 审查方案 | 现有实现有什么问题、证据是什么、怎么改 |
| REPORT | 结果报告 | 实际做成了什么、证据在哪、还欠什么 |

扩展类型按建议归属使用，不必占用一级入口：

| 类型 | 中文 | 归到 |
| --- | --- | --- |
| ARCH | 架构设计 | SPEC |
| ADR | 架构决策记录 | SPEC |
| RFC | 提案与讨论 | DESIGN / RESEARCH |
| POC | 概念验证 | EXP |
| TEST | 测试方案 | PLAN |
| MIG | 迁移方案 | PLAN |
| SOP | 标准操作流程 | PLAN |
| RCA | 根因分析 | AUDIT |

## 2. 先分类，再动笔

- 用户说「写一份 PRD / SPEC / 实验方案 / 审查 / 报告」时，用他说的那一类。
- 用户没说类型时，看**主要目标**选一个，不要为了分类去拆文档。一份方案可以同时承担多种职责，按主要目标归类（PRD §3.2）。
- 历史文档没有 `类型` 字段时，文件名或标题里的关键词只能作为**建议**；不要为了凑类型批量改写历史文件，更不要凭文档自述推断功能已经完成。
- 简单需求可以只有一份 PRD，也可以只有一份 PLAN；专题可以只有一篇。

## 3. 每类方案的核心内容（指导，不是章节清单）

| 类型 | 核心内容 |
| --- | --- |
| PRD | 背景、问题、目标、范围、需求、约束、验收标准 |
| SPEC | 设计目标、技术机制、接口、行为规范、边界条件 |
| DESIGN | 设计目标、使用场景、交互流程、视觉与体验要求 |
| RESEARCH | 调研目标、调查范围、事实依据、发现、结论 |
| EXP | 实验目标、假设、变量、评价指标、实验方法、停止条件 |
| PLAN | 实施目标、现状、实施步骤、依赖、验收要求 |
| AUDIT | 审查目标、审查范围、问题、证据、影响、改进建议 |
| REPORT | 实际成果、验证证据、结论、差异、遗留问题 |

写法上的硬要求（PRD §4）：

- **准确复述用户意图**：读者能在第一屏确认你理解对了。
- **目标与范围明确**：写清这次做什么、不做什么。
- **区分事实、假设、建议与已确认决策**：把「我猜的」写成「我猜的」，把「用户定的」写成「用户定的」。
- **可执行或有研究价值**：需要实施的目标，每条完成标准都要能被验证。
- **不要**：套话、重复内容、无意义的背景介绍、未经验证的技术承诺。篇幅按复杂度决定，短方案是正常方案。

各类的最小骨架见 `references/plan-types.md`（相对插件技能根目录读取）。

## 4. frontmatter：最小元数据

```yaml
---
类型: PRD
状态: 草稿          # 设计状态：草案 / 生效 / 已归档 / 已废弃
实施: 未实施        # 实施状态：未实施 / 实施中 / 待验收 / 已验收（可选）
专题: Sunday Memory # 可选，用来把同一件事的几份方案归到一起
摘要: 一句话，列表里显示
收藏: true          # 可选
关联: 方案/记忆检索机制.md, 会话:<session-id>   # 可选
---
```

- 只写有意义的字段。简单方案只要 `类型` + `状态` + `摘要` 就够。
- 旧文档只写了 `状态: 草稿 / 就绪 / 执行中 / 完成` 也能读：草稿→草案，就绪→生效，执行中→生效 + 实施中，完成→生效 + 已验收。**读得出就不要为了统一措辞改写历史文件。**
- 状态不是门禁：不要求所有方案走完四个状态；研究、审查、报告可以不写实施状态。
- 关联用路径或 `会话:<id>` 即可，不建专用关系库（PRD §10.2）。

## 5. 八种能力落在哪

| 能力 | 怎么做 |
| --- | --- |
| Create | `draft-plan`：对话中确认目标与边界，把方案写进 `方案/`，类型按第 2 节定 |
| Discuss | 直接对话：围绕目标、范围、约束与未答问题提问；结论写回方案 |
| Review | 按第 3 节的核心内容与第 6 节的质量标准逐项核对，问题带证据写回方案或同专题的审查记录 |
| Revise | `refine-plan`：只改用户要求的部分，保留其余；不重复创建 |
| Execute | `execute-plan`：读回方案、核对现状、记录裁定、装清单、按步骤开工 |
| Verify | 用真实证据核对完成标准；对照第 6 节给结果 |
| Report | 写 REPORT 类型文档或直接写回方案：成果、证据、差异、遗留 |
| Organize | 设类型、专题与关联；识别重复 / 失效 / 被替代的方案，但不擅自删除 |

## 6. 验收结果只用这五个词

需要实施的方案，在报告里逐条标注：

| 结果 | 含义 |
| --- | --- |
| PASS | 已验证满足要求 |
| PARTIAL | 部分满足 |
| FAIL | 验证未通过 |
| UNVERIFIED | 尚未验证 |
| BLOCKED | 存在阻塞 |

- 代码存在、编译成功、模拟测试通过，都不等于功能验收通过；要有真实运行、界面操作、测试输出或实验数据作证据。
- 不要求每份方案都写独立验收报告；简单任务直接在方案末尾或相关会话里记录结果。

## 7. 文件与检索

- 方案只放在项目 `方案/` 下（可以嵌套文件夹做专题），用普通文件工具读写；不建方案数据库，不建第二套索引。
- 新建时优先用资料库的「新建方案」（会按类型铺骨架），也可以直接 `write_file` 一篇 Markdown。
- 导出就是把文件复制出去；跨会话继续工作时，先读方案再读它点名的文档，不要一次加载全部历史。
