# 方案类型的写法参考

这是 `plan-docs` 的参考资料：写到哪一类，就只读那一类。骨架是最小形状，不是章节任务；复杂度低就删节，复杂度高就在骨架里加内容，不要为了凑齐章节而写空话。

所有方案都是 `方案/` 下的一篇 Markdown，frontmatter 与正文的约定见 `plan-docs` 技能第 4 节。

## PRD · 产品需求文档

回答：为什么做、做什么、达到什么效果。

```markdown
---
类型: PRD
状态: 草稿
摘要: 一句话说清这份 PRD 要解决什么
---

# <标题>

## 背景与问题
现在是什么情况，谁在受什么影响，为什么现在要做。

## 目标与范围
- 目标：做完之后用户能看到什么。
- 不做：这次明确不碰的东西。

## 需求
逐条写，每条都能被核对；区分已确认的决定、待确认的假设、我的建议。

## 约束与假设
时间、平台、依赖、不能动的边界。

## 验收标准
- [ ] 可观察的结果 1
- [ ] 可观察的结果 2
```

常见错误：把实现方案写进需求；用「提升体验」这类无法验证的句子当验收标准；把没问过用户的假设写成决定。

## SPEC · 技术规范

回答：机制、接口、协议、行为与边界是什么。

```markdown
---
类型: SPEC
状态: 草稿
---

# <标题>

## 设计目标
这个机制要保证什么，明确不为哪些场景负责。

## 机制
数据怎么流、状态怎么变、谁是唯一事实来源。

## 接口与行为
输入、输出、错误、幂等性、并发或顺序要求。

## 边界条件
空值、超限、失败重试、路径越界、跨端差异。

## 验证方式
哪条测试 / 命令 / 观察能证明行为符合本规范。
```

常见错误：只写接口不写错误行为；把「应该不会出问题」当边界条件；规范与现有实现打架却不说明以谁为准。

## DESIGN · 设计方案

回答：视觉、交互、布局与体验长什么样。

```markdown
---
类型: DESIGN
状态: 草稿
---

# <标题>

## 设计目标
用户要完成什么，界面应该让哪件事变得顺手。

## 使用场景
谁在什么情况下打开它，带着什么预期。

## 交互流程
从进入到完成的主要路径，关键分支与空态、错误态。

## 视觉与体验要求
布局、密度、层级、动效、深浅主题、窄屏行为。

## 验收标准
- [ ] 在这个路径上能完成这件事
- [ ] 空态 / 错误态 / 窄屏都不塌
```

常见错误：只贴一张图不写流程；把组件选型当设计目标；忽略空态、加载态和失败态。

## RESEARCH · 调研方案

回答：事实是什么、现状如何、能得出什么结论。

```markdown
---
类型: RESEARCH
状态: 草稿
---

# <标题>

## 调研目标
这次要回答的具体问题，以及不打算回答什么。

## 调查范围
看哪些文件 / 代码 / 资料 / 环境，为什么是这些。

## 事实依据
带出处的事实：路径、行号、命令输出、链接、日期。

## 发现
按问题组织，区分事实与推断。

## 结论
能支撑什么决定；还缺什么信息。
```

常见错误：把观点当事实；只写结论不写出处；调研范围无限扩大。

## EXP · 实验方案

回答：假设是否成立、哪条路更优。

```markdown
---
类型: EXP
状态: 草稿
---

# <标题>

## 实验目标
要验证或比较什么。

## 假设
可被推翻的陈述（不是愿望）。

## 变量与指标
自变量、对照、衡量指标、样本量或重复次数。

## 实验方法
步骤、环境、数据来源、如何记录结果。

## 停止条件
什么情况下判定成立 / 不成立 / 无效，什么时候中止。
```

常见错误：没有对照；指标事后才定；结果不好时改判据。

## PLAN · 实施方案

回答：分几步做、依赖什么、怎样算交付。

```markdown
---
类型: PLAN
状态: 草稿
实施: 未实施
---

# <标题>

## 目标与现状
要达成什么；现在到哪一步，哪些前提已经核实。

## 实施步骤
1. <改什么，动哪些文件> — 验证：<命令 / 测试 / 观察，必须显示什么>
2. …

## 依赖
前置步骤、外部条件、需要用户决定的事。

## 验收要求
逐条可查的完成标准；未完成项写在这里，不藏进正文。
```

常见错误：步骤不可验证；把「写计划」当「做完」；遗漏依赖导致中途返工。`draft-plan` / `execute-plan` 里的六节形状（需求与边界、取舍、步骤、目标与完成判据、风险、未答问题）是这一类的一个完整实例，可以照用。

## AUDIT · 审查方案

回答：现有实现有什么问题、证据是什么、怎么改。

```markdown
---
类型: AUDIT
状态: 草稿
---

# <标题>

## 审查目标
审什么、按什么标准审、这次不审什么。

## 审查范围
文件、模块、提交范围、环境。

## 问题与证据
| 问题 | 证据（路径 / 行号 / 输出） | 影响 |
| --- | --- | --- |

## 影响
哪些用户路径、数据或后续工作会被影响。

## 改进建议
按优先级排列；写清哪条是必须改，哪条是建议。
```

常见错误：只列问题不给证据；把审美偏好当缺陷；不区分「必须改」与「可以改」。

## REPORT · 结果报告

回答：实际做成了什么、证据在哪、还欠什么。

```markdown
---
类型: REPORT
状态: 草稿
实施: 待验收
---

# <标题>

## 实际成果
做了什么，落在哪些文件 / 路径。

## 验证证据
每条完成标准对应一条证据：命令输出、测试结果、界面观察、实验数据。

## 结论
PASS / PARTIAL / FAIL / UNVERIFIED / BLOCKED，逐条对应目标。

## 差异
与方案的偏差：改了什么、为什么改、影响是什么。

## 遗留问题
没做完的、没验证的、需要用户决定的。
```

常见错误：用「已完成」代替证据；把代码存在当功能验收；不写偏差，导致下一轮照着旧方案返工。

## 扩展类型

| 类型 | 骨架要点 |
| --- | --- |
| ARCH | 上下文 → 目标与非目标 → 结构（模块 / 数据流）→ 风险与替代方案 → 迁移影响 |
| ADR | 背景 → 决定 → 备选与取舍 → 后果（接受什么代价）→ 状态 |
| RFC | 问题 → 提案 → 影响面 → 反对意见 → 待决问题与期限 |
| POC | 要证明的最小命题 → 最小实现范围 → 成功/失败判据 → 结论与下一步 |
| TEST | 测试范围 → 用例与优先级 → 环境与数据 → 通过标准 → 回归范围 |
| MIG | 迁移目标 → 现状与差异 → 步骤与回滚 → 数据校验 → 切换与观察 |
| SOP | 适用场景 → 前置条件 → 步骤 → 校验点 → 失败处理 |
| RCA | 现象 → 时间线 → 直接原因 → 根因 → 证据 → 修复与预防 |

## 状态怎么标

设计状态与实施状态是两条独立的轴：

- `状态`（设计）：草案 → 生效 → 已归档 / 已废弃。生效表示「现在以它为准」。
- `实施`（实施）：未实施 → 实施中 → 待验收 → 已验收。研究 / 审查 / 报告可以一直不写这一行。

状态只帮助读者判断当前情况，不是流程门禁；一份草案被用户认可后可以直接生效，不需要补中间状态。
