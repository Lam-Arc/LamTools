# 对话太长时的上下文整理

**上下文整理**（Compaction）是 Sunday 把较早的对话换成摘要、给后续请求腾出空间的过程。它整理的是后续请求使用的派生上下文，不会把原始会话记录替换成摘要。

| 信息框 | |
|---|---|
| 类型 | 上下文整理 |
| 触发方式 | 自动：context window 数值达到阈值；手动：`/compact` |
| 数值来源 | 真实 usage 优先，缺失时用本地估算（×2.5） |
| 命令 | `/compact` 或命令列表中的“压缩上下文” |
| 保留设置 | 压缩保留最近 Step 数，默认 0 |
| 对原文影响 | 原始记录继续保留，压缩只改变后续请求 |
| 单次任务内次数 | 达到阈值可再次整理，无一次性限制 |
| 对缓存影响 | 整段前缀失效一次 |

## 概述

模型一次能接收的内容有限。长对话迟早会接近这个上限，Sunday 会整理较早内容，把摘要和保留的近期对话一起交给后续请求。<sup>[1][2]</sup>

整理不是删除聊天记录。原始消息仍保存在会话中，用户仍可以回看；改变的是模型后续能直接看到的内容。

## 自动整理与手动命令

**自动整理**：每一步请求前，Sunday 计算一个 context window 数值。有真实 usage 时使用上一次成功响应的 prompt tokens；没有时使用本地估算，并乘 2.5 作为安全系数。数值达到阈值（可用窗口的 80%）时，系统调用摘要模型整理较早内容。

**手动整理**：在输入框的命令列表中选择“压缩上下文”，或执行 `/compact`。它不检查阈值，直接整理。

真实 usage 描述的是上一次请求，不是当前请求。阈值以下留出的 20% 用来吸收这一拍延迟；较大的本地估算不会覆盖已有的真实用量。接口没有返回有效用量时使用估算；换模型或完成整理后，旧用量失效。<sup>[3][5]</sup>

### 连续任务中的再次整理

一次用户任务可以经历多次整理。例如，Sunday 阅读文件后占用达到 80%，先整理一次；继续工作后再次达到 80%，仍会整理，不需要用户再发一条消息。主代理和子代理使用同样的规则。<sup>[3][5]</sup>

### 占用卡片

右侧卡片显示自动整理判断使用的同一个占用值，并区分“实测”和“估算”。卡片使用最新状态，不会用旧模型的历史用量覆盖当前数值；一条回复分成多个片段时，也取更新后的状态。<sup>[6][7]</sup>

整理期间界面会显示状态与结果。若当前会话历史存储不支持手动整理，命令会报错，而不是静默失败。

## 会保留什么

摘要主要保留：

- 目标与当前意图。
- 已做出的决定。
- 关键事实与约束。
- 待办事项。
- 错误与未解决的问题。

另外还会保留：

- 近期对话尾部，数量由“压缩保留最近 Step 数”控制。
- 最近的用户指令。

Step 指一次模型回复及其工具结果。保留数为 0 时，不完整保留近期步骤，只按摘要与最近指令处理。

摘要空间不足时，较早的近期轮次可能被移除，或摘要被缩短。

## 忘了细节怎么办

摘要是概括，不保证保留每个数字、原句、链接和附件细节。

需要细节时：

1. 重新提供关键约束。
2. 让 Sunday 查找并读取原始消息、文件或附件。
3. 需要跨会话保留的内容，明确保存到文件或记忆。

整理失败或被取消时，原上下文与原系统提示保留。整理后继续完成的工作仍逐步保存；重启恢复时读取摘要和未被覆盖的消息，而不是等任务全部结束后才保存。<sup>[5]</sup>

## 与缓存的关系

整理会把较早历史换成摘要，等于重写整段前缀，因此会造成一次明显的缓存失效。这是换取上下文空间所必需的代价。

Sunday 会把最新系统提示词和完整运行时状态的空间一起计入整理预算，检查通过后才保存新版本并重新冻结工具数组。之后重新建立稳定前缀。完整机制见[上下文与缓存命中](context-and-cache.md)。<sup>[3][5]</sup>

整理不会重置图片的全分辨率额度；已经降级的图片不会因为整理而恢复原图。

## 提示

- 长会话及时整理，避免每次请求都携带过大历史。
- 重要规则写进[上下文文件](context-files.md)，不要依赖摘要记住。
- 手动整理前，先把当前目标与关键约束补进对话。

## 已知问题

- 摘要可能丢失具体数字、原句与附件细节。
- 整理会造成一次缓存失效。
- 真实用量允许落后一次请求；突然加入的内容可能大于预留空间，预留比例不是容量保证。
- 最新用户指令和固定内容本身超过整理目标时，整理会报错，原始内容不会因此被截断。
