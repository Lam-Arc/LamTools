# 方案：从想法到开工

**方案**（Plan）是保存在项目“方案/”目录中的 Markdown 文档，用来记录已确认的需求、边界、步骤和完成标准。方案本身不会执行任务。

| 信息框 | |
|---|---|
| 类型 | 计划文档 |
| 存放位置 | 项目根目录的“方案/”文件夹 |
| 状态 | 草稿、就绪、执行中、完成 |
| 起草技能 | draft-plan |
| 修改技能 | refine-plan |
| 执行技能 | execute-plan |
| 开工条件 | 状态为“就绪” |

## 概述

方案解决“开工前先把话说清楚”。它先把用户已经决定的内容写下来，再暴露还没决定的问题，避免模型替用户补全假设。<sup>[1]</sup>

方案是普通 Markdown 文件，会跟随项目目录。没有选中项目时不能创建。

## 先起草：draft-plan

当用户说“先帮我把这个想法整理成方案”或“开工前先想清楚”，主代理可以调用 `draft-plan`。

技能会：

1. 用一句话复述用户想做什么。
2. 主动问最多两三个会改变方案的问题。
3. 把未答问题写进方案的“未答问题”一节，并在对话中询问。
4. 保存到项目根目录的 `方案/<标题>.md`。

早期只有标题、复述和待答问题是正常的。不会擅自补齐技术方案。

例如“我想自动整理笔记”，应先确认笔记位置、整理后想看到什么、哪些不能碰，而不是直接编出完整实现步骤。

## 再完善：refine-plan

已有方案需要补充或纠正时，使用 `refine-plan`。

技能会先读完整方案，再按本次反馈修改相关部分，保留其余已确认内容。

- 新边界写入对应章节。
- 问题得到回答后，把答案放进正文并移出未答列表。
- 修改重新打开了原本已确认的目标或边界时，状态退回“草稿”。

## 什么时候算就绪

只有同时满足以下条件，才把“草稿”改为“就绪”：

- 用户确认了目标和边界。
- 至少有一个可检查是否完成的步骤。
- 会改变方案的未答问题已处理，或被明确保留。

“就绪”表示双方认为可以开始，不代表代码已经修改，也不代表应用会自动启动执行。

资料库中的“开工”按钮只在状态为“就绪”时可用。按钮不可用时，打开方案查看状态，用 `refine-plan` 补齐缺项。

## 资料库里的方案操作

进入“资料库 → 方案”后，可以：

- 新建方案和文件夹。
- 搜索。
- 切换网格或列表视图。
- 按状态筛选。
- 阅读与编辑。
- 收藏、重命名、移动或删除。

编辑后点击“确认”保存并回到阅读状态。离开未保存的编辑时，页面会要求继续编辑或确认放弃。

## 开工：execute-plan

1. 在资料库打开一份“就绪”方案。
2. 点击“开工”，选择执行项目。
3. 应用为所选项目创建新的专属会话。
4. 提交执行指令。

`execute-plan` 会重新读取方案和它引用的文档，对照当前目录核对路径、接口和前置条件。发现计划与现实不一致时，先记录处理结论并修订方案，再把目标和步骤装入会话的目标与清单，逐步执行。

完成后依据完成判据核验结果，再把状态更新为“完成”。

如果方案属于另一个项目，读取工作目录之外的文件需要申请访问批准；更新仍写回方案原目录。

开工不会跳过权限确认，也不意味着每个步骤都已完成。

## 提示

- 先回答问题，再要求“就绪”，不要跳过未答问题。
- 一个方案只解决一件事，避免把多个目标塞进同一份文档。
- 只想要本次任务的步骤时，使用会话清单，不要把清单和方案混为一谈。

## 已知问题

- “就绪”只表示双方达成一致，不保证实施顺利。
- 跨项目执行方案可能需要额外访问批准。
