# 使用任务清单

**任务清单**（Checklist）是 Sunday 在对话中展示的结构化步骤列表，用来让用户看见当前进行到哪一步、每一步的验收标准是什么。

| 信息框 | |
|---|---|
| 类型 | 任务进度清单 |
| 入口 | 对话中要求列出步骤；模型通过清单工具写入 |
| 出现位置 | 对话中的清单区域 |
| 状态 | 待处理、进行中、已完成、受阻 |
| 是否自动执行 | 否，只记录进度 |
| 适用场景 | 多阶段、多文件、需要逐项核对的任务 |

## 概述

复杂任务容易在中途失去线索。清单把任务拆成若干步骤，并为每一步保留状态与说明。它解决的是“现在做到哪里、还差什么”，不负责实际执行，也不替代文件检查。<sup>[1][2]</sup>

## 清单的作用与边界

清单会做：

- 按顺序列出步骤。
- 显示每一步的状态。
- 记录阻塞原因或替换关系。
- 在对话中提供可核对的进度。

清单不会做：

- 自动执行步骤。
- 证明某一步真的成功。
- 代替测试结果、文件检查或用户确认。

## 创建与更新

可以直接在对话中提出：

> 先列出完成这份报告的步骤，每一步写明可检查的交付物。

Sunday 会按顺序列出步骤。之后：

- 完成某一步时，先检查对应结果，再标记完成。
- 计划变化时，更新步骤状态或说明阻塞原因。
- 某一步被拆分为多个子步骤时，原步骤会被替换，子步骤继承它的进度。

简单问题通常不需要清单。多阶段、涉及多个文件或需要逐项核对时更合适。<sup>[2]</sup>

## 写好一条清单

好的步骤应当：

- 互不重叠，避免“整理资料”和“汇总资料”同时出现。
- 有能被看到或检查的结果，例如“读取三份来源并保存一页事实摘要”。
- 写明预计改动的文件或交付物。
- 等待用户决定的步骤保持“待处理”，不要提前标成完成。

太笼统的步骤无法验收，例如“整理资料”；可验收的写法是“读取三份来源，生成一页事实摘要，列出来源链接”。

## 进度与失败

| 状态 | 含义 |
|---|---|
| 待处理 | 还没有开始 |
| 进行中 | 正在做，或正在等待结果 |
| 已完成 | 已检查过对应结果 |
| 受阻 | 缺少依赖、等待用户决定或执行失败 |
| 被替换 | 原步骤已拆成更细的子步骤 |

清单中的勾选只反映助手记录的状态。发现成果不存在、命令失败或依赖缺失时，应把步骤保持未完成并说明原因，而不是继续推进后续步骤。

任务范围改变时，更新剩余步骤，避免继续执行旧计划。

## 提示

- 让每一步都带一个可检查的结果，比只写动作更有用。
- 长任务中定期要求展示当前清单，比翻聊天记录更快。
- 清单停滞时，先处理“受阻”的那一步，不要并行推进后面的步骤。

## 已知问题

- 清单状态由助手维护，不与文件系统自动核对。
- 不同任务的清单展示位置可能随界面布局变化。
