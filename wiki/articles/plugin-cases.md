## 案例：能力承载形态（MCP、工具还是脚本）

同一个能力有三种承载方式：进程内工具（零安装，宿主环境装得下即可）、MCP 服务器（可指向插件自管的环境，能力成套迁移）、脚本加自管环境引导（依赖再重也不受限，如 538 MB 的 Whisper 配 uv 引导与"装转写依赖"按钮）。选择顺序是：**原版已经是 MCP 服务器，就照搬它的 MCP 配置**——能力成套迁移、平时休眠，不要重写成工具；原版不是 MCP 时，再按依赖住在哪选择，宿主环境装得下就用进程内工具，装不下就走 MCP 或脚本。把现成的 MCP 重写成工具属于偏离，要在差异表中交给用户裁决。bili-scroll 的读路径被改写成了进程内工具，而原版同一路径来自 MCP 服务器；按现在的规则，这一形态差异应先交给用户决定，而不是默认重写。

## 案例：外部依赖的三条出路

依赖无法进入宿主进程时，出路有三：技能引导（在配置里声明环境要求，教用户或 agent 装环境）；run_command 或专用工具执行插件目录里的脚本（脚本能否运行取决于用户机器，与宿主打包无关）；自造 MCP 包裹外部脚本。原版的"装转写依赖"按钮就是引导模式的实例。判定一条能力"无法移植"之前，先过一遍这三条路。

## 案例：授权分层（评论与私信类能力）

替用户发言的能力，授权分三层：**同意权在配置开关**（用户打开"自动评论并 @ 我"即常设授权，无需逐次确认——逐次确认会堵死无人值守轮）；**执行闸在处理器代码**（判重、限额、凭证校验，缺一拒绝）；**审批随运行上下文**（交互轮内容拿不准先给人过目，无人值守轮按开关与限额执行）。bili_post_comment 即此分层的实现：auto_allow + 开关硬闸 + 判重硬闸。

## 案例：双副本（源目录与安装目录）

安装即复制：运行时只认安装目录（代码、data、配置全在安装副本），源目录是作者的工作区，运行组件不会读它。配置变更走配置操作或插件页，不要在源目录旁写 data 文件——写了运行时永远看不到。
