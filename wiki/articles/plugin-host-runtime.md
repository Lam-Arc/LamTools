# 插件宿主运行时能力

**插件宿主运行时能力**是 Sunday 为插件后端提供的一组稳定契约，覆盖外部进程后端、模型目录、子会话操作、通用聊天通道和多问题交互。它们的共同目标是：插件只实现自己的业务和协议，会话、模型、压缩、审批、问答、流式这些宿主已经具备的能力不再由每个插件重复实现。<sup>[1][2]</sup>

| 信息框 | |
|---|---|
| 类型 | 宿主能力 |
| 作用域 | 插件后端、子代理、聊天通道 |
| 入口 | 插件清单 `runtime`、`context.service(...)`、子代理运行器 |
| 首次引入 | 2026 年 10 月 |
| 当前状态 | 启用 |

## 概述

插件系统早期只支持 Python 进程内的后端：插件在 `backend/__init__.py` 里实现 `create_plugin(context)`，宿主负责启动、健康检查和停止。移植 Node 插件时，这条边界迫使插件把协议、会话和运行逻辑全部改写成 Python；移植聊天机器人时，每个插件又要自己实现会话映射、审批续跑、问答、消息合并和流式输出。<sup>[1][3]</sup>

现在宿主把这些重复部分收敛为运行时能力。插件仍然拥有自己的网络协议、消息格式和业务规则，但会话、模型、压缩、历史、审批和问答由宿主提供统一入口。插件后端通过 `context.service(...)` 取得这些服务，不需要导入宿主内部模块。<sup>[2][4]</sup>

| 能力 | 插件原来要自己做的事 | 现在由宿主提供 |
|---|---|---|
| 外部进程后端 | 把 Node 代码改写成 Python，或让用户手工启动进程 | `runtime.kind=process`，宿主托管启停与 JSON-RPC |
| 模型目录 | 导入内部 `ModelStore`，自己处理默认模型和失败回退 | `model_catalog` 服务 |
| 子会话操作 | 只能运行，不能手动压缩、分叉或读历史 | `compact` / `fork` / `session_info` |
| 聊天通道 | 自己写会话、合并、命令、审批、问答、流式 | `channel_host` + `ChannelAdapter` |
| 实时会话投递 | 自己判断空闲/运行/暂停，拼活动执行标识 | `live_turn_service.deliver_message` |
| 多问题 | 一次只能问一题，多题要拆成多轮 | `question` 工具的 `questions` 数组 |
| 交付物 | 自己扫描工具结果里的 artifacts | `deliverables/presented` 事件 |
| 插件凭据 | 明文写在自己的配置里，自己决定怎么保护 | `secrets` 按插件隔离的密钥视图 |
| HTTP 回调 | 自己起服务、自己鉴权 | `http.routes` 声明，宿主统一挂载和 token 校验 |
| 改代码后重载 | 重启整个应用 | `plugin.system.reload` 显式重载 |

## 外部进程后端

插件可以在清单里声明一个外部进程作为后端，而不是 Python 模块：

```jsonc
"runtime": {
  "kind": "process",
  "command": ["node", "dist/server.js"],
  "cwd": ".",
  "env": { "NODE_ENV": "production" },
  "startupTimeoutMs": 15000,
  "requestTimeoutMs": 60000
}
```

宿主用与 Python 后端相同的生命周期启动这个进程：启动、就绪、健康检查、停用、重启都由宿主负责。进程通过标准输入输出交换按行分隔的 JSON-RPC 2.0 消息，支持 `initialize`、`tools/call`、`operations/call`、`health` 和 `shutdown`。工具和操作仍然在 `tools.jsonc` / `operations.jsonc` 中声明；进程后端的声明可以省略 `handler`，因为处理函数就在子进程里。<sup>[5]</sup>

`cwd` 默认是插件根目录，适合子进程需要自己的相对路径的场景；`env` 会叠加在宿主环境之上。子进程的标准输出必须是 JSON，日志写标准错误，宿主会按插件名记录。进程退出会让后端变为不可用，下一次启用或重启会创建新的进程。<sup>[5]</sup>

## 模型目录

`model_catalog` 是只读的模型目录服务，提供 `list()`、`resolve(ref)`、`default()`、`capability(ref)` 和 `providers()`。每个模型包含标识、显示名、供应商、能力、上下文窗口和最大输出等字段。它包装现有的模型存储，因此项目、全局和内置模型的优先级仍由宿主统一决定。<sup>[6]</sup>

插件不再需要知道模型配置文件的布局，也不需要自己判断某个模型是否支持图片。需要视觉能力时读取 `capability(ref)`；需要默认模型时读取 `default()`；切换模型时把解析出的供应商和模型标识交给子代理运行器。<sup>[6]</sup>

## 子会话操作

子代理运行器除了运行一轮对话，还提供三个手动操作：

| 操作 | 作用 |
|---|---|
| `compact(session_id)` | 按正常压缩管线手动压缩一个子会话的历史 |
| `fork(session_id, new_agent_name)` | 复制会话状态和历史到一个新的子会话 |
| `session_info(session_id)` | 读取状态、轮次、历史条数、用量和最近消息 |

分叉会生成新的会话标识和代理名称，清除挂起的审批/问题，并保留历史副本。压缩和分叉都需要宿主的状态存储支持检查点；内存状态存储也能工作，但重启后不会保留。<sup>[7]</sup>

运行器还提供 `preset_service("compaction", preset_id)`。宿主内置一个压缩服务，插件也可以在启动时按预设注册自己的服务，从而替换某个预设下的压缩实现，而不替换整个运行器。<sup>[7][8]</sup>

## 通用聊天通道

`channel_host` 把聊天机器人共有的部分收敛成一个运行时。插件实现 `ChannelAdapter`，负责网络发送和交互展示；`ChannelRuntime` 负责其余部分：<sup>[4]</sup>

- 一个私聊或群聊映射到一个稳定的子代理会话；
- 按 peer 串行处理消息，忙时把后续消息合并成一批；
- 解析斜杠命令，命令不进入模型；
- 把宿主的审批和问题请求交给适配器，收到回答后恢复同一会话；
- 把流式文本、工具结果、用量、轮次结束和交付物转发给适配器；
- 提供状态、用量、历史、导出、重置、停止、压缩和分叉操作。

适配器接口包括发送文本、发送文件、打开流、询问审批、询问问题、处理按钮交互、处理文本、取消挂起和确认交互。插件仍然掌握 QQ、Telegram 或其他平台的消息格式；运行时只处理会话和事件流。<sup>[4]</sup>

## 实时会话投递

聊天通道面对的是插件自己映射的子会话；实时会话则是用户正在 Sunday 里查看的那个会话。两者不能共用同一套投递判断。插件把消息送进实时会话时，如果先读取内存里的运行登记表，或在运行中先尝试开始新回合，消息就可能排到会话串行队列后面，等当前回合结束才返回；结果不是运行中引导，而是下一条用户消息。<sup>[16]</sup>

宿主为这条路径提供单一投递入口。插件只提交会话、文本和消息标识，由宿主决定当前状态：<sup>[16]</sup>

| 会话状态 | 宿主行为 | 插件看到的结果 |
|---|---|---|
| 空闲 | 开始一个正常用户回合 | `started` |
| 运行中 | 走与桌面相同的回合引导路径，写入引导事件和用户可见的引导条目 | `steered` |
| 暂停 | 继续被暂停的回合 | 续跑结果 |
| 回合刚好结束 | 把文本落成下一条用户消息，不丢弃 | `queued` |

插件不需要读取运行登记表、会话快照或活动执行标识，也不需要在运行中先开始新回合再回退到引导。实时会话的归属、排队和持久化由宿主负责；插件只根据返回结果等待目标回合的事件并转发回复。<sup>[16][17]</sup>

## 多问题交互

内置 `question` 工具现在接受 `questions` 数组，一次可以提出多个问题，每个问题有自己的标题、选项和是否多选。内核在挂起记录里保留完整数组，聊天通道逐题展示，最后把合并后的回答作为一次续跑输入交回模型。<sup>[9]</sup>

这减少了「问一题、等一次、再问下一题」的往返，也让插件不需要自己维护多题状态机。只有一个问题时，行为与原来的单问题调用一致。<sup>[9]</sup>

## 交付物事件

工具返回 `artifacts` 时，内核和子代理运行器会额外发出 `deliverables/presented` 事件，负载里是规范化的文件列表、工具名和调用 id。这样通道插件和界面不必只靠扫描 `runtime.tool.finished` 来发现文件。<sup>[15]</sup>

子代理的事件转发器现在把 `deliverables/presented` 视为可见事件，转发时会带上 `sub_agent` 身份，因此聊天通道能定位到正确的会话。通用聊天通道会同时收到工具事件和交付物事件，并按文件路径去重，避免同一个文件发送两次。<sup>[4][15]</sup>

这个事件镜像的是工具产物，不额外判断“用户是否想保存”；需要区分交付物和中间文件时，由工具在 artifact 的 metadata 里表达，消费者按自己的策略筛选。

## 插件密钥存储

`secrets` 是宿主提供的按插件隔离的密钥视图。插件通过 `context.service("secrets")` 取得自己的视图，用 `get`、`set`、`delete`、`keys` 管理凭据。每个插件只能看到自己的命名空间；共享的底层存储不会作为服务暴露，插件无法借它读取别的插件。<sup>[10][11]</sup>

在 Windows 上，每个值用当前用户登录凭据保护的 DPAPI 加密后写入宿主的密钥文件；在支持 POSIX 权限的平台还会把文件权限限制为当前用户。其他平台退化为 base64 加文件权限，这只是混淆而不是加密，宿主会记录该限制。密钥值损坏或无法解密时读取会报错，而不是返回错误的文本。<sup>[10]</sup>

QQ 机器人插件已经使用这个能力：AppID 留在普通配置里，AppSecret 写入 `secrets`；旧版本写在 `config.jsonc` 里的明文会在启动时迁移到密钥库并从配置中清除。这样升级不会让已绑定的机器人掉线，也不会继续保留明文。<sup>[3][12]</sup>

## 插件 HTTP 路由

插件可以在清单里声明自己的 HTTP 路由，用来接收 Webhook、OAuth 回调或本地集成请求：

```jsonc
"http": {
  "routes": [
    {"method": "POST", "path": "/webhook", "operation": "demo.webhook"},
    {"method": "GET", "path": "/health", "operation": "demo.health", "auth": "none"}
  ]
}
```

路由统一挂在 `/api/core/plugin-http/<插件名>/<路径>`，请求以 `{method, path, query, body, headers}` 交给插件自己的操作。默认要求 token：宿主在插件密钥库里生成 `httpToken`，调用方用 `X-Plugin-Token` 或 `Authorization: Bearer …` 携带；插件可以读取这个值并在设置页展示。`auth: "none"` 只适合纯本地的集成。<sup>[13]</sup>

为了不让 HTTP 绕过审批，路由只能指向本插件拥有且 `permission: "auto_allow"` 的操作；`ask_user` 和 `hard_block` 会被拒绝。路径必须精确匹配，不能包含 `..`、`?` 或 `#`，每个插件最多 32 条路由。<sup>[13]</sup>

## 插件代码重载与预设目录

`plugin.system.reload`（别名 `plugin.reload`）会停止插件后端、清除已导入模块、重新加载当前文件、启动后端并重新挂载该插件的操作。它解决的是“改完插件代码不想重启整个应用”，不是自动文件监视；替换整个插件目录仍用 `plugin.system.update`。<sup>[14]</sup>

`plugin.system.presets.list` 返回宿主预设注册表中的全部预设和默认项，供设置界面或工具读取。它只读；编辑预设仍通过插件清单或 `agent-presets.jsonc` 配置。<sup>[8]</sup>

## 这些能力如何配合

QQ 机器人插件是一个完整例子：它声明三个智能体预设，后端启动时注册提示词流水线；聊天命令把模型和预设写入该 peer 的偏好；下一轮子代理运行器读取预设、模型目录和会话状态，审批或问题通过按钮通道恢复；压缩、分叉和历史命令调用运行器的子会话操作。<sup>[3][8]</sup>

QQ 插件的目标会话是另一条路径：每个 Sunday 会话可以拥有独立的 QQ 机器人，消息交给实时会话投递入口，由宿主判断空闲、运行中或暂停；运行中通过桌面同款引导路径写入，插件不再直接操作运行登记表。QQ 插件仍保留自己的桥接层，因为它在通用通道运行时之前就已经实现了 QQ 特有的流式、按钮和偏好逻辑；通用通道运行时已经通过独立测试验证，后续可以把桥接层迁移到它上面。<sup>[3][4][16]</sup>

## 已知边界

1. 外部进程后端目前只有请求/响应，没有宿主回调；需要长时间推送的插件应通过自己的操作或工具报告进度。
2. 进程后端不会自动安装依赖；`command` 指向的可执行文件和模块必须已经在用户机器上。
3. 子会话压缩和分叉依赖状态存储的检查点能力；普通内存存储不保证重启后保留。
4. 通用聊天通道要求插件实现完整的适配器接口；只做单向通知的插件不必使用它。
5. 多问题回答最终合并成一段文本；需要结构化答案的插件应自己解析或继续使用单问题调用。
6. 模型目录是只读的；修改模型配置仍走宿主的模型设置和配置操作。
7. 非 Windows 平台的密钥存储只有 base64 加文件权限，不提供强加密；需要强保护的插件应把凭据放在 Windows 桌面端。
8. 插件 HTTP 路由属于桌面本机 API；不要把后端端口直接暴露到公网，`auth: "none"` 只适合本机集成。
9. 插件代码重载是显式操作，没有文件监视；保存文件后需要调用 `plugin.system.reload` 或重启应用。
10. 插件运行时读取的是安装副本，不是工作区源目录；只改工作区不会影响正在运行的插件。代码变更需同步安装副本并显式重载，宿主服务本身的变更则需要重启后端或应用。

## 历史

- **2026 年 10 月 28 日**：新增实时会话投递契约。
  - 插件不再自行判断实时会话的空闲、运行或暂停，也不直接读写运行登记表。
  - 运行中消息走桌面同款引导路径，暂停消息继续原回合，回合结束边界上的消息落成下一条用户消息。
  - 对应宿主测试和 QQ 真实 live 会话测试补入。
- **2026 年 10 月**：为 QQ 机器人移植补齐宿主运行时能力。
  - 新增外部进程后端与 JSON-RPC 标准输入输出协议，工具、操作、健康和生命周期由宿主托管。
  - 新增只读模型目录服务。
  - 子代理运行器新增手动压缩、分叉和会话信息。
  - 新增通用聊天通道运行时和适配器接口。
  - `question` 工具支持一次提出多个问题。
  - 新增按插件隔离的密钥存储，QQ 的 AppSecret 已迁移。
  - 新增插件 HTTP 路由、显式代码重载和预设目录查询操作。
  - 工具产物现在会发 `deliverables/presented` 事件，子代理转发并由通道去重投递。
  - 新增对应验收测试。
