# 把需求说清楚

**需求表达**（Task phrasing）是让 Sunday 更容易交付可核对结果的方法。它不需要特殊口令，重点是把目标、材料、边界和完成标准说清楚。

| 信息框 | |
|---|---|
| 类型 | 使用建议 |
| 作用 | 提高结果的可核对性 |
| 四个要素 | 目标、材料、允许的动作、完成标准 |
| 是否强制 | 否，属于建议格式 |
| 适用入口 | 任一会话的输入框 |

## 概述

模型不会自动知道用户心里的完成标准。任务描述越明确，越容易得到可检查的结果，也越容易在出错时判断是哪一步偏离了预期。

## 一个好任务包含什么

告诉 Sunday 四件事：

| 要素 | 要回答的问题 |
|---|---|
| 目标 | 想得到什么结果 |
| 材料 | 资料在哪里 |
| 边界 | 允许做到哪一步，哪些不能动 |
| 完成标准 | 怎样判断已经完成 |

示例：

> 阅读项目目录里的三份采访记录，按主题整理成一份约 1000 字的纪要，标出存在分歧的说法，保存成新的 Markdown 文件，不覆盖原记录。完成后告诉我文件在哪里。

这比“整理一下”更容易检查结果。

## 先讨论还是直接执行

| 目的 | 说法 |
|---|---|
| 先想清楚 | “先列方案和取舍，暂时不改文件。” |
| 已经决定要做 | “按这个方案完成，并检查结果。” |
| 只检查不修改 | “只读检查，不要写入。” |

文字要求不能代替权限设置。说“别修改”不等于工具一定被禁止；实际行为还受[工具模式](tool-modes.md)和[审批](approvals.md)约束。

## 长期规则放在哪里

| 内容 | 放置位置 |
|---|---|
| 长期写作习惯、项目约定 | [上下文文件](context-files.md)，例如 `AGENTS.md` |
| 具体事实与偏好 | [记忆](memory.md) |
| 只适用于本次任务的要求 | 当次对话 |

不要每次都粘贴整段无关历史，这会占用上下文并增加费用。

## 中途补充信息

任务运行时仍可能想到新要求。先确认新消息是进入了待发送队列，还是作为引导送入当前回合，见[消息引导与排队](queued-messages.md)。

如果补充改变了目标，要说明哪些部分仍然保留，避免 Sunday 把新旧要求混在一起。

需要回答的提问卡与选项行为见[提问](questions.md)。

## 怎样检查交付

模型说“完成”后，打开实际文件抽查内容与关键数据。

| 工作类型 | 检查点 |
|---|---|
| 文件整理 | 文件是否存在、内容是否完整、原文件是否保留 |
| 网页结论 | 是否给出可访问的来源 |
| 代码修改 | 是否说明检查或测试结果 |
| 定时任务 | 运行历史与输出是否符合预期 |

Sunday 能帮助检查，但模型回答仍可能出错，工具成功也不等于工作质量合格。

## 提示

- 一次只要求一个明确结果，比同时提多个目标更容易验收。
- 写明“不要覆盖”“只读检查”这类边界。
- 要求 Sunday 报告它实际读了哪些文件、用了哪些工具。

## 已知问题

- 任务描述清晰不能弥补材料缺失或权限不足。
- 不同模型对长指令的遵循程度不同。
