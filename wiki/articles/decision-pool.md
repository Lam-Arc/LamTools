# 决策池

**决策池**（Decision pool）是 Sunday 保存待用户处理的审批与提问的持久索引。它按进入顺序排列每张卡，决定卡片何时出现、由哪个会话负责、何时从界面移除。

| 信息框 | |
|---|---|
| 类型 | 待办索引 |
| 作用域 | 会话，可包含子代理会话 |
| 记录位置 | 本机持久记录 |
| 入口 | 聊天待处理面板、输入框接管区 |
| 顺序 | 进入顺序，先到先处理 |
| 结束 | 决定写入后立即移除 |

## 概述

决策池不是聊天记录的一部分，而是聊天记录之外的待办索引。<sup>[1][2]</sup>

消息树可能因分页、压缩或恢复而缺少某张卡片所属的回合，决策池仍然保留该交互及其回答入口。界面每次读取时从持久记录取回未结束的卡，而不是从消息树重新推断。

池中的每一张卡都回答四个问题：

1. 这是审批还是提问。
2. 由谁投递。
3. 属于哪个项目和会话。
4. 按什么顺序等待。

## 池里记录什么

| 信息 | 作用 |
|---|---|
| 类型 | 审批或提问 |
| 状态 | 待回答、处理中、暂缓、已回答、已取消、已过期 |
| 归属 | 主会话或某个子代理会话 |
| 顺序 | 进入池的先后 |
| 项目 | 发起交互的项目 |
| 投递者 | 主会话或某个子代理 |
| 稳定标识 | 跨窗口去重，重放同一事件不会产生第二张卡 |

稳定标识不随卡片状态变化。因此同一条事件被重复投递时，池子不会多出一张卡。

## 生命周期

卡片状态按固定方向推进，终态不可逆：

| 阶段 | 界面表现 | 触发条件 |
|---|---|---|
| 出现 | 待处理，可作答 | 交互进入池子 |
| 处理中 | 显示“处理中”，不可重复作答 | 回答已被接受 |
| 结束 | 卡片从池中移除 | 回答保存、被取消或过期 |

结束的判定点是决定写入，而不是下一轮模型请求发出。回答写入后，卡片立即结束并移除；模型的后续输出不会让这张卡重新出现。<sup>[3][4]</sup>

“处理中”只表示回答已被接受，决定仍在写入或续跑。它保留原来的进入顺序，因此卡片不会因为状态更新而跳到队尾。

## 顺序

1. 新交互进入时，取得当前会话的下一个顺序号。
2. 读取时按顺序升序返回。
3. 界面按该顺序展示待处理项。
4. 状态更新只改状态，不改顺序。
5. 一张卡结束后，下一张按原有顺序补上位置。

顺序在单个写入事务内分配，避免两张卡拿到同一个位置。<sup>[2]</sup>

## 持久化

- 交互创建时写入持久记录。
- 回答、取消和过期都更新同一条记录。
- 续跑任务单独保存，用于在连接断开或应用重启后继续执行已经接受的决定。
- 读取快照时，未结束的卡以持久记录为准。

因此，池子的事实来源是持久记录，不是快照中的事件汇总，也不是消息树。

## 投递

池子的“出现”只有一个来源：运行时的审批请求事件。

运行进入等待状态只是回合状态变化，不会重复生成卡片。<sup>[3]</sup>

| 事件 | 对池子的作用 | 界面 |
|---|---|---|
| 审批请求 | 新增一张待回答的卡 | 卡片出现 |
| 交互出现 | 新增或确认同一张卡 | 卡片出现或保持 |
| 交互进入处理中 | 把同一张卡改为处理中 | 显示“处理中” |
| 审批结束 | 移除该卡并标记请求已解决 | 卡片消失 |
| 运行进入等待 | 不改变池子 | 仅对无卡片的等待显示状态行 |

卡片事件走可靠控制通道，与普通流式增量分开传输，避免断线时丢失审批边界。<sup>[5]</sup>

## 归属

主会话与子代理共用同一个池子视图，但每一张卡保留自己的归属。

- 子代理发起的交互标记为属于该子代理会话。
- 回答按交互归属路由回对应运行，而不是默认交给父会话。
- 同类交互在父会话时间线上可见，不代表答案属于父会话。
- 续跑任务登记在归属会话上，使两个子代理不会互相阻塞。<sup>[4]</sup>

## 事件与界面变化

| 变化 | 池子 | 界面 | 回合 |
|---|---|---|---|
| 卡片出现 | 新增一张 | 待处理面板或聊天内卡片出现 | 进入等待 |
| 回答被接受 | 改为处理中 | 显示“处理中” | 续跑开始 |
| 决定写入 | 改为终态并移除 | 卡片立即消失 | 续跑继续 |
| 重复点击 | 无变化 | 保持已处理状态 | 无额外任务 |
| 迟到重复事件 | 终态卡不被改写 | 不会重新出现 | 不复活已结束回合 |

## 提示

- 卡片消失表示决定已经保存，不表示模型已经完成后续工作。
- 多张卡按进入顺序排列；逐张处理比同时点击更容易判断每条决定对应哪个操作。
- 会话恢复后，未结束的卡从持久记录重新加载；不要用聊天记录里是否还能看到卡片来判断它是否仍然有效。

## 已知问题

1. 同一会话可以同时保留多张卡，但续跑以会话为串行单位；回答一张后由该会话推进，不保证多个等待步骤并行续跑。
2. 旧快照完全没有池子信息时，界面会退回消息树查找卡片；这类兼容路径无法识别只存在于持久记录中的历史回答。
3. 工作目录边界不再作为审批阻断条件；池中的审批卡不是文件系统沙箱。

## 历史

- **2026 年 10 月**：交互成为独立记录，进入顺序、稳定标识、项目与子代理归属写入持久记录；回答通过持久任务续跑。
- **2026 年 10 月 22 日**：卡片出现收口为单一来源；终态不可逆；重复事件不再擦除选项；回答写入后立即出池。
