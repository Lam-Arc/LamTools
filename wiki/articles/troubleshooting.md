# 故障排查：先看问题发生在哪一层

**故障排查**（Troubleshooting）是先判断问题发生在哪一层、再针对性处理的顺序。同样是“没有反应”，原因可能完全不同。

| 信息框 | |
|---|---|
| 类型 | 排查指南 |
| 排查层次 | 程序连接、模型请求、工具执行、等待确认、最终交付 |
| 入口 | 当前会话的错误与运行记录；设置中的对应分区 |
| 首要原则 | 先定位层次，再改设置 |
| 是否建议重装 | 否，重装通常不是第一步 |

## 概述

排查的核心不是“多试几个开关”，而是确定问题层级：

1. 桌面程序与本机后台是否连通。
2. 模型请求是否成功。
3. 工具是否被允许执行。
4. 任务是否在等待用户确认。
5. 结果是否真的写入了文件。

## 程序能打开，但无法工作

| 现象 | 先检查 | 下一步 |
|---|---|---|
| 主窗口显示后台停止或连接断开 | 本机后台是否准备好 | 完整退出再启动，保留错误提示 |
| 新会话模型列表为空 | 是否已经添加供应商与模型 | 参考[模型与供应商](models.md) |
| 普通文字问答也报错 | 服务地址、密钥、模型名称、额度 | 看服务商返回的具体原因 |
| 只有部分联网功能失败 | 代理、证书、该服务是否可用 | 参考[网络与连接](network.md) |

常见状态码的大致含义：

| 状态 | 通常表示 |
|---|---|
| 401、403 | 认证或权限问题 |
| 429 | 限流或额度问题 |
| 5xx | 服务端问题 |

具体原因仍以服务商返回的信息为准，不要只凭数字改一大批设置。

## 能聊天，但某项能力不可用

| 能力 | 先检查 |
|---|---|
| 读取文件 | 当前项目、文件是否存在、路径是否可访问 |
| 修改文件 | 工具模式、写入工具是否开放、是否有待处理审批 |
| 查看图片 | 模型能力、附件状态、多模态子代理配置 |
| 搜索或生成图片 | 对应插件、服务配置与网络 |
| 操作浏览器 | 是否配置了提供浏览器工具的 MCP 服务 |
| RAG 检索 | 是否安装并启用了检索提供方 |

聊天模型可用，不代表另一项服务也可用。不要通过放宽所有权限来修复普通网络错误，权限与连接是两类问题。

## 任务停住或结果不对

按以下顺序检查：

1. [审批](approvals.md)或[提问卡](questions.md)。
2. [运行状态](runtime-status.md)。
3. [子代理](sub-agents.md)。
4. [后台进程](processes.md)。
5. [待发送队列](queued-messages.md)。

如果补充要求还在队列中，当前任务可能尚未收到。

模型说完成但找不到文件时，检查：

- 是否确实调用过写入工具。
- 保存路径是否正确。
- 成果库是否登记。

如果输出遗漏旧要求，可能与[上下文整理](compaction.md)有关。把关键限制重新明确，并要求核对原始资料。

## 重试前先检查什么

上一次可能已经部分执行：

- 创建的文件。
- 修改的内容。
- 发出的外部请求。

这些不会因为界面报错就自动撤销。先明确失败环节，再重试，避免重复操作。重要数据先[备份](data-backup.md)。

## 求助时提供的信息

提供：

- Sunday 版本。
- 问题发生的入口。
- 原本想做什么。
- 最后一次成功动作。
- 第一条错误。

必要时附脱敏后的相关日志。

不要发送 API Key、完整配置、私密附件或整个数据库。一句“卡住了”通常不足以定位原因。

## 提示

- 先确认是哪一层失败，再改对应设置。
- 保留第一条错误，而不是只记录最后一条。
- 修改设置后，用一轮最小任务验证。

## 已知问题

- 部分错误信息来自外部服务，Sunday 只能原样转述。
- 不同版本的状态码含义可能略有差异。
