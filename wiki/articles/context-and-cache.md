# 上下文与缓存命中

**上下文与缓存命中**（Context and cache hit）是 Sunday 在构造模型请求时使用的一组机制。其目标是在不改变模型可见信息的前提下，使请求的系统提示词前缀在单个会话内保持稳定，从而提高模型供应商提示词缓存（prompt cache）的复用率。缓存是否命中由供应商根据请求前缀计算，Sunday 只能影响请求内容，不能保证命中。<sup>[1][3]</sup>

Sunday 将系统提示词按块冻结在一个“压缩周期”内；内容变化以尾部通知追加；运行时状态只追加变化字段；图片在首次请求后降为低分辨率副本；上下文压缩是唯一重建系统提示词的时机。<sup>[1][2]</sup>

| 信息框 | |
|---|---|
| 类型 | 请求构造机制 |
| 作用域 | 单个会话的每次模型请求 |
| 相关功能 | 系统提示词、上下文文件、记忆、技能、MCP、上下文压缩、附件、子代理 |
| 首次引入 | 2026 年 10 月 |
| 当前状态 | 已实现；原生 Anthropic 缓存仍缺显式断点 |

## 概述

提示词缓存是一种前缀缓存：供应商从请求的第一个 token 开始逐段比对，只有连续相同的前缀才能复用。前缀中任意位置出现差异，该位置及其之后的内容都需要重新计算。<sup>[8]</sup> 因此，请求中越靠前的内容变化，代价越大；只在末尾追加内容，代价最小。

Sunday 的请求由模型参数、工具定义、系统提示词、会话历史、运行时状态、本轮唤醒和图片组成。系统提示词位于请求最前部，是缓存收益最高、也最容易被改写的一部分。Sunday 将这部分拆分为可独立比较的块，并在一个压缩周期内发送第一次渲染出的完整文本，而不是每一步重新拼接。<sup>[1][3]</sup>

缓存命中仍然产生费用，只是单价通常低于未命中；具体比例、缓存存活时间（TTL）和计费方式由供应商决定。Sunday 中显示的命中率是观测值，不能替代供应商账单。<sup>[10]</sup>

## 请求组成

一次模型请求按以下顺序携带内容：

| 层 | 内容 | 是否参与前缀 | 典型变化频率 |
|---|---|---|---|
| 模型与参数 | 模型 id、温度、输出上限、思考/推理等级、工具选择 | 是 | 低 |
| 工具定义 | 工具名称、描述、参数结构 | 是 | 压缩周期内冻结 |
| 系统提示词 | 长期规则、身份、协议、技能索引、项目上下文等 | 是 | 压缩周期内冻结 |
| 会话历史 | 用户消息、助手回复、工具调用与结果、压缩摘要 | 是 | 只追加 |
| 运行时状态 | 计划、后台进程、验证要求、能力说明、模式 | 尾部 | 高 |
| 本轮唤醒 | 子代理完成等控制输入 | 尾部 | 每轮 |
| 图片 | 原图或低分辨率副本 | 历史中的消息 | 首次之后降级一次 |

不同协议对 system 消息的摆放方式不同。Anthropic 将普通 system 消息提升到顶层 `system` 字段；Gemini 放入 `systemInstruction`；OpenAI Chat Completions 与 Responses 保持消息顺序或转换为 developer 消息。Sunday 的协议层会处理这些差异，但缓存仍按供应商自身的规则计算。<sup>[3]</sup>

## 缓存机制

### 前缀匹配

供应商的提示词缓存以请求前缀为单位。若本次请求与上一次成功请求在某个位置之前完全一致，该前缀可以复用；从第一个差异位置开始，后续内容重新计算。<sup>[8]</sup>

由此可得三条基本规则：

- 修改系统提示词的影响最大，因为其位于请求最前部。
- 修改会话历史中间的消息，影响范围从该消息开始。
- 仅在末尾追加新消息，已缓存的前缀仍可复用。

缓存存在存活时间。即使请求内容完全一致，超过 TTL 后也不会命中；这与 Sunday 是否修改内容无关。

### 压缩周期与冻结

“压缩周期”是 Sunday 为系统提示词定义的冻结区间：从会话第一次构造请求开始，到下一次上下文压缩成功为止。<sup>[1][4]</sup>

- 压缩周期开始时，Sunday 渲染整段系统提示词并保存为冻结文本。
- 之后每一步发送这份冻结文本，而不是重新拼接。
- 任一提示词块变化时，不修改前面的系统提示词，而是在请求末尾追加通知。
- 冻结文本随会话状态持久化；重启后继续使用同一份。

系统提示词被拆分为以下可比较的块：<sup>[3]</sup>

| 块 | 内容 |
|---|---|
| 成员指令 | 用户或成员配置的长期规则；Study 模式下为内置 Study 指令 |
| 会话身份 | 项目路径、会话标识、当前模型 |
| 子代理指南 | 子代理的角色、委派策略与角色分配 |
| 命令行环境 | 当前使用的命令 shell |
| 工具协议 | 通用工具调用协议 |
| 完成规则 | 最终答复的格式与完整性要求 |
| 技能索引 | 当前可用技能清单 |
| MCP 服务器 | 可激活的外部工具服务器名单 |
| 项目上下文文件 | `AGENTS.md`、`CLAUDE.md`、`CONTEXT.md`、全局与项目记忆索引等 |
| 图片保真说明 | 图片在请求中的清晰度说明 |

Sunday 为每个块保留“上一次已告知模型的版本”，并逐块比较内容。压缩周期的首次请求只记录基线，不产生通知。<sup>[4]</sup>

### 变化通知

块内容变化时，Sunday 在请求末尾追加一条系统消息。通知只包含两种状态：<sup>[4]</sup>

- `changed`：给出变化后的完整内容。
- `deleted`：说明该块已删除，顶部旧副本不再适用。

内容改回旧值同样记为 `changed`，不设单独的“回退”状态。示例：

```text
[System context update]
System message "AGENTS.md" are changed, now:
（变化后的完整内容）
```

```text
System message "skills index" are deleted; the copy in the leading system prompt no longer applies.
```

通知在发出的那一步位于请求末尾；同时会写入会话记录并固定在那里，下一步起成为可复用前缀的一部分，不需要重复发送。<sup>[6]</sup>

### 运行时状态

计划、后台进程 PID、验证要求、能力说明、模式和空回复重试指令属于运行时状态，不属于系统提示词。<sup>[1][5]</sup>

- 会话第一次请求或压缩后：发送一张完整快照。
- 之后每一步只比较字段，只追加变化项。
- 没有变化时不发送消息，也不重复整张快照。

示例：

```text
[Runtime context update]
- Plan step step-2: completed · 写报告
- Process 1234: exited
```

用于比较的基线随会话保存。压缩时这些增量从压缩输入中排除，压缩成功后补发一张完整快照作为新基线。<sup>[5][6]</sup>

### 图片降级

图片会随历史在每次请求中重新发送。Sunday 的策略是：<sup>[7][13]</sup>

- 图片产生后的第一次请求发送原图。
- 第二次请求起改为 360p、256 色索引色 PNG：横图最多 640×360，竖图最多 360×640。
- 降级副本按内容缓存，使用固定参数重编码；同一输入每次生成完全相同的字节。
- 图像处理失败时原样返回，不丢图，也不阻断请求。
- 已在本框内且小于 64 KB 的 JPEG 保持原样，避免无意义地改变字节。

降级会改写图片所在位置之后的前缀，因此缓存损失从图片位置开始。图片通常产生于一轮末尾，损失约等于最后一轮的内容。<sup>[7]</sup>

计数口径统一为“模型已经回答过几次”：用户消息、工具消息、审批恢复写入的工具结果都记录该计数；下一次请求使用同一计数时仍为原图，再下一次计数加一后才降级。<sup>[6][7]</sup>

压缩不会重置图片的全分辨率额度。压缩只重建系统提示词与摘要，不会把已经降级的图片重新升为原图；会话记录中保留的是原图，请求时每次按计数生成副本。若图片在压缩前已经过了全分辨率窗口，压缩后仍是低清；若尚未过窗口，压缩保留的那一次请求仍可能是原图，之后按计数降级。压缩摘要看到的是当时请求携带的版本：新图片为原图，过期图片为低清。需要重新查看细节时，让模型重新读取原文件或重新附加；这会生成一条新消息和新计数，下一次请求恢复原图。<sup>[6][7]</sup>

### 上下文压缩

上下文压缩将较早历史替换为摘要，本身就会重写整段前缀。压缩只有两条触发路径：<sup>[1][2]</sup>

- **自动**：每一步计算 context window 数值；有真实 usage 时用上一次成功响应的 prompt tokens，没有时用本地估算（×2.5）；达到可用窗口的 80% 触发。
- **手动**：`/compact`，不看阈值。

Sunday 将压缩成功视为允许系统提示词和工具数组更新的刷新点：

1. 压缩输入排除系统提示词通知、运行时增量与目标续跑提醒。
2. 用当前所有块的最新内容重新渲染系统提示词，建立新压缩周期。
3. 当前请求的第一条 system 消息替换为新文本。
4. 补发一张完整的运行时快照。
5. 重新冻结工具数组，下一次请求使用新的数组。
6. 旧通知与旧增量不再保留。

目标续跑自动追加的“存在目标……未完成，请继续”是独立消息，不会进入压缩摘要；它只作为提醒留在历史里。

压缩不会重新发送原图。压缩保留的消息会映射回会话记录中的原始消息，因此会话记录保存的是原图，而不是请求期的低清副本；请求时继续按计数决定这一轮发原图还是低清。<sup>[6][7]</sup>

压缩会造成一次明显的缓存失效，但这是换取上下文空间所必需的代价；之后会重新建立稳定前缀。

### 重启延续

冻结文本随会话状态落库。应用完全退出后重新打开并继续同一会话时，第一次请求仍使用退出前的系统提示词；关闭期间对 `AGENTS.md` 等文件的修改会以尾部通知补上。只有压缩成功才会重建系统提示词。

工具数组的冻结只存在当前进程内；应用重启后，下一次请求会按当前工具集重新冻结。因此重启也会让工具集的变化生效。

## 缓存失效

| 变化 | 位置 | 影响范围 | 当前处理 |
|---|---|---|---|
| 系统提示词块内容变化 | 开头 | 直接改写会使整段历史失效 | 冻结 + 尾部 `changed` / `deleted` 通知 |
| 运行时状态变化 | 尾部 | 仅尾部 | 只追加变化字段 |
| 图片降级 | 图片所在消息 | 从图片位置往后一次 | 首次原图，之后 360p 8bit |
| 工具数组变化 | 工具定义区 | 整段 | 压缩周期内冻结；压缩、新会话或重启时重建 |
| 历史裁剪 | 历史开头 | 从裁剪位置往后 | 不专门处理 |
| 上下文压缩 | 历史开头 | 整段一次 | 设计内行为；压缩后重建 |
| 工具历史修复 | 历史中断点 | 从修复点往后 | 行为不变；仅记录日志 |
| 模型、温度、输出上限、思考等级变化 | 参数或开头 | 整段 | 换模型本身即重置缓存 |
| 模型备注变化 | 开头 system 消息末尾 | 整段 | 已知问题，尚未块化 |
| 供应商路由变化 | 供应商侧 | 可能切换缓存池 | 仅 OpenCode 配置会话粘性 |
| 缓存 TTL 到期 | 供应商侧 | 整段 | 无法由 Sunday 控制 |

## 供应商差异

| 供应商/协议 | 缓存方式 | 关键设置 | Sunday 现状 |
|---|---|---|---|
| OpenAI | 自动前缀缓存 | 无需额外设置 | 依赖自动缓存 |
| Anthropic | 需显式缓存断点 | 在请求中标注缓存位置 | 当前未标注，原生接口无缓存收益 |
| Gemini | 部分模型隐式缓存 | 达到最小 token 数后自动生效 | 依赖模型自身行为 |
| DeepSeek、Moonshot 等 | 自动前缀缓存 | 供应商自有计数方式 | 用量中统一读取 |
| OpenCode | 会话粘性路由 | 请求携带会话标识 | 已配置 |
| 网关/聚合服务 | 取决于实现 | 取决于实现 | 请求体一致也可能因路由不同而不命中 |

命中率的计算依赖供应商上报的用量信息。Sunday 将各供应商上报的缓存读取量统一为“缓存读取 token”，再除以输入 token。缺失信息按“未知”处理，而不是按 0 计算。<sup>[9][10]</sup>

## 观测

- **资源面板**：显示 context window 数值、输入/输出 token 与缓存命中率；部分版本提供缓存趋势图。context window 数值优先真实 usage，缺失时用估算；压缩后它会继续更新，不会停在“已压缩”。<sup>[10][11]</sup>
- **后端日志**：位于 `<数据目录>/backend.log`。
  - `[cache-diagnostic]`：命中率异常偏低或突然下降时记录，指出首个变化的消息位置、工具是否变化、请求是否仅尾部延长。<sup>[8]</sup>
  - `[kernel:history-repair]`：历史被修复时记录悬空调用数、孤立结果数和首个修复位置。<sup>[6]</sup>

排查顺序通常为：先确认是否有块变化通知；再确认是否刚发生压缩（新压缩周期）；然后检查工具数组是否变化；最后确认历史是否被修复，或缓存是否只是过期。

## 提示

- 将长期规则写入 `AGENTS.md`、记忆库或项目上下文文件，避免在每次对话中重复。<sup>[2]</sup>
- 避免在会话中途频繁修改系统规则。修改不会破坏前面的前缀，但会产生可能很长的通知。
- 保持会话主题集中；无关话题另开会话，可缩短历史并减少压缩次数。
- 长会话及时压缩。压缩会失效一次，但可避免后续请求持续携带过大的历史。
- 工具集变化后，等压缩、新会话或重启再用新工具；中途调用会得到“当前工具组未更新”的提示。
- 图片首次以原图发送，之后为低分辨率副本；需要细节时重新读取原文件。<sup>[7]</sup>
- 避免频繁更换模型或调整参数；此类变化本身会使缓存归零。
- 将命中率视为参考指标，而非账单。总费用还取决于输入/输出 token 数量、命中单价与调用次数。

## 已知问题

截至 2026 年 10 月，仍存在以下限制：<sup>[1][3]</sup>

1. **模型备注的改动不会产生通知。** 用户在会话中途修改模型备注时，系统提示词会被直接改写，目前不会出现块通知。
2. **原生 Anthropic 没有显式缓存断点。** 前缀稳定只是必要条件，Anthropic 还需要在请求中标注缓存位置。
3. **工具集变化要等刷新点。** 同一压缩周期内工具数组冻结；新启用的插件、MCP 工具或技能工具要等到压缩、新会话或重启才出现。期间调用会收到“当前工具组未更新”的提示。
4. **路由粘性仅覆盖 OpenCode。** OpenAI 与网关侧的会话粘滞尚未使用。
5. **压缩后未重新核算空间。** 压缩成功后系统提示词会换成最新版本并补发快照，但本轮的空间预算仍按旧提示词估算；极端大的规则变化可能超过目标预算。
6. **严格延续增加状态写入体积。** 整段系统提示词保存在会话状态中，每次检查点都会多写这部分。
7. **缺少逐供应商的实机验证。** 360p 调色板 PNG 与尾部 system 消息在 Anthropic、Gemini 上的实际表现，目前主要依赖自动测试，尚未逐一在真实账号中验证。
8. **同一轮只自动压缩一次。** 压缩后这一轮继续长回去，要等下一轮再压缩；一个会话可以压缩无限次，不存在永久的“已压缩”状态。
9. **真实 usage 晚一拍。** 它描述的是上一次请求；当前请求新加的内容要等下一次响应才计入，阈值以下留出的 20% 用来吸收这一拍延迟。

## 历史

- **2026 年 10 月**：本条目对应的实现包含以下变更：
  - 引入系统提示词压缩周期与冻结机制；块变化以尾部 `changed` / `deleted` 通知追加；通知写入会话记录后固定为历史的一部分。
  - 运行时计划、PID、验证状态改为增量追加；压缩后补发完整快照。
  - 图片降级改为 360p、256 色 PNG，并统一用户消息、工具消息与审批恢复结果的计数口径。
  - 压缩保留的消息会映射回会话记录中的原始消息，避免保留的图片被请求期副本过滤掉，或把低清副本写回存储。
  - 通知状态简化为 `changed` 与 `deleted`；严格重启延续与压缩重建完成。
- **2026 年 10 月 22 日**：压缩触发简化为自动（context window 数值达到阈值）和手动 `/compact`；数值优先真实 usage，缺失时用 2.5 倍本地估算；工具数组在压缩周期内冻结，压缩、新会话或重启时重建。
