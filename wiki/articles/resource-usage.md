# 上下文占用、用量与费用

**上下文用量**（Context usage）是 Sunday 对一次请求携带了多少内容、供应商报告了多少 token 的显示。它帮助判断上下文是否接近上限，也帮助理解费用来源，但不等于供应商账单。

| 信息框 | |
|---|---|
| 类型 | 用量与费用 |
| 入口 | 输入框附近的上下文占用条；右侧“资源”模块 |
| 主要指标 | 输入 token、输出 token、缓存读取 token |
| 数值来源 | 真实 usage 优先，缺失时用本地估算（×2.5） |
| 缺失数据 | 按“未知”处理，不按 0 计算 |
| 是否等于账单 | 否 |

## 概述

模型每次回答只能接收一定数量的材料。上下文占用表示这次请求使用了多少可用范围。材料包括系统规则、会话历史、文件内容、工具结果和图片，不只是最新输入的文字。<sup>[1][2]</sup>

Token 是模型计算内容长度的单位，不能简单等同于汉字数。

## 上下文占用是什么

上下文占用条把当前请求与模型可容纳范围进行比较。数值优先使用供应商返回的真实 usage；没有真实 usage 时使用本地估算，并乘 2.5 作为安全系数。右侧卡片显示的就是这个数值。它受以下因素影响：

| 因素 | 影响 |
|---|---|
| 系统提示词 | 规则、技能索引、项目上下文文件 |
| 会话历史 | 消息、工具调用与结果 |
| 文件与附件 | 读取的文档、图片 |
| 工具定义 | 可用工具的数量与描述 |
| 运行时状态 | 计划、进程、验证要求 |

窗口越大，通常能一次带入更多材料，但实际效果还受模型能力、请求限制与配置影响。

## 为什么会自动整理

context window 数值达到可用窗口的 80% 时，Sunday 会自动把较早内容整理成摘要，给后续工作腾出空间；也可以手动执行 `/compact`。同一次任务内再次达到阈值仍可整理，卡片继续显示最新占用。详情见[对话太长时的上下文整理](compaction.md)。

整理会保留概况，但可能损失细节。重要规则适合放进[上下文文件](context-files.md)，稳定事实可以保存在[记忆](memory.md)。

一份很长的命令输出同样会占用上下文。只读取相关文件和必要片段，通常比反复发送整个项目更有效。

## 用量与费用怎样理解

资源模块使用供应商返回的用量信息：

| 指标 | 含义 |
|---|---|
| 输入 token | 本次请求携带的内容 |
| 输出 token | 模型生成的回答 |
| 缓存读取 token | 供应商报告从缓存读取的部分 |

有些服务不报告完整数据。“暂无统计”不等于没有消耗，缺失的缓存信息按未知处理，而不是当成未命中。

以下情况也可能产生额外调用：

- 子代理执行。
- 摘要生成。
- 图片生成。
- 失败后的重试。

需要控制花费时，先减少无关材料，完成小范围验证，再扩大任务。不要假设换个模型名字就能自动限制所有费用。

## 缓存命中率

缓存命中率是“缓存读取 token ÷ 可统计的输入 token”。它反映供应商是否复用前缀，不直接等于节省比例。

命中率时高时低，通常与以下变化有关：

- 系统提示词内容变化。
- 工具数组变化。
- 图片降级。
- 上下文整理。
- 缓存过期。

完整机制见[上下文与缓存命中](context-and-cache.md)。

## 提示

- 上下文占用高时，先整理历史，再考虑换更大的窗口。
- 不要反复发送整份文件，让 Sunday 按需读取片段。
- 把命中率当参考指标，不当账单。
- 长任务分阶段完成，比一次塞入全部资料更可控。

## 已知问题

- 供应商未报告缓存字段时，命中率可能显示为未知。
- 不同供应商对输入 token 的统计口径并不完全一致。
- 真实 usage 描述上一次请求，当前请求新加的内容要等下一次响应才计入；阈值以下留出的 20% 用来吸收这一拍延迟。
- 压缩后卡片会继续更新，不存在永久的“已压缩”状态。
- Sunday 显示的数字不能替代供应商账单。
