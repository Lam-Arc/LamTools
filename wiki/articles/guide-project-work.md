# 实用教程：让 Sunday 修改一个项目

**项目修改教程**（Project change walkthrough）是一套让 Sunday 安全修改项目的步骤：先读规则与现状，再明确验收，执行后查看真实变化。

| 信息框 | |
|---|---|
| 类型 | 实践教程 |
| 适用场景 | 修改文字项目或代码项目 |
| 前置条件 | 项目已打开、重要文件有备份或版本记录 |
| 步骤数 | 4 |
| 相关功能 | 上下文文件、审批、工具模式、Git |
| 关键原则 | 先确认范围，再允许修改 |

## 概述

这个流程适用于文字项目，也适用于代码项目。核心是先确认范围和验收方法，再允许修改，最后检查真正的文件变化。<sup>[1][2]</sup>

准备事项：

- 打开正确的项目。
- 对重要文件已有备份或版本记录。
- 需要运行命令时，本机已安装相关工具。

## 第一步：读规则和现状

发送：

> 先阅读项目说明和适用规则，找出与这次需求有关的文件。告诉我目前的做法、要修改的位置和可能影响。此阶段只查看，不改文件。

检查它找出的内容是否相关。如果完全找错位置，先纠正项目和路径。

长期规则放在 [AGENTS.md 等上下文文件](context-files.md)，临时需求写在当前消息里。

## 第二步：明确验收

发送：

> 我希望得到的变化是：……。完成标准是：……。只改相关内容，保留原有工作。请先列出能够证明结果正确的检查，再实施。

验收标准示例：

| 项目类型 | 可检查的结果 |
|---|---|
| 文字项目 | 内容、结构、原文是否保留 |
| 代码项目 | 特定行为、相关测试、构建结果 |

不要只要求“确保没问题”，要说明哪些结果可以复核。

## 第三步：执行和查看差异

确认后让它继续，同时检查[权限](approvals.md)与[工具模式](tool-modes.md)。

| 环境 | 检查方式 |
|---|---|
| 有版本管理 | 列出 [Git 差异](git.md) |
| 无版本管理 | 列出改动文件、保存路径、关键变化 |

执行命令遇到缺依赖、目录错误或服务报错时，先解决原因。反复运行同一条失败命令，不等于完成验证。

对已有文件的修改要格外注意，别把模型建议的一段替换文字误当成已经写入。

## 第四步：交付检查

要求说明：

- 改了什么。
- 检查了什么。
- 还有哪些限制。

自己打开文件或运行目标行为，确认“任务结束”与“需求达成”一致。

需要尝试另一套方案时，可以[另开会话](message-history.md)，但两条会话可能共享同一个项目目录。

## 常见偏差

| 偏差 | 调整 |
|---|---|
| 改动了无关文件 | 回到第一步缩小范围 |
| 只说改了，没有证据 | 要求列出差异与检查结果 |
| 测试没跑就说完成 | 要求给出实际输出 |
| 覆盖了原文件 | 先备份，再重新执行 |

## 提示

- 先只读检查，再写入，分两步走。
- 每步都要求给出可复核的证据。
- 重要项目先提交或备份，再让 Sunday 动手。

## 已知问题

- 会话回退不会恢复文件，文件要另行恢复。
- 没有版本管理时，只能依靠文件列表与人工核对。
