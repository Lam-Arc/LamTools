**任务 1：基于开源模型微调**  
复杂度：中等  
目标：交付一个能加载、能推理、能回答目标领域样例的小模型。

流程：  
Writer 负责训练项目、数据格式、LoRA/QLoRA 脚本、推理 CLI/API、文档。  
Butler 负责租 GPU、部署环境、跑 smoke train、下载 checkpoint、释放资源。  
验收：checkpoint 可加载，推理脚本可运行，20 个样例有可用输出，成本记录完整。

**任务 2：继续预训练 + 指令微调**  
复杂度：高  
目标：让模型吸收一批领域语料，再做指令微调，交付领域增强小模型。

流程：  
Writer 负责语料清洗、continued pretraining 脚本、SFT 脚本、评测集、推理服务。  
Butler 负责多阶段训练调度、断点恢复、日志监控、显存/费用监控、checkpoint 管理。  
验收：继续预训练和 SFT 都跑通，有 loss 曲线、checkpoint、基础 eval，对比 base model 有可解释变化。

**任务 3：从零预训练 1B/2B 小模型**  
复杂度：极高  
目标：从 tokenizer / 架构 / 数据配比 / 预训练 loop 开始，训练一个可推理的小模型原型。

流程：  
Writer 负责 tokenizer、模型架构配置、数据管线、预训练框架、分布式训练配置、评测和导出。  
Butler 负责预算决策点、GPU 集群租用、长时间训练、失败恢复、成本硬上限、checkpoint 回收。  
验收：模型可加载、可生成非空输出，有 tokenizer、训练日志、checkpoint、最小 benchmark。质量不要求高，但必须可复现。


  
与其他成员协作，建议不要做成普通 tool，而是做成 **Runtime 级协作协议 + Agent/Member 调用接口**。

核心区别是：

`tool：我需要一个动作 agent：我需要一个专业判断 member：我需要另一个角色共同承担任务`

比如 Writer 调 Butler，不应该像调工具一样：

`run_server_rental_tool()`

而应该是：

`ask_member("butler", task="评估并租用适合训练 1B 模型的服务器")`

因为 Butler 不只是执行动作，它还要判断预算、供应商、风险、失败恢复、是否需要用户确认。

**我建议这样分层：**

`WriterRuntime → CollaborationManager → call_member("Butler") → call_member("Sage") → call_member("Artist") → call_member("Reviewer") → ToolRuntime`

成员之间的协作应该走 call_member，不是直接互相乱调工具。

---

**成员协作协议**

每个成员调用都应该是结构化的：

`call_member( member="butler", task="租一台适合 QLoRA 微调 1B 模型的服务器", mode="high", constraints={ "budget": "low", "duration": "24h", "must_confirm_before_payment": True }, expected_output=[ "推荐方案", "预算估算", "风险", "需要用户确认的决策点" ] )`

返回也必须结构化：

`{ "status": "need_decision", "summary": "找到 3 个可用服务器方案", "result": {...}, "decision_points": [...], "risks": [...], "next_actions": [...] }`

Runtime 根据 status 决定下一步：

`success → 继续任务 partial → 可用但标风险 need_decision → 暂停给用户 failed → 重试 / 换成员 / 降级方案`

---

**为什么不是 tool？**

因为成员协作不是原子动作。

例如：

- Sage：决定研究路线、数据策略、评估标准
- Butler：处理资源、预算、调度、外部服务
- Artist：生成视觉资产、图像数据、风格统一
- Writer：写代码、集成系统、跑测试

这些都包含判断、规划、验证和失败恢复。  
如果做成 tool，会把复杂判断藏进工具里，Runtime 失去控制。

---

**为什么也不是普通 agent？**

因为“成员”比 agent 更重。

DesignAgent 是 Writer 内部能力。  
Butler 是另一个成员，有自己的 Runtime、记忆、权限、工具、长期目标。

所以应该区分：

`内部 agent：Writer 的专业子能力 外部 member：另一个完整成员 runtime`

例如：

`Writer 调 DesignAgent：内部设计能力 Writer 调 Butler：跨成员协作 Writer 调 Artist：跨成员协作 Butler 调 SearchAgent：Butler 内部能力`

---

我建议最终统一成两个接口：

`call_agent(name, task, mode, context) call_member(name, task, mode, context, contract)`

其中：

- call_agent：调用当前成员内部能力
- call_member：调用其他成员 Runtime
- contract：协作契约，定义交付物、权限、决策点、失败策略

这会比“所有东西都是 tool”稳定，也比“成员之间随便互调”更可控。
