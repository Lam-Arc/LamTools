这次真实任务暴露的问题，按严重程度汇总如下。

**阻塞级**

1. **完成判定太弱**
   旧验证只看 compile/import/pytest，没发现 `main.py` 调用了不存在的方法。  
   后果：复杂项目看起来“完成”，实际 GUI 操作会炸。  
   已修：新增 `python_api_refs`，检查本地类实例的方法/属性引用。

2. **修复态会读循环**
   用户反馈问题后，Writer 反复 `read_file/recall_session`，迟迟不改。  
   后果：CLI 长时间跑，任务不收敛。  
   已修：完成验证失败后进入修复态，限制只读轮次，之后强制 `write_file/edit_file`。

3. **修复态只给摘要导致无法编辑**
   工具输出只剩摘要和 `output_id` 后，Writer 缺少完整代码上下文，只能继续 `recall_session`。  
   后果：摘要化和修复能力冲突。  
   已修：普通状态摘要化；修复态 `read_file` 保留必要文件内容进当前 prompt。

4. **完成会话无法 CLI 精确召回**
   `writer tool recall_session` 使用临时 data_dir，查不到真实 session memory。  
   后果：调试和人工接管困难。  
   已修：CLI tool 使用后端一致的 `settings.data_dir`，并加载真实 session state。

5. **完成态 state 读不回来**
   Runtime 会保存 `loop_position=idle`，但 schema 不允许 `idle`。  
   后果：完成后的 session 无法被 tool/CLI 正常加载。  
   已修：`WriterLoopPosition` 加入 `idle`。

**高风险**

6. **任务分支被占用时退回 writer/main**
   某次 worktree 占用任务分支，Writer 没切成功，最后直接在 `writer/main` 上提交。  
   后果：分支分层被破坏。  
   已修：任务分支被占用时自动生成独立 fallback 分支。

7. **edit_file 短匹配破坏代码**
   Writer 用太短的 `old_text` 做替换，可能替错位置。  
   后果：代码结构被破坏。  
   已缓解：失败修复和完成验证能拉回来。  
   未彻底修：还需要强制 old_text 唯一匹配/足够上下文，或改结构化 patch。

8. **复杂任务首次独立开发质量不够稳**
   “本地视频剪辑软件”能产出项目，但第一版存在 API 漂移。  
   后果：说明 Writer 能跑链路，但复杂任务一次性质量还不够。  
   状态：需用新版验证器重跑空目录完整开发。

**中风险**

9. **CLI 长任务体验差**
   长任务 raw 输出难读，某些 `Start-Process` 场景 exit code 为空。  
   后果：用户不知道是真的卡住、还在跑、还是已完成。  
   状态：未修。

10. **Git 树不够干净**
   测试留下多个 worktree 和旧分支；早期分支名如 `writer/test/api-readme` 质量差。  
   后果：真实长期使用会积累噪声。  
   状态：未做自动清理策略。

11. **checkpoint 主要集中在最终**
   中间关键阶段锚点不足。  
   后果：失败后恢复粒度不够细。  
   状态：未修。

12. **完成验证结果过去没有进入 session memory**
   错误如 `python_api_refs` 之前不能按错误名召回。  
   已修：后续 completion verifier 结果会被索引。

**待验证**

13. **session memory 排序质量**
   能按 `output_id`、文件名、符号召回，但排序是否稳定最优还没专项测试。

14. **Git 决策分支流程**
   “决策点先 checkpoint，再切独立 decision 分支”还没真实压测。

15. **跨会话长期记忆机制**
   candidate/confirmed/deprecated、用户级/项目级作用域，还没完整真实验证。

最终一句话：

这次测试最大的价值是把 Writer 从“看起来能完成”推进到“能被更强验证拦住、能接反馈继续修、能收口提交”。但复杂任务从零一次性高质量交付，还需要再跑新版完整验收。

- 还没有做来源可信度分级，比如官方文档 > GitHub > npm > 博客。
- 还没有做专门的许可证解析。

大致可以这样分：

**Writer：runtime loop**
适合开放式编程任务。路径不可预知，需要读代码、改代码、测试、修复、提交。

**Artist：runtime loop + 明确阶段**
如果 Artist 是做视觉/产品/多媒体生成，通常也不适合纯 LangGraph。创作过程会反复试、评审、修改。但它可以有固定阶段：

```text
理解需求 -> 生成方向 -> 产出草案 -> 视觉自检 -> 修改 -> 交付
```

所以 Artist 适合“主循环 + 阶段约束”，不是硬图。

**Sage：graph / workflow 更合适**
如果 Sage 偏知识、研究、分析、规划、资料整理，它更适合可控流程：

```text
收集资料 -> 归纳 -> 交叉验证 -> 生成结论 -> 标注来源
```

这种任务要求可追溯、可审核，LangGraph 类结构会更稳。

**Butler：graph / workflow 最合适**
如果 Butler 是助理、自动化、日程、文件整理、通知、后台任务，它通常是明确流程和权限边界：

```text
触发 -> 检查条件 -> 执行动作 -> 确认结果 -> 通知用户
```

这类任务更需要可控、可审计、可重试，适合 graph/workflow。

**LamMate / Companion 类：state machine + lightweight loop**
如果 Mate 是陪伴、对话、用户偏好、日常协助，它不需要复杂图，也不该像 Writer 那样无限工程循环。更适合：

```text
用户状态 -> 意图识别 -> 回复/建议/记忆更新
```

也就是状态机 + 小 loop。

**总结**

```text
Writer  -> runtime loop
Artist  -> runtime loop + creative stages
Sage    -> graph/workflow + verification
Butler  -> graph/workflow + permissions
Mate    -> state machine + small loop
```
