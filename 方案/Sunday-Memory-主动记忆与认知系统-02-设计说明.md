# Sunday Memory · 设计说明（可供审查）

> 对应 PRD：`方案/Sunday-Memory-主动记忆与认知系统-PRD-V1.0.md`
> 本版按 2026-11-25 评审意见收敛：去掉过度保护与过度工程化，以实际认知效果、准确性、及时性和成本为准。
> 实现与测试证据见 `方案/Sunday-Memory-主动记忆与认知系统-01-现状复核与实施报告.md`。

## 一、这份 PRD 要解决的真问题

不是「再加一个记忆文件」，而是三件具体的事：

1. **新会话不再从零开始**。现在 Agent 要知道你的偏好，得先意识到「我该去翻记忆」，再去读文件。多数时候它不会翻，于是每次都像第一次见你。
2. **认知要自己长**。靠用户每次说「记住这个」不现实；靠模型当场写也只在它想起来时发生。
3. **不能为了省事，把记忆变成一团没法维护的摘要**。记忆得能读、能改、能带走、能回滚。

一句话：**让 Agent 每次开口前就已经知道该知道的事，同时让这些「知道」始终是用户可以打开、修改、撤销的普通文件。**

## 二、总体思路：加一层「认知」，不建第二个记忆库

现有记忆库已经是一个可靠的知识仓库：一档全局、一档项目，都是普通 Markdown 文件，靠目录结构和自动生成的索引让人和模型都能找到东西。

在这之上加一层 `memory.md`：它不是目录，也不是所有记忆的拼接，而是**「现在最该直接知道的那几段话」**。知识还在原来的文件里，`memory.md` 只负责让人一开口就带着它。

四层分工：

| 层 | 是什么 | 什么时候用 |
| --- | --- | --- |
| 认知 | `memory.md` | 每次对话自动带上 |
| 索引 | `INDEX.md`（沿用原有） | 自动带上，告诉模型还有哪些细节可查 |
| 详情 | 一条条记忆文件 | 模型觉得需要时才读 |
| 原始记录 | 历史会话与来源快照 | 需要追根问底时才查 |

**为什么不让模型自己决定要不要读记忆？** 那等于把「省调用」和「一定有认知」对立起来。PRD 要「无需工具调用即可掌握」，所以必须发生在请求组装时。

**为什么不新建记忆库？** 两套系统一定打架：谁是权威、删了算谁的、改了一边另一边怎么办。现有文件库已经能看懂、能备份、能迁移，直接在上面长最省事。

## 三、核心设计：认知可以演进，用户能置顶，版本兜底

第一版设计把文档切成「手写区」和「自动整理区」，自动整理永远碰不到手写区。评审指出这会带来新问题：**两段长期各说各话**——你三年前写「喜欢长回答」，自动区早就改成「要短」，文件里同时存在两个答案。

改成的规则是：

1. **整篇认知由整理统一改写**。合并重复、替换过时结论、消解矛盾，这是它的正常工作，不再被结构拦住。
2. **用户可以置顶**。把一句话放进 `memory:keep` 标记之间，任何自动改写都会原样保留它——这是「用户明确意图」的表达方式，不靠模型自觉。
3. **版本备份兜底**。每次改写前存一份旧版本，记忆页可以看历史并一键恢复。被主动替换掉的内容找得回来。

这三条合起来的意思是：**正常演进不受阻碍，重要内容不靠运气，事故有退路。**

## 四、后台整理（Dreaming）：什么时候动

设计难点不是「让模型总结」，而是**什么时候值得花一次模型调用**。

- **时间**是主要的频率控制：同一档位两次整理之间有冷却；同一个会话短时间内不反复整理。
- **字数只用来决定「现在整理，还是过一会儿再整理」**：一轮对话结束时如果新内容太少，就先不动；定时扫描会把这段短内容补上。
- **绝不因为「短」而丢弃**。一句「以后都用 Rust」只有十个字，但它比一段寒暄重要得多。
- **只处理没整理过的部分**：每个会话记一个进度点，不重复读历史，也不因为重启而从头再来。
- **单次有上限**：处理的对话量、输出长度都有封顶，成本可预期。

三个触发入口：一轮对话结束后顺手看一眼（不阻塞回复）、每十分钟的兜底扫描、用户在记忆页点「立即整理」。

**放弃的方案**：每条消息都整理（贵、吵、半句话不该当结论）；按字数过滤内容（把「短而重要」当成「不重要」）。

## 五、记忆怎么变「准」，而不是变「长」

1. **分清事实与推断**：用户说过的、确认过的、模型推断的、还没定的，提示中要求区分；推断不能写成结论。
2. **过时的结论要改，不是叠着放**：整篇重写让旧答案被替换，而不是和新的并列。
3. **有时间感**：会过期的信息要带时间。
4. **体积靠整理控制，不靠截断**：提示中要求把 `memory.md` 维持在三千字左右，变长时把细节下沉到独立记忆文件、认知层只留一行。只有在模型明显失控时才截断，并写明「已超上限、末尾截断」——截断是异常兜底，不是日常手段。

## 六、记忆和当前对话冲突时听谁的

**听用户当前的。** 记忆是背景知识，不是系统指令。注入时会明确写：如果你现在说的和记忆不一致，以你现在说的为准，并考虑更正记忆。

所以记忆的措辞是「用户偏好 X」这种描述，而不是「必须做 X」这种命令。

## 七、开关：关掉之后，到底关了什么

- 关掉：不再自动把认知带进对话，不再后台整理；正在跑的整理即使模型已经回了，也不落盘。
- 不关：已保存的记忆一个不删；记忆工具照常可用；手动查看、编辑、恢复版本照常。
- 重新打开：立刻恢复，之前积累的认知还在。

**关闭要真的生效，而不是「发一条说明、旧内容继续留在头部」。** 所以开关一翻，下一次请求会重建头部——这一次缓存失效是用户主动改变行为换来的，值得。反过来说：日常的记忆更新不做这种重建，只追加一条尾部说明。

## 八、安全与「忘记」

- **密钥类内容不记**：整理结果按行过滤，密码、令牌、私钥直接丢掉。
- **删除就留下遗忘记录**：三个删除入口都会记；整理提示词把它列为禁止恢复。
- **做到「合理可靠」为止**：这是防复活的提醒，不是绝对语义遗忘，也不为此建一套追踪系统。
- **每次改写都可回滚**：改前存旧版本，保留最近若干份。

## 九、并发：两个人同时动记忆

- 整理写之前确认「我读到的那版还是最新的吗」。不是，就从最新内容重新算，而不是盖掉。
- 同一时间只允许一个整理在跑；不同项目的整理也不会同时写共享的全局档。
- 整理中途崩溃留下的锁会自动作废；状态文件坏了只丢进度，不丢记忆。

## 十、代价：为什么它不会让每次对话都变贵

1. **注入的内容是稳定的**：两次上下文压缩之间，头部沿用第一次的文本；记忆更新只在请求末尾追加一条说明，且同一次变化只说一次。
2. **只有三种时刻会重算头部**：新会话、上下文压缩后重建、开关切换。前两个是既有机制，第三个是用户主动操作。
3. **整理有闸门**，而且内容没变就完全不写。

日常增量主要是第一次把认知读进来，之后是缓存命中；整理是一天几次后台调用，不占对话路径。

## 十一、按评审收敛掉的地方（原设计里多做的）

| 原做法 | 现在 |
| --- | --- |
| 自动整理永远不许碰手写段 | 允许整篇演进；用户需要保留就置顶，事故靠版本恢复 |
| 新增正文不到 240 字就不整理 | 只影响「马上整理还是稍后整理」，扫描会补上 |
| 自动段固定 2000 字、超出截断 | 提示里要求整篇控制在三千字、细节下沉；截断只作异常兜底 |
| 开关只影响之后的请求（头部仍留旧认知） | 开关切换会重建头部，实际生效 |
| 一个 app 层的 supervisor 包装模块 | 合并回记忆模块，少一个文件 |
| 若干「待定」项（入口、删文件、导入导出、模型选择） | 已按评审定下：入口只留记忆页；不自动删文件；不做导入导出；复用后台任务模型 |

## 十二、怎么判断这次做成了（用大白话）

| 场景 | 现在会怎样 |
| --- | --- |
| 第一次用 | 默认就开着，不用配置 |
| 开新会话 | 不用叫它去查，它已经知道你的偏好和项目约定 |
| 你说了一个长期偏好 | 之后某次整理会吸收进认知，后面自然用上 |
| 你改了旧决定 | 认知里的旧结论被替换，不会新旧并列 |
| 你让它「记住」 | 当场就写，不等整理 |
| 你在文档里「置顶」了一段 | 以后每次自动整理都原样保留；被替换掉的旧版本可恢复 |
| 你说「忘掉」 | 删掉并留下遗忘记录，整理不会主动捡回来 |
| 换项目 | 项目认知跟着项目走，不串味 |
| 只说了一句话但很重要 | 不会因为短被丢掉；最迟下一次扫描就整理 |
| 用很久 | 认知维持在一个小体量，细节在下面按主题堆 |
| 同时开两个会话 | 记忆不会互相覆盖 |
| 整理出错 | 原有记忆原样保留 |
| 关掉开关 | 下一次请求起认知真的不再出现，整理停止；文件和手动功能都在 |
| 想回到旧版本 | 记忆页能看历史并恢复 |

## 十三、已知限制（先说在前面）

- **缓存命中率没有在真实应用里采样过**。现有证据是「请求头部逐字节不变」，这是命中的必要条件；实际数字还取决于服务商的缓存规则和过期时间。
- **整理质量取决于模型**。闸门能挡频率，挡不住判断失误；写歪了可以手改、可以恢复旧版本。
- **对话中途的会话也可能被扫到**，可能只整理到用户那句话。影响很小（用户说的才是信息），设计上不追求「必须等整轮结束」。
- **只做桌面端**。手机端记忆页本来就没有接入记忆接口，符合项目规则。
