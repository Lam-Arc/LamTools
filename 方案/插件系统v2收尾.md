# 插件系统 v2 收尾

## 需求与边界

### 这份方案从哪来

《插件系统重构》十二步迁移完成后做了一轮代码审查。结论：核心装配层是好的，问题集中在三个接缝，并有两个实锤的运行期 bug。

实锤 bug：

1. v2 插件后端在同一进程里被反复创建。`assemble_core_agent_plugins` 的 v2 分支每次都无条件 `load_enabled_plugin_backends`（`app/base_agent.py` 约 1930 行），而这个函数无缓存（`plugins/lifecycle.py:262`）。它又在每轮对话开始（`app/default_agent.py:578`）、命令技能注册（317 行）、审批恢复（1422 行）反复执行；`build_core_plugin_operation_catalog`（`app/base_agent.py:2146`）启动时再加载一遍。study、workflow 每轮对话新起一套后端，旧的从不停。
2. study/workflow 会话被判"插件已禁用"。会话可见性用 v1 注册表判断（`plugins/session_visibility.py:39`），v1 注册表跳过所有 v2 插件（`plugins/registry.py:232`），于是 `app/core_session_store.py:98` 抛 ValueError。`tests/test_plugin_session_visibility.py` 当前是红的。

三个接缝：

- **两本账、两套注册表并存**。"插件启用了吗"没有唯一答案（`plugins.jsonc` 与 `plugin-system.jsonc`），"这个子系统该看到哪些插件"没有唯一入口（`assembly` 过滤散落在各调用点，`plugin_system/operations.py` 三处漏过滤，v1 插件被 v2 插件页误管）。
- **声明装配与后端生命周期混在一层**。设计 7.1 说声明每轮重读、代码层启动时决定，但实现把两者绑在一起，"每轮重读"拖着"每轮重启后端"跑。
- **前端契约半兑现**。九个区域只挂了两个（composer、settings），`entry_url` 无人消费，`replace` 未实现，import map 模块替换整块缺失，行为表未产出——与"十二步全部完成"的记录不符。

### 要什么

用户已拍板两件事，直接决定本方案形态：

- user:“目前没有存量插件，此系统一直处于开发状态” → **直接删除 v1 旧系统**，废除 `assembly` 迁移标记，所有 plugin.json 默认走 v2。不做兼容桥，不迁移旧账本。
- user:“本轮一起实现”（针对前端模块替换）→ **import map 覆盖层与行为表纳入本轮**，不再收缩承诺。

在此之上：

1. 单一插件系统：一个账本、一个发现与启停入口、一个插件页。
2. 装配纯函数化、后端进程级唯一：连续对话不重复起后端。
3. 前端契约兑现：九区挂载、自绘 entry、replace、dangerous 确认、参数收集。
4. 前端模块替换（import map）与行为表，补上原方案步骤 4、15 的欠账。
5. 审查发现的配套缺陷按附表逐条修复。

### 这次不做

权限模型与沙箱（维持原案，用户明确不需要）、密钥处理（单独排期）、市场客户端与索引（只留本地管理）。

### 推定

开发期不存在需要保数据的用户插件目录；开发机上的 `plugins.jsonc`、手装 v1 插件目录直接清掉，不写迁移代码。`create-plugin` 生成的插件从此不需要 `assembly` 字段。

### 2. 装配与后端生命周期分层

原则：**声明装配是纯函数，每轮可跑；后端实例进程级唯一，启动时定，运行中只按启停切换。**

- `PluginHost` 进程级单例：应用启动（`desktop_backend` / `http_agent_app`）构造一次，经依赖注入传给各使用方；CLI 与测试自行构造。当前五个构造点（`cli.py:2518`、`base_agent.py:1922/2146`、`default_agent.py:2531`、`study/eval_manifest.py:72`）全部收敛。
- 后端实例归 `V2RuntimeManager` 演进出的 `PluginBackendRegistry` 唯一持有：首次需要的插件加载一次，启停走 manager，句柄复用（含 `_stopped` 复活路径）。`build_core_plugin_operation_catalog` 与 `assemble_core_agent_plugins` 共享同一份句柄，删除两处无条件 `load_enabled_plugin_backends`——这正是 v1 注释里警告过的"双实例分脑"。
- `assemble_core_agent_plugins` 拆成两段：`assemble_declarations(host)`（纯读：清单、六类能力、agent、ui、hooks 定义，每轮跑）＋ 后端句柄从 registry 取。turn_start、命令技能注册、审批恢复、`plugin_sub_agent_runner_factory` 只调声明段。
- 冻结语义（7.1 节）不动：工具数组按会话加压缩周期冻结、系统提示词冻结在会话元数据，已有 `test_tool_freeze.py` 锁住。

### 3. 前端契约兑现

**统一挂载层。** 九个区域（appRail、left、titlebar、main、right、composer、composerSide、message、settings）各挂一个 `PluginSystemContributions`（`region` prop 不同）；挂载点落在 `WorkspaceShell.vue` 与 `MessageView.vue` 已有的 `data-region` 容器上，不新造位置。

**`PluginRegionBlocks.vue` 补齐四件事：**

- `entry_url`：区域里放一个空容器并注入模块脚本（走现有 `injectScript` 的去重机制），插件自己往里画。
- `replace: true`：同区域有接管者时隐藏原内容（挂载层读 region 列表里的 replace 标记）。
- `dangerous` 按钮：点击先弹确认，再调 operation。
- `input_schema`：声明了入参的 action 弹参数表单（复用配置面板的控件），不再一律传空对象。

**样式与脚本的生命周期约定写进作者文档：** link/script 每地址只注入一次，禁用插件后已注入的不撤除，需整页重载；含 overrides/styles 变更的启停操作由插件页自动触发重载。

**右栏与模式：** websearch 右栏面板改为经 `right` 区域挂载——清单里声明右栏贡献，组件本体仍随包编译（沿用 `bundledPluginModeLoader` 的先例给 bundled 插件配组件装载器）。理由：右栏挂载层需要一个真实且复杂的消费者来验证，不能只靠玩具插件；联网搜索本来就是 websearch 插件的功能面，留在核心里反而是一颗特例。核心右栏其余五个模块（清单、资源、子代理、后台进程、RAG）本轮不动，后续谁插件化谁照这条路走。模式组件继续随包编译，第三方模式的界面路径 = 区域挂载 + import map 替换。

### 4. 前端模块替换（import map）

补上原方案第 13/15 节欠账，与后端 boot finder 同一套 overrides 声明。

**键空间放开。** `overrides` 的键支持两族：`lamtools_core.xxx`（后端，boot finder，已实现）与 `ui/src/...` 前端模块路径（本轮新增）。两族同表解析、同表查冲突（同一目标只能一个插件接管）。

**构建改造。** Vite 生产构建对 `ui/src/**` 保留模块边界（`build.rollupOptions.output.preserveModules`，应用代码每源文件一个产物），第三方依赖仍打进 vendor chunk，不参与替换。构建同时产出模块清单（模块路径列表），供行为表与冲突校验用。开发版天然是模块边界，行为一致。

**注入时机。** Core 返回 `index.html` 时，按当前启用插件的 overrides 前端键生成 `<script type="importmap">`，插在文档最前、任何模块脚本之前；映射值指向插件资产路由（`/api/core/plugin-system/<名字>/assets/<路径>`，同源）。安全模式（`LAMTOOLS_SAFE_MODE`）跳过全部映射。含 overrides 的插件装/卸/启停后必须整页重载——import map 在模块加载前就定了，这是原方案 15 节写明的代价。

**校验。** 安装时检查前端键确实存在于构建模块清单，不存在按"检测只用来提醒"处理（原方案 10.2）；替换文件缺导出 → 页面启动报错，错误落在具体导入上，日志可见——与后端"启动时报错、日志能看出是谁"对称。

### 5. 行为表

- 后端：构建/启动时用 `pkgutil` 反射 `lamtools_core` 产出模块清单。
- 前端：构建时产出模块清单（上一节）。
- 合成：发布流程把两份清单合成 `behavior-table.json`（条目：层、名字、可替换、内核标记），随版本分发；插件页可查，`create-plugin` 与 `port-plugin` 读它。
- 内核四样照旧不可替换：插件加载器、模块清单本身、安全模式入口、日志。

## 步骤

每步先写验收测试再动手。仅运行本步骤相关测试。

1. **单一系统与账本统一。** 删 v1 注册表与旧账本读取，路径权威搬 `plugin_system/paths.py`，`session_visibility` 改读 `PluginHost`，`assembly` 字段废除。验收：全仓无 `PluginRegistry` 引用、无 `plugins.jsonc` 读取；`test_plugin_session_visibility.py` 转绿；插件页单一列表。
2. **生命周期单例与装配纯化。** `PluginBackendRegistry` 进程级唯一；五处 `PluginHost` 构造收敛；`assemble_core_agent_plugins` 拆声明段；discover 短缓存。验收：新增探针测试——同一进程连续 N 轮装配后 study/workflow 后端实例数恒为 1；启停插件后实例数随启停 ±1。
3. **插件页完整化。** 安装（本地/zip/链接）、依赖检查、更新、卸载、配置表单并入 v2 插件页；`plugin.system.*` 补链接来源与冲突展示。验收：从 zip 安装→启用→配置→更新（数据还在）→卸载（可选留数据）全程在 v2 页完成，无需 v1 操作。
4. **host 与 boot 加固。** 更新回滚、残留目录、boot 路径单一来源、utf-8-sig。验收：模拟 `os.replace` 失败后 `data/` 在原位；预置 `.update-*` 目录不出现在插件列表且下次启动被清扫；boot 与运行时读到的根列表、账本路径逐项相等（测试断言）。
5. **区域挂载层与交互补齐。** 九区挂载、entry_url、replace、dangerous 确认、参数收集；websearch 右栏面板迁到 `right` 区域挂载。验收：右栏卡片插件、`replace` 换主区插件、纯 CSS 插件三条端到端（前端测试）；`entry_url` 自绘插件能画能点；联网搜索面板经区域层挂载后功能与迁移前一致。
6. **import map 模块替换。** 构建保留模块边界、Core 注入 import map、overrides 双键族、安全模式、重载约定。验收：原方案步骤 4 三条——只替换流式淡入模块的插件装上后淡入变粒子、卸载后恢复；故意删一个导出，启动报错且日志指明是哪个导入断了。
7. **行为表。** 双端模块清单合成 `behavior-table.json`，插件页可查。验收：表内条目全部标注"模块或内核"之一，无漏网；插件页能按名字查到任一条目。
8. **文档与技能对齐。** 设计文档 schema 全量重写并如实更新迁移进度；`create-plugin`、`port-plugin` 技能同步（不需要 `assembly`、覆盖层后果自负、import map 重载约定）。验收：schema 字段与实现一一对应（测试断言文档列出的字段解析器全部支持）；用 `create-plugin` 生成最小插件不手改可装可用。

## 目标与完成判据

目标：一个插件系统、一套装配、一份兑现了的前端契约；审查发现清零。

完成判据（在原方案判据之上）：

## 宿主能力缺口（bili-scroll 实测暴露，2026-10-24）

把复刻插件装进真实会话跑，暴露的不是插件 bug，而是宿主能力的缺口。按抽象层级记档，每条标注处置状态。

### 1. 运行时身份不可内省（已补一半）

安装即复制，源目录（作者工作区）与安装副本（运行时）是两份文件树——这个模型本身是对的（卸载/更新需要干净边界，随包只读根同构）。缺的是：**"运行时身份"没有可发现的入口**。agent 想配插件时，面对的是文件系统，它不知道哪份副本在跑、data/config/logs 在哪，只能猜。已补：config.get 返回配置路径、模型侧 plugin_config 工具。待补：`plugin.system.paths` 内省操作，一次返回每颗插件的 root / data / config / logs 权威位置——让"运行时在哪"成为可查询事实而不是文件系统推理题。

### 2. 模型面与用户面不对齐（已补）

插件页能做的事（配置、安装、依赖检查），in-session 模型没有对等工具。agent 的工具列表里只有 install/deps/list，没有 config——于是它拿文件系统即兴发挥。已补：plugin_config（读）/ plugin_config_save（写，需确认）。**原则**：模型侧工具应是插件页能力的镜像；用户面与模型面的能力差距，就是第三方 agent 即兴发挥的空间。

### 3. 能力-触达矩阵缺失（已补文档，设计文档待立）

六类能力各自"谁够得着"没有成文：工具→模型，命令→输入框，操作→UI/CLI，配置→面板，钩子→引擎，上下文→提示词。create-plugin 技能曾把 operation 写成"模型可调"——模型没有任何操作桥，这是设计事实，却没写在任何地方，第三方作者必踩。已在技能修正。**设计文档应立一张能力-触达矩阵**，每个声明能力标注三个触达面（模型 / 用户界面 / 引擎），"操作不可被模型调用"这类事实属于矩阵而不是约定俗成。

### 3b. 单能力多面触达：一次声明只够一个面（待设计）

bili-scroll 的值班参数写了两种方言：operations.jsonc 一份给命令与面板，tools.jsonc 一份给模型，载荷靠共享函数手动防漂移——这是自觉，不是机制。"既给界面又给模型"的能力，任何插件都要重复声明。设计候选：操作声明加 `model` 扩展（permission + tool_name），宿主装配时为显式声明的操作自动生成模型工具；默认不暴露（保住"操作 auto_allow 是人面通道"的安全姿态），声明即上模型面，重名装配期报。前置：能力-触达矩阵（3）先行成文，本条是矩阵上"操作"一格的扩展。触发时机：第二颗"两面插件"出现时实施。

### 4. 无人值守执行语义缺失（待设计）

原版用专用 profile 解决"值班轮无人看着跑"：只读工具面 + 白名单 + 无头会话。我们的对应物是子代理（run() 原生支持 allowed_tools / mode），缺的是**声明式的运行约束**：插件应能声明"我派生的运行长什么样"（工具白名单、审批策略、模型场景），由宿主强制执行——而不是像现在这样由调用方（主会话模型）自觉传参。配套缺口：arrange 的设计语义是"达到条件时在指定项目的新会话或已有会话发送一条用户消息"（用户 2026-10-24 澄清）——因此无人值守轮今天就能拼出（arrange 发消息 → 章程技能 → 子代理收窄面），只读轮（auto_allow 工具）可全程无人跑通；卡住的是写操作（如发评论的 ask_user 审批在无人会话里等待）。缺的是把运行档附到 arrange 任务与子代理派生上的声明与宿主强制。这是 bili-scroll 与原版的真实能力差距，也是一类插件（自动化、监控、值班）的共性需求。

### 5. 变更生效范围不透明（待补）

设计 7.1 的冻结语义（声明每轮重读、工具数组按压缩周期冻结、代码层启动时决定）存在且有测试，但它**没有外化给调用方**：update/enable/config 操作的返回里不说"这次变更何时生效"。实测实例：更新到 0.2.0 后，新工具的声明立刻可见，调用却撞上进程内旧模块。待补：变更类操作返回 effective_at（now / new-session / compaction / restart），插件页与 agent 据此告知用户。

### 6. 双副本的作者教育（已补）

create-plugin 技能原本说"在工作区写文件夹然后安装"，没说**安装之后工作区那份就死了**——运行时代码、data、配置全部以安装副本为准。in-app 模型按直觉把配置写进源目录，运行时永远读不到。已在技能补上两副本规则。port-plugin 同理适用。

### 7. 工具结果携带图像的返回通道（已存在，撤回）

初判为宿主缺口，经用户指正核实为**已实现**：`ToolResult.model_image_data_url` 是模型专属的图像字段（read_file 的图像分支在用），只进当次请求、刻意不落库；图像能否进入请求由按模型能力的请求装配决定，文本模型会收到"你是一个文本模型，这个图片你无法接收"的明确说明——降级路径也是现成的。**封面/画面帧能力对 bili-scroll 而言是纯插件侧工作**：`bili_frames` 按同一形状返回即可，视觉值班模型看图判断，文本值班模型收到可读的降级说明。从宿主缺口清单移除，转入插件待办。

### 7b. 本地转写：初判错误，脚本模式可移植（改判）

初判"torch 级依赖进不了冻结环境所以无解"是**错的**——把宿主进程内工具 handler 的限制，错误外推成了插件的一切。原版的做法就是标准解：插件自带脚本，bootstrap 工具（装转写依赖按钮）用 uv 建自己的 venv、把 Whisper 装进插件家目录，值班轮经脚本进程执行转写。**脚本能否运行取决于用户机器的环境，与宿主打包完全无关**；体积没有约束（原版 538MB 模型，复刻语义 = 行为等价，无大小限制）。create-plugin 技能机制表第一行（skill + run_command）就是这个模式，执行时未应用。

补齐形态：`scripts/transcribe.py` 进插件目录 + 配置声明环境要求 + 装依赖工具（uv 引导）+ 转写工具经 run_command/子进程执行。待实施。

### 7c. 复刻语义与偏离呈现（原则，执行教训）

复刻 = 行为等价，尺寸/体积/依赖形态不做隐性约束。凡原版有而移植版没有或改了形态的，**必须以"偏离"身份进差异表并交用户裁决**——不得以"架构简化/改进"单方面定案。本轮三次偏离（转写、MCP→原生工具、私信延后）均属此类，其中 MCP→原生工具与转写被错误包装成改进。port-plugin 技能的"差异表即交付物"规则本身是对的，执行时违反了它。

另：MCP vs 原生工具的选择在宿主里两皆合法（`mcp/mcp.json` 合并是六类能力之一，MCP 服务端可指向插件自管 venv 的命令路径）。原生工具的真实优势是零安装读路径（原版最大故障源即装依赖链）；真实代价是能力覆盖止步于重写范围、重依赖能力无法进程内表达。正确形态大概率是**混合**：读路径保持原生工具，转写/弹幕/批量抓取走脚本或 MCP——此决策应交用户。
