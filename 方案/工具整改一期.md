## 第二项：权限分级

### 现在的权限是怎么走的

七条事实，都是代码里读出来的。

1. 工具名对一张三档表：自动放行、要审批、硬拦截。表在 `tool/default_toolbox.py` 的 `DEFAULT_TOOL_PERMISSIONS`。
2. `run_command` 另判一次：命令按正则分成普通和高危两组，普通默认自动放行、高危要审批。但这条只在工具本身是自动放行时才生效，而 `run_command` 默认是要审批，所以普通命令实际上还是会弹。
3. 能力档 `read_only` / `limited_edit` / `full_edit` 按工具名白名单，文件是 `access_tools.jsonc`，这是硬边界。
4. 会话预设 `ask` / `full_access`。`full_access` 下所有审批一律放行，包括命令确认。
5. 插件 Agent 可以声明 `ask` / `auto` / `block`，这是最后一道。
6. `read_actions` 字段只有 `arrange` 声明过，没有任何代码读它。
7. 审批面板只有同意、拒绝、指引、跳过；`approve_for_session` 被归一成单次同意，等于现在没有信任记忆。

### 收敛后的形态

一根轴，两个数，一本账，五步判定。

一根轴：0 到 N 的整数级别。

- 0 级：拦截，不注入，任何模式与信任都不放行。
- 1 级：不问。
- 2 级：ask 模式问，auto 与 full 不问。
- 3 级：ask 与 auto 都问，full 不问。
- 4 级以后：三种模式都问，加一行数据即可。

两个数，每个会话各一份：

- 免问线：级别小于等于它就不问。ask 给 1，auto 给 2，full 给 3。
- 可用上限：级别大于它就拒绝。read_only 给 1，limited_edit 给 2，full_edit 给 3。

两个数分开，是因为「问」和「拒绝」不是一回事。read_only 会话不是什么都问，是写类直接不让用。这样 `access_tools.jsonc` 那三张工具名名单就变成一个数。

### 模式接壤

| 模式 | 免问线 | 直接通过 | 仍然要问 |
| --- | --- | --- | --- |
| ask | 1 | 1 级 | 2 级、3 级 |
| auto | 2 | 1 级、2 级 | 3 级 |
| full_access | 3 | 1 级、2 级、3 级 | 无 |

### 判定五步

1. 硬拦截：敏感路径、插件清单 hard block、被禁用的工具。命中就拒绝，任何模式与信任都绕不过。
2. 取基础级：查档位表。没登记的一律 3。
3. 信任覆盖：账里有这个键，生效级取「记录的级」与「基础级」里较小的那个，最低到 1，不能降到 0。
4. 比上限：生效级大于可用上限就拒绝，提示当前会话能力不放行。
5. 比免问线：小于等于就放行，否则问。用户同意后可以点「信任」，把生效级降一级记进账。

### 信任的账

键是工具名加一个规范化选择子：`command` 用命令原文，`web_fetch` 用域名，`write` 与 `edit` 用所在目录，其余用工具名加动作。只做精确匹配，不做前缀通配，否则信任了 `git` 就等于信任 `git push --force`。

存一个全局文件，键里带绝对路径，项目之间天然隔离。审批面板加一个信任按钮，设置页给一张能删的列表。

### 加第四级的条件

用户已定：full 就是对应 3 级，阈值写死为 3，不是「当前最高级」。

今天所有档位都在 3 以内，所以 full 看起来百无禁忌。以后加 4 级，只往档位表里加一行，4 级在 ask、auto、full 三种模式下都不通过，永远要问。删库跑路这种正好落在这里，这是有意的结果，不是漏洞。

前提两条，缺一条就变成改代码：

- 档位是整数，判定只有一句「级别小于等于阈值」，代码里不许按具体档位值分支。
- 阈值是配置项，值就是 3，不是枚举。

哪天要让 full 也放行 4 级，改的是阈值这个配置值，不是重做结构。

信任账要记目标档，不记降了几档。基础档以后调整时，生效档取「记录的档」和「基础档」里较小的那个，避免把一条 3 级命令误降到 1。

### 代价

- 精确匹配意味着命令换个参数就再问一次。
- 只读命令表要人维护，短了照样弹，长了容易漏。
- 命令判断不是安全边界，`npm run build` 里藏一句删除挡不住，它只负责减少无意义弹窗。
- 两个数比一个数多一个概念，换掉的是三张工具名名单和两套并行的判断。

## 取舍

### 能交给基础工具的

read、write、edit、command 这四项是底座，其余都问一句「能不能交给它」。

能直接交出去的是读取类的三个和 `check_exports`：`list_dir`、`search_files`、`search_content` 用 command 做同样的事，`check_exports` 就是一段静态分析脚本。

交出去要付代价的：`memory` 会丢掉索引刷新；`load_skill` 会丢掉技能目录解析；`list_processes` 与 `kill_process` 会丢掉会话归属。`web_fetch` 本来也在这一列，用户已定保留，见下一条。

`read_file` 传目录直接报错，所以三个读取类工具删掉后，列目录这件事要么落到 command，要么让 read 认出目录。这是删之前必须先定的一步。

### 记忆与资料库不合并

用户已定不合并。这一条记下理由，免得以后再翻。

`memory` 是 8 个动作、10 个参数，管 Markdown 记忆库，分项目档与全局档，每轮生成的索引注入提示词。`library` 是 6 个动作、6 个参数，管 SQLite 里的成果目录，条目指向文件，有分层与收藏。两个都是自动放行，权限上没有障碍，合起来是 14 个动作，两边都有 list，得靠前缀区分。

不合并的理由是对象不同：一个是「我记住的东西」，一个是「这个项目产出的文件」。记忆有全局档，资料库只有项目档，合成一个工具后容易把项目成果登记成全局记忆。省一个条目不值得多这个失败面。

`load_skill` 也不并入：它只有一个参数，是技能索引的唯一入口，输出是一整块提示词，调用频率高。技能索引里那句「Use load_skill」也得跟着改，18 个技能里有 5 个文件提到它。

### 技能工具的名字

问题是 `load_skill` 要不要改成 `skill`。判断是保持 `load_skill`。

「名字不齐」这个理由站不住：基础四项里 `read` `write` `edit` 本来就是动词，`command` 是名词，这批工具从来不是清一色名词。`load_skill` 是动词短语，跟 `read` 一脉，读起来就知道要干什么。改成 `skill` 反而要模型读描述才知道是加载，不是列表也不是管理。

改名只在一种情况下值得：把「读技能参考文件」也收进同一个工具，变成 `skill(action=load|reference)`。但现在 Python 侧不需要这个动作，`load_skill` 已经把技能目录带回来了，参考文件用 `read_file` 直接读。Rust 侧有 `read_skill_reference`，那是另一套运行时的事。

改名的账：仓库里 24 个文件提到 `load_skill`，含 4 个语言包、3 处配置、study 清单两处、Rust 与界面各一处，还有注入提示词里那句「Use load_skill only when the task matches a trigger below」。改动换不来任何行为变化。

### web 的去向

已定：保留，不交给 command，合成一个 web 工具，`action` 分 search 与 fetch。fetch 的可靠性是硬要求，行为一条不能退；search 尽力，外源本来就不稳。合并后按动作分档，search 1 级、fetch 2 级。

保留的理由记在这里，免得以后再争一遍。`web_fetch` 现在做四件事：目标地址与每一跳重定向都查内网、代理按应用配置走且不读环境变量、25MB 流式上限、HTML 正文提取与图片候选。换成 curl 这四样都要自己补，其中内网拦截防的是抓来的网页反过来指挥模型，不是防模型本身。

`web_search` 是多家引擎的解析加插件配置，不是一次 HTTP 请求，本来也不适合交给 command。

### 合并的硬约束

权限是按工具算的，不是按动作算的。`read_actions` 这个字段只有 `arrange` 声明过一次，没有任何代码读它，等于没有按动作分档。

所以合并只在同一权限档里干净：`write_checklist` 与 `update_checklist` 都是自动放行，`list_processes` 与 `kill_process` 都是自动放行，`sub_agent` 与 `sub_agent_message` 都是自动放行。

跨档合并会把审批一起改掉：`plugin_list` 与 `plugin_deps` 自动放行、`plugin_install` 要审批，合成一个要么放宽安装审批，要么把查询也变成要审批。`web_search` 与 `web_fetch` 是同一个毛病，但这一期两个都保留，不再作为合并候选。

MCP 两个工具是一个自动放行一个要审批，但按用户的方向执行走 command 之后，只剩一个查询动作，这条冲突自然消失。

### 对 MCP 的判断

合并的取向同意，但「最容易替换」这个说法要更正。真正最省事的是三个读取类工具，一行命令的事。MCP 不是技术上好换，是因为本机压根没配服务器，`mcp.json` 是空的，现在改它没有存量风险。

执行走 command 这件事只对带命令行的服务器成立。MCP 客户端是常驻子进程，先 `initialize` 再 `notifications/initialized`，之后按 id 收发 `tools/call`。一条 shell 命令做不到握手后调用再退出。真要执行，得有一个薄桥接脚本，那等于把工具藏进命令里。

### 合并的代价

合并省的是工具条目的数量，不省多少上下文，因为枚举值也占 token。代价是多一个用错动作的失败面，模型可能把查询动作传到写动作的字段上。所以只在同一对象上合并，不同对象之间不合并。

## 步骤

每一步先写验收测试再改实现，测试只跑本次相关的，不跑全量。

1. 权限内核。把三档枚举换成整数级别，判定改成五步，会话的两个数从模式推出来。这一步不动任何工具名，装配结果与今天一致。
   验证：新增单测覆盖五步顺序，0 级被信任也不能过，超上限拒绝且提示文案固定，信任降到 1 为止不再降。

2. 档位表与命令有序表。把现在的 ask 与 auto 迁进表，命令改成一张有序表，第一行沿用 `SHELL_STRUCTURE_RE`。
   验证：一张对照测试，同一批工具与命令在 ask、auto、full 三种模式下的最终判定与设计表逐条相等。只允许两处有意差异：auto 下 3 级仍要问，read_only 改由上限表达。

3. 删旧机制。删 `access_tools.jsonc` 的读取、`read_actions`、`arrange` 特例、`command_policies` 两档枚举、插件 Agent 的 `ask`/`auto`/`block`、`DEFAULT_TOOL_PERMISSIONS`。
   验证：全仓搜索这六个名字零引用；`arrange` 的 list 与 get 仍然不问；插件 Agent 声明的阈值仍然生效。

4. 信任账。持久化文件、面板信任按钮、设置页列表与撤销。
   验证：信任一次后重启应用仍不问；撤销后恢复问；账里最低记到 1；删掉账文件等于全部回到默认。

5. 工具去重。改名、合并、删掉两个检索工具，装配出 19 个。
   验证：装配结果的工具名正好是那 19 个；老名字调用返回明确的未知工具；合并后的工具动作按档位表分流。

6. 配置与提示词同步。`access_tools`、`loadtools`、study 清单、界面文案。
   验证：consider 模式与只读档在新名字下仍可用；study 白名单里的 `read_file` 已同步成 `read`，装配不报冲突。

7. web 合并。合成一个 web 工具，`action` 分 search 与 fetch。fetch 现有的内网拦截、代理分流、25MB 上限、PDF 转文本、图片候选逐条不回归；search 至少与今天等价。
   验证：fetch 的旧行为有回归测试且一条不改；search 用同一批查询对比结果条数；工具数组里只剩一个 web。

## 风险

- 工具数组按会话加压缩周期冻结在进程内存里。改完工具定义，正在进行的会话要压缩或新开会话才看得到。
- study 插件的 agent 白名单里写着 `read_file`、`list_dir`、`search_files`、`search_content`、`load_skill`、`web_search`、`web_fetch`。全改之后要同步成 `read`、`list_dir`、`load_skill`、`web_search`、`web_fetch`，去掉两个检索名，否则 study 虽然在范围外也会被打断。
- `access_tools.jsonc` 的只读档与 `loadtools.jsonc` 的 consider 模式都按名字列着 `search_files` 与 `search_content`，删这两个名字要一起改。`list_dir` 保留，不动。
- 两套工具定义同时在仓库里，Python 与 Rust 同名不同 schema。只改 Python 会留下两个口径。
- 两套插件系统都在装配链上，动插件工具要先确定走哪一套。
- 迁移期两套判定并存会短暂出现同一操作两种结果。切换要一次性完成，不长期并存。
- 信任账是全局单文件，删掉等于全部回到默认。这个可以接受，但设置页要写明。
- 档位表是新的维护面，命令那一列写错会把危险命令放行。改表要配一条测试。
