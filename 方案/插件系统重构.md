# 插件系统重构

## 需求与边界

### 要什么

插件是一个文件夹加一份清单。几十行能写一个，也能长成一套完整应用，中间没有分档，也没有插件类型字段。

基础能力六类：技能、工具、钩子、MCP、斜杠命令、上下文片段。

每个插件必须有配置面板。作者可以自定义样式，不定义就落到默认样式上。

界面四档全开：在固定位置加卡片按钮、往任意位置注入、接管整块区域、自带完整界面。插件代码和主界面在同一个页面里，不隔离。

插件可以整套接管 Agent：自己的系统提示词、自己的工具清单、自己的审批规则、自己的上下文拼法。同一时间只有一套生效。

生效范围由插件自己声明：一直生效、跟某个模式、跟某个会话。

完全开放第三方。应用内有市场，能搜索、安装、看版本、更新，同时支持压缩包和链接安装外部插件。

不做权限控制，不设沙箱，不做能力申请。

### 这次不做

插件权限模型和沙箱。用户已明确不需要。

密钥的处理方式。用户要求单独处理，当前搁置。

`create-plugin` 技能的提示词改写。等本设计定稿后单独做。

移动端。

### 推定

插件目录由用户和第三方共同写，宿主不做来源审核之外的任何代码检查。

插件可以弄崩界面，宿主只保证能恢复，不保证不出事。

## 设计原则

核心只做底座，其余全部可以插件化。

核心保留六件事：发现和加载插件、注册和替换管道节点、挂载界面区域和样式、装配六类基础能力、提供数据目录和日志、安全模式恢复。

别的都不进核心。管道替换之后的完整性校验、兼容性检查、冲突诊断、开发调试面板、市场浏览界面、写插件用的技能和模板，谁需要谁做成插件。

理由很简单。任何保障一旦写进核心，就变成核心必须维护的规则，也就变成对插件作者的限制。放进插件里，作者不满意可以换掉，甚至可以写一个更好的。

这条原则有个副产品：管道完整性校验本身就是一颗插件的好样板，它要读模块清单、找缺失的导出、报结果，正好把覆盖层的接口完整用一遍。所以第一颗新增内置插件就可以是它，用来证明校验也是插件。

## 设计

### 1. 一个插件就是一个文件夹

```
hello/
  plugin.json          必须有
  main.py              可选，后端代码
  tools.jsonc          可选，工具声明
  skills/              可选，技能目录
  hooks/hooks.json     可选，钩子
  mcp/mcp.json         可选，MCP 配置
  context/rules.md     可选，要拼进上下文的东西
  config/schema.jsonc  可选，配置字段
  ui/main.js           可选，界面代码
  ui/panel.js          可选，自定义配置面板
  data/                运行时生成，更新时保留
```

除了 `plugin.json`，没有任何必需文件。放什么就有什么本事。

### 2. 清单

最小的插件就两行：

```json
{ "name": "hello", "version": "0.1.0" }
```

完整形态长这样，字段全部可选：

```json
{
  "name": "diary",
  "version": "1.0.0",
  "description": "自动写日记",
  "scope": "mode",
  "engine": {
    "runtime": "python",
    "python": ">=3.14,<3.15",
    "app": ">=0.4",
    "platform": "windows-x64"
  },
  "skills": ["./skills"],
  "tools": ["./tools.jsonc"],
  "hooks": ["./hooks/hooks.json"],
  "mcp": ["./mcp/mcp.json"],
  "commands": [
    { "name": "diary", "title": "打开日记", "operation": "diary.open" }
  ],
  "context": [
    { "file": "./context/rules.md", "order": 30 }
  ],
  "config": {
    "schema": "./config/schema.jsonc",
    "panel": "./ui/panel.js"
  },
  "ui": {
    "styles": ["./ui/thinking.css"],
    "regions": [
      { "region": "right", "order": 20, "blocks": [ ... ] },
      { "region": "main", "mode": "diary", "entry": "./ui/main.js" }
    ],
    "script": "./ui/main.js",
    "windows": [
      { "id": "pet", "title": "日记", "entry": "./ui/window.html", "width": 420, "height": 620 }
    ]
  },
  "agent": {
    "mode": "diary",
    "prompt": "./prompt.md",
    "tools": ["read_file", "write_file", "diary_write"],
    "approval": "ask",
    "context": ["..."],
    "exclusiveTools": true
  },
  "operations": ["./operations.jsonc"]
}
```

没有 `type` 字段，没有 `level` 字段，没有轻和重的开关。填了多少就装多少。

### 3. 六类基础能力

| 类别 | 怎么写 | 装上去之后 |
| --- | --- | --- |
| 技能 | 一个装 `SKILL.md` 的目录 | 模型的技能索引里多一条，按需加载 |
| 工具 | `tools.jsonc` 加一个 Python 函数 | 模型能调用，按声明的权限走审批 |
| 钩子 | `hooks/hooks.json` | 在指定事件前后插一脚，能看能改能拦 |
| MCP | `mcp/mcp.json` | 外部服务的工具进模型工具列表 |
| 斜杠命令 | 清单里的 `commands` | 输入框打 `/xxx` 就能触发 |
| 上下文片段 | 清单里的 `context` | 一段文字或一个 md 文件进系统提示词 |

六类都是声明就生效，不需要写界面。

### 4. 配置面板

必填，不允许没有。三种情况：

只有名字和版本，宿主自动生成一个面板，显示名字、版本、描述，没有可填项。

写了 `config.schema`，宿主生成表单，控件有文本、数字、开关、下拉、数组、目录扫描、模型选择。

写了 `config.panel`，宿主给一块空地方和一套取值存值的接口，作者自己画。

密钥字段默认打码，提交掩码或空值保留原值。具体规则等密钥那一项定下来再补。

### 5. 界面

#### 5.1 宿主提供哪些位置，现在那里放的是什么

| 区域名 | 现在放的是什么 |
| --- | --- |
| `appRail` | 最左边的常驻导航条 |
| `left` | 会话和项目列表，顶上有新建、搜索、设置入口 |
| `titlebar` | 会话标题，能改名；整版界面时换成返回按钮和标题 |
| `main` | 聊天消息列表；整版界面时换成搜索、资料库、定时任务、设置；插件模式时换成插件页面 |
| `right` | 右竖栏，现在六个模块：清单、资源、子代理、联网搜索、后台进程、RAG |
| `composer` | 输入框、命令菜单、附件区、发送按钮 |
| `composerSide` | 输入框右边那排工具按钮 |
| `message` | 每条消息一行，里面分思考、工具调用、结论几段 |
| `settings` | 设置页里每颗插件一张卡片 |

这些位置不是新造的，对应的是现有 `WorkspaceShell` 里已经存在的插槽，还有 `MessageView` 里的消息段。插件挂上去之前那里已经有内容，插件挂上去之后怎么处理，看下一节。

#### 5.2 插件内容和原有内容是什么关系

默认是追加。原内容不动，插件内容按 `order` 插进去。同一个位置有多个插件时按 `order` 排，`order` 相同按名字排。

只有显式写 `replace: true` 才隐藏原内容。这是给重插件用的，比如写作插件要整个换掉聊天列表。样式插件永远不该用它。

只改外观不改结构，走样式层，不动区域。

#### 5.3 三种写法，从轻到重

样式层 `ui.styles`，只给 CSS，宿主把它注入成一张样式表。改颜色、字体、间距、圆角、动效都走这条，不写 JS，不碰区域。

注入方式是用 link 标签加载，不是往页面里塞一段 style 文本。因为插件目录里的图片、字体要用相对路径引用，只有 CSS 本身是一个 URL 的时候相对路径才成立。所以宿主必须提供一条插件资源路由，把插件目录映射成 URL，比如 `/api/core/plugins/<名字>/assets/<路径>`，并且限制在这个插件目录里面。

背景这类东西有一个前提要写进约定：主界面的背景色只能由样式表控制，不能用内联样式或者 `!important` 写死，否则插件盖不掉。

声明式内容 `regions[].blocks`，说说要什么，宿主帮你画。支持文字、状态、指标、列表、进度条、按钮。按钮点了调一个 operation。

自绘内容 `regions[].entry` 和 `ui.script`，给 JS，宿主插入 script 标签，在区域里放一个空盒子，插件自己往里画。因为不隔离，插件也能直接拿 `document` 去改别的地方。

#### 5.4 挂点名，插件靠这个定位

插件要改某个已有元素，不能靠内部 class，因为内部 class 随时会改。宿主保证一批 `data-` 属性跨版本不变，这就是契约。

| 挂点名 | 挂在哪 |
| --- | --- |
| `data-region="main"` | 每个界面区域的外层，名字和 5.1 那张表一致 |
| `data-part="reasoning"` | 思考块 |
| `data-part="tool"` | 工具调用 |
| `data-part="conclusion"` | 结论 |
| `data-role="user"` 和 `data-role="assistant"` | 消息行 |
| `data-session-header` | 会话标题 |
| `data-right-rail-module="id"` | 右栏每个模块 |

现在代码里只有 `data-part-id`，是每个消息段的唯一编号，没有按类型挂的名字。这批属性要新加，并且写进文档当成对外承诺。

#### 5.5 例子一：控制思考样式

整个插件三个文件，不到二十行。

`plugin.json`：

```json
{
  "name": "thinking-style",
  "version": "1.0.0",
  "ui": { "styles": ["./thinking.css"] }
}
```

`thinking.css`：

```css
[data-part="reasoning"] {
  border-left: 2px solid var(--blue);
  font-size: 13px;
}
[data-part="reasoning"] .reasoning-duration { display: none; }
```

装上去就生效。不需要重绘界面，不需要禁用原有组件，也不需要去 GitHub 翻源码。挂点名是公开的，改样式就是写 CSS。

如果还想加交互，比如点一下折叠全部思考，再补一个 `ui.script`，用 `document.querySelectorAll('[data-part="reasoning"]')` 找到它们，加按钮、加事件。

#### 5.6 例子二：把聊天区背景换成一张图片

三个文件。

`plugin.json`：

```json
{
  "name": "chat-wallpaper",
  "version": "1.0.0",
  "ui": { "styles": ["./wallpaper.css"] }
}
```

`wallpaper.css`：

```css
[data-region="main"] {
  background-image: url("./bg.jpg");
  background-size: cover;
  background-position: center;
  background-repeat: no-repeat;
}
```

`bg.jpg` 和 CSS 放同一个目录。宿主按插件资源路由加载 CSS，`url("./bg.jpg")` 就解析到插件自己的目录里，图片能出来。

有两个真实的坑要写进约定。

主界面现在有一层不透明底色，来自 `--theme-main-background`，挂在 `.workspace-main` 上。插件样式在 Core 样式之后加载，同优先级能盖住。所以约定是主界面的背景只能由样式表控制，不能内联写死，也不能加 `!important`。

消息列表 `.thread` 顶部有一段渐变遮罩，图片如果挂在消息列表上会被吃掉一截。所以挂点是外层的主界面，不是消息列表。输入框也在同一个区域里，图片会一起铺到输入框底下，不想要就自己再给输入框补一层背景。

#### 5.7 独立窗口

`ui.windows` 声明一个真正的桌面窗口，加载插件自己的 HTML。窗口和主界面同源，能直接调 Core 的接口，也能通过宿主注入的桥接对象跟主界面互相发消息。桌宠重做后就落在这里。

### 6. Agent 接管

`agent` 段声明四件事：提示词文件、工具白名单、审批规则、额外上下文。

声明了提示词，就整段替换 Core 的系统提示词，不是追加。

声明了工具清单，就只给这些工具，没声明就是全部。不做“只换提示词但沿用别人的工具”这种混合。

审批规则三档：每次问、全部放行、全部拦截。也可以指向一个规则文件，按工具名分别设。

同一时间只有一套 Agent 生效。优先级从高到低：会话指定、模式指定、全局指定、Core 默认。

### 7. 生效范围

清单里的 `scope` 三选一。

`global`，启用就一直生效，工具、上下文、界面都挂上去。

`mode`，只有切到它声明的模式时才接管界面和 Agent，切走恢复原样。study 和 workflow 属于这一档。

`session`，插件创建自己的会话，只在那些会话里生效，其他会话看不到它。

#### 7.1 生效时机

声明层每轮重新读，但模型看到的东西按压缩周期冻结。这是两件事，不能混。

每轮装配时，工具声明、技能、钩子、MCP、命令、上下文、配置、Agent 声明都会被重新解析。但请求顶部的内容不会跟着变。

系统提示词类，包括 instructions、上下文片段、技能索引、MCP 服务器列表，冻结在会话元数据里。改了之后只会追加一条尾部通知，告诉模型哪一块变了。要真正换到顶部，得开新会话，或者等一次上下文压缩。重启不重建这一块，因为冻结的原文存在会话状态里。

工具数组单独冻结，按会话加压缩周期，缓存在进程内。冻结期内调用新工具，会返回「当前工具组未更新，工具数组将会在压缩或新会话更新。」重启后端会重建工具数组，因为缓存只在进程里，但不会重建系统提示词。

钩子、斜杠命令、配置不在冻结范围内。钩子每轮重新加载，命令和配置在界面侧读取，改了就是新的。

代码层启动时决定。后端模块覆盖、前端模块覆盖、后端插件进程，都在启动时装配好，运行中不换。改了这些要重启。打包版重启整个应用，开发版只重启后端进程，前端走 Vite 热更新。

所以准确说法不是「下一轮生效」，而是：装配在下一轮生效，模型看到的提示词和工具列表要等压缩、新会话，工具数组额外可以靠重启刷新。

### 8. 上下文拼接

清单里的 `context` 每项是 `{ file, order }`。宿主在加载插件时把 `file` 相对插件目录解析成完整路径，然后并进现有的上下文配置，不另造一套。

排序先看 `order`，`order` 相同再看文件名首字母。序号不移动，作者写多少就是多少。

现在的 `load_context.jsonc` 里 `addition` 的条目只按工作区根解析，这次要放开到插件目录。

### 9. 数据与日志

插件目录下的 `data/` 是持久区。更新插件时只替换代码和资源，`data/` 原样保留。

作者可以在清单里声明把数据放到外部目录，默认就是 `data/`。

日志写 `data/logs/`，每个插件一份。推荐作者自己写日志，宿主只保证目录存在。

### 10. 安装、市场、更新

#### 10.1 宿主自带什么，插件声明什么

不为了一颗插件改打包策略。宿主只公布一张固定的环境清单，够了就装，不够就不装。

| 环境 | 我们自带 | 插件能拿到的 |
| --- | --- | --- |
| Python | 3.14 解释器，冻结在应用里 | 进程内 import，自带标准库和打包进去的依赖 |
| WebView | 桌面窗口自带的浏览器内核 | 编译好的 JS 模块，跑插件前端 |
| 原生 | 能运行可执行文件，没有编译器 | 作者自己编译好的二进制，宿主负责启动它 |

我们没有 Node、没有 rustc、没有 C 编译器。所以插件写「我用 Rust 写的」没有意义，写「windows-x64 的原生二进制」才有意义，因为宿主不负责编译，只负责运行。

所谓冻结，是 PyInstaller 把 Python 3.14 解释器、标准库和我们用到的依赖一起打进一个文件夹，随应用分发。用户机器上不需要装 Python，也看不到一个能随便用的 python 命令。代价是往这个环境里装新包很麻烦，pip 不一定可用，我们也不打算为插件改打包。

所以 Python 插件的第三方依赖自己带。插件目录里放一个 `vendor/`，宿主加载插件时把它加到 `sys.path` 前面。纯 Python 包直接放进去，带 C 扩展的包要按 3.14 和 windows-x64 编译好。宿主不跑 pip，也不改自己的环境。

安装时检查插件声明的依赖能不能 import。宿主自带的算通过，`vendor/` 里的算通过，都没有就提示缺哪个包，不阻止安装。插件清单里可以写 `"dependencies": ["httpx"]` 这样的声明，只用于检查，不触发安装。

插件在清单的 `engine` 段声明自己要什么：

```json
"engine": {
  "runtime": "python",
  "python": ">=3.14,<3.15",
  "app": ">=0.4",
  "platform": "windows-x64"
}
```

宿主安装时逐条比对，不满足就不装，并说清是哪一条不满足。不写版本约束就是放弃兼容保证，风险作者承担。

#### 10.2 以声明为准，检测只用来提醒

自动检测能做，但不能当依据。同一个 `.py` 可能是入口也可能是数据，同一个 `.exe` 可能是插件本体也可能是个辅助工具。所以安装时以 `engine` 声明为准，检测只做一致性提醒：声明了 Python 却没看到 `.py`，声明了原生却没看到二进制，就在插件页给一条提示，不阻止安装。

#### 10.3 本地管理优先

这一版只做本地管理。装、卸、启用、禁用、更新、看状态，全部在本地完成，不依赖任何外部服务。

安装来源三种：本地文件夹、本地压缩包、链接。三者走同一条流程：校验、解压到插件目录、读清单、比对环境、检查依赖、装配。

更新只替换代码和资源，`data/` 保留。装完插件重新起一遍。

卸载删目录，问一句要不要连 `data/` 一起删。

市场只留接口，不做深。索引格式先定下来：名字、版本、描述、作者、兼容的宿主版本、环境要求、下载地址、校验值。来源有两个，自建服务器和 GitHub Release，客户端实现放到以后。本地管理整明白之前，市场不接。

### 11. 冲突规则

一条原则：能排序的排序，不能排序的拒绝，交给用户选。不做隐式的先装赢。

工具重名：核心工具名保留，插件不能用核心工具名，报了就不加载。插件之间重名，后装的拒绝加载，插件页显示冲突。

命令重名：后装的拒绝加载，插件页显示冲突。

模块覆盖：同一个模块只能一个插件接管，第二个拒绝加载。

区域冲突：同一个区域允许多个插件追加，按 `order` 排，`order` 相同按名字排。声明 `replace` 的区域只能有一个接管者，第二个拒绝。

Agent 冲突：按会话、模式、全局、Core 默认分四层。同一层只能有一个生效，第二个拒绝加载并显示冲突。

上下文冲突：按 `order` 加文件名排序，永远有确定结果，不需要用户选。

### 12. 坏了怎么办

启动时可以带一个安全模式参数，跳过所有插件，只起 Core。

连续两次没正常退出，启动时提示上一次是插件导致的，并列出可跳过的插件。

每个插件一份日志，出错能看到是谁。

因为不隔离，界面被插件弄崩是可能的。设计上不防止，只保证能回到干净状态。

### 13. 覆盖层，把运行时看成模块图

Sunday 的运行时是一张管道图，图上的每个节点是一个模块，模块之间靠导入相连。插件可以拆掉任意模块，换上自己的实现。

插件只声明一件事：我接管哪些模块，每个模块用哪个文件。

```json
"overrides": {
  "ui/src/components/streamingTextFade.ts": "./overrides/streamingTextFade.js",
  "lamtools_core.prompt": "./overrides/prompt.py"
}
```

前端写模块路径，Core 在返回页面时生成 import map，把那个模块指向插件的文件。后端写模块名，Core 在导入任何 `lamtools_core` 子模块之前装一个导入查找器，命中就从插件目录加载。

两边同一个规则：启动时决定，运行中不换。

宿主只做两个检查：模块名在清单里，文件能加载。除此之外一概不管。不校验版本，不校验导出是否齐全，不要求作者声明丢了什么。

拆掉一个模块，导入它的地方会在启动时报错，错误明确落在哪个导入上，不会出现改一半生效。作者要么把导出补齐，要么接受启动失败。

后端模块加载失败会阻断启动，前端的表现是页面起不来。两种都是有意的，安全模式可以跳过所有插件，先让 Core 起来。

冲突只有一条规则：同一个模块只能有一个插件接管，第二个拒绝加载，插件页显示冲突，用户自己选。

这件事不再加任何别的东西。没有版本契约，没有能力声明，没有兼容矩阵，没有自动修复。这是最底层、最直接的手段，责任和后果都在作者那边。

这条要写进 `create-plugin` 的提示词：覆盖等于拆掉一个模块，导入不回来是你的事，宿主只保证启动时报错、日志里能看出是谁。

### 14. 完备性边界

先把问题拆成两个。一个是插件能不能算出任何东西，一个是插件能不能替换任何行为。第一个是语言问题，Python 和 JS 都图灵完备，答案是能。第二个是架构问题，答案是取决于图里有多少模块。

完备性等于模块覆盖度。凡是落在图里某个模块上的行为，插件都能换。不在模块里的，换不了。所以「万能」不是一句口号，是一条可以检查的约束：任何影响用户体验的行为，都必须经过某个管道节点。

内核不可替换，只有四样：插件加载器、模块清单本身、安全模式入口、日志。这四样如果也能换，一颗坏插件就能让应用再也起不来。这是唯一的例外，也是恢复能力的来源。

打包版和开发版的差别要说清楚。

后端，冻结包里照样能换。覆盖发生在导入之前，模块由查找器从插件目录加载，所以 `from 模块 import 函数` 拿到的也是插件的函数，不存在旧引用的问题。这条在开发版和打包版完全一样。

前端，打包之后模块被编译进闭包，直接改模块内部函数做不到。但整块换模块可以做到：构建时保留模块边界，每个源文件一个模块文件，启动时用 import map 把指定模块指向插件的文件。import map 必须在任何模块加载之前生效，所以由 Core 在返回页面时生成。这套机制在开发版和打包版都成立，前提是构建配置改成保留模块。第三方依赖仍然打包，不参与替换。

源码级覆盖，也就是直接替换一个源文件，只在重新构建时成立。打包版不重新构建就没有这条路。所以要求「改任意源码」的场景，答案是另外做一份构建，不是运行时插件。

完备性的验收方式：把运行时的行为列一张表，逐项标它落在哪个模块。找不到归属的，要么拆成模块，要么明确写进内核。这张表就是这套架构的自由度清单，也是它不图灵的地方。

### 15. 管道图怎么来

标注成本是零，两边都不需要。

后端不需要任何标注。插件在清单里写模块名，比如 `lamtools_core.prompt`。Core 在导入任何 `lamtools_core` 子模块之前装一个查找器，命中就从插件目录加载。模块名就是路径，不需要一张手写的图。启动时把 `lamtools_core` 下的模块名列出来，给插件页和 `create-plugin` 看，这份清单是算出来的，不是维护的。

前端也不需要标注，办法是换整个模块。构建时保留模块边界，每个源文件产出一个模块文件，名字就是路径。启动时 Core 生成一张 import map，把插件声明要顶掉的模块指向插件的文件，浏览器加载到那个模块时自然就用插件版本。源码里一行标记都不用写。

这条路的代价有三个。粒度是模块不是函数，想改一个函数也要把同模块其他导出一起带上。构建配置要改成保留模块，产物从一两个大 chunk 变成一堆小文件，本地加载没问题。装完插件要重载界面，因为 import map 在模块加载前就定了。

如果不想改构建，退路才是构建时包装导出函数。那条路风险高，Vue 组件、类、特殊方法、异步生成器被包一层容易坏，堆栈变深，不推荐。

为什么不用扒 GitHub。名字就是路径，运行时自己找得到，扒源码只会引入版本漂移。原先是怕「不知道有哪些函数」，现在这个问题由反射和模块路径解决了。

行为表也可以自动生成：后端遍历反射结果，前端把模块清单导出来，合成一份，标出哪些行为可替换、哪些在内核里。这份表随版本发布，插件页能查，`create-plugin` 也读它。

#### 15.1 现状的粒度

后端 263 个 Python 文件，中位数 223 行，超过 1000 行的 28 个，超过 2000 行的 12 个。最大的五个是 `live_operations.py` 7367 行、workflow 的 `runtime.py` 6332 行、`cli.py` 6256 行、`kernel/loop.py` 4940 行、`default_agent.py` 3678 行。这五个占后端代码约两成。

前端 224 个文件，中位数 178 行，超过 1000 行的 15 个，超过 2000 行的 5 个。最大的五个是 `CoreSettings.vue` 5257 行、`LamToolsApp.vue` 4901 行、`MessageView.vue` 4512 行、`ChatThread.vue` 2221 行、`appServer/store.ts` 2050 行。这五个占前端代码约两成。

所以整体粒度不粗，中位数很小，绝大多数模块可以整块换。问题在尾巴：插件最想动的正好是最大的几个文件。为了改一个思考块的样式去接一个 4500 行的文件，不现实。

决定：统一走模块级替换，不为个别文件另开函数级通道。这几个巨型文件的拆分单独作为一次前端重构，由用户择期安排，不进本方案的实施步骤。在那之前，它们就是粗粒度节点，插件要么整块接，要么用样式层和 DOM 改外观。

### 16. 兼容其他插件生态，可选

不做代码级兼容。

以 DSH 为例，按它当前的文档：一个 DSH 插件等于一个 cordis 插件加 `package.json` 里的 `dsh` 字段，没有单独的清单文件。它跑在 Node 进程内，靠 cordis 做依赖注入和生命周期，用 `inject` 静态声明要哪些服务，形态上分 bundle 插件和仓库插件，双面插件还有一半跑在浏览器里。安装走 pnpm，bundle 装完要重启。

所以 DSH 插件不是能独立运行的东西，它必须挂在一个 cordis 宿主上。要兼容它的代码，等于把 Node 和 cordis 一起搬进来，那是另一个项目，不是适配器能解决的。

资产级适配能捞到的东西也有限。DSH 的插件以代码插件为主，工具是用 `ctx.tools.register` 在代码里注册的，不是一份静态清单。只有那些纯资产的插件才翻得动。

真要做生态兼容，唯一现实的路径是起一个 Node 边车，在里面跑一个 DSH profile，把它的工具通过 MCP 或 JSON-RPC 桥过来。这件事和本方案无关，也不阻塞前面十五节。

#### 16.1 如果真要做，工作拆成四块

运行时。打包一个 Node，或者要求用户自己装。起一个子进程，跟应用一起启动和退出。

宿主。用官方的 `@deepseek-ai/cordis` 起一个 app，把插件的 `apply(ctx, config)` 跑起来。插件的 `inject` 声明了哪些服务，就得提供哪些。`tools` 必须真做，其他先给桩，桩不满足就报错禁用，不能假装兼容。

桥接。截住 `ctx.tools.register`，把名字、描述、参数 schema、execute 映射成我们的工具声明和调用。参数和返回值要做双向转换。

生命周期。启动、停止、崩溃隔离、日志、跟着插件启停走。

最小可用版本只做工具类插件：Node 边车加官方 cordis，只实现 `tools` 服务，只桥接工具注册。这一块覆盖 DSH 插件里最有价值的一类，估计三到六周。

不含 UI 半边。`dsh.client` 依赖 DSH 自己的前端启动协议和 `window.__DSH_BOOT__`，要支持得另写一层，或者 iframe 加假 boot map，工作量另算。

不含 bundle 的 patch 语义。要支持 bundle 插件，得实现 `cordis.patch.yml` 的 insert 和 override 规则，再加一到两周。

代价是分发里多一个 Node，几十兆；多一套依赖树要维护；DSH 的接口一变就要跟着改。收益是三百多个社区插件里能用的那一部分。

#### 16.2 用 skill 复刻，替代运行时兼容

结论：可行，而且比运行时兼容划算。

做法是一颗技能。输入是一个外部插件的仓库或者包名，输出是一个我们自己的插件。

步骤是固定的：取源，读清单、README 和入口代码；判定类型；列出它注册了哪些工具、用到了哪些服务、有哪些配置项；逐项映射到我们的六类能力；生成骨架；跑验收；给一张差异表。

为什么可行。我们要的是能力，不是它的代码。绝大多数插件的价值集中在几个工具上，用我们的工具通道重写一遍，比搬一个 Node 运行时便宜得多。产出还是原生的，配置、权限、日志、界面全用我们自己的机制，不需要维护两套运行时。

边界要写清楚。UI 类插件复刻不了原样，只能做等价功能或者跳过。依赖 DSH 专有服务的插件要看我们有没有对等物，没有就列进差异表。源码被压缩或混淆的插件，只能按 README 和行为描述复刻，差异要如实写。

许可是硬要求。按行为复刻，不逐行抄。技能里要求先读 LICENSE，遇到不允许衍生的直接停，只输出差异说明。

和 `create-plugin` 的关系：这颗技能不重复清单规则和模板，只做分析、映射和差异表，生成部分复用 `create-plugin` 的东西。它是薄薄一层。

## 取舍

**不隔离。** 用户明确选择。插件能直接改界面，代价是坏插件能弄崩界面。换来的是插件写界面不需要学一套 API，也不需要宿主维护沙箱。

**不分轻重大小两套。** 一套清单一套装配。复杂度的差别来自作者填了多少，不来自宿主的分档。

**界面只有两种画法。** 声明式和自绘式，加一个全局脚本。没有插槽 DSL，没有组件协议，没有样式主题系统。区域名单是有限的，名单之外靠全局脚本。

**Agent 整套替换，不做逐项混合。** 避免半套提示词配半套工具的怪状态。

**序号不移动。** 同号按文件名排，保证作者声明的序号永远算数。

**git 插件删掉。** `run_command` 就能做，留着只是多一个要维护的工具。

**工具默认不做成独立工具。** 先用 skill 加命令或脚本。只有三个条件同时成立才做独立工具：需要绕过命令的最高权限管控、调用频繁、需要严格定义返回结构。

**覆盖层不做兼容保证。** 宿主只保证能加载、能卸载、能报冲突，不保证拆掉模块之后功能完整。怎么接回去是作者的事，写进 skill。不要求作者声明输入输出，也不校验他接得对不对。

## 步骤

1. 清单与装配内核。读得懂最小清单，能装、能禁用、能卸载，插件页能看到它。验收：放一个只有名字和版本的文件夹进去，插件页出现；禁用后消失，文件还在。

2. 六类基础能力。六样各自声明后都能观察到。验收：一个插件同时声明六样，六样都生效；关掉插件后六样全部消失。

3. 界面接入。区域名单、追加与替换两种关系、声明式内容、自绘内容、样式层、挂点名、全局脚本。验收：一个只带 CSS 的插件能把思考块改成另一种样子，不写一行 JS；一个插件在右栏加卡片；一个插件用 `replace` 把主内容区换成自己的页面。

4. 覆盖层。后端在导入前按模块名替换，前端按模块路径做 import map 替换，同时产出一张行为表，逐项标注行为落在哪个模块。验收：写一个只替换流式淡入模块的插件，装上去流式输出从淡入变成粒子，卸载后恢复；再写一个只替换一个后端模块的插件，确认 from 模块 import 函数的调用方也拿到插件版本；故意删掉一个导出，确认启动时报错并写进日志。

5. 窗口。任意插件能开独立窗口，窗口能调 Core 的接口、能和主界面互发消息。验收：桌宠重做版能开窗、能拖、能调一个 operation 拿到结果。

6. Agent 接管。提示词、工具白名单、审批、上下文四项生效。验收：切进插件模式后系统提示词整段变了，工具只剩声明的那些，切走完全恢复。

7. 配置面板。默认面板、自定义面板、必填校验三件事。验收：只有名字和版本的插件有默认面板；自定义面板能改样式，存的值重进还在。

8. 数据与更新。`data` 保留、日志分离、更新替换。验收：日记插件写三条日记，更新到新版本，三条日记还在。

9. 本地安装与更新。本地文件夹、压缩包、链接三种来源，环境比对，依赖检查，安装、更新、卸载、启用禁用。市场客户端不做。验收：从本地压缩包装一个，更新到新版本数据还在，卸载时能选择保留数据；换一个声明了宿主没有的环境的插件，安装被拒绝并说明是哪一条不满足。

10. 内置插件重写。七颗按处置表重写，git 删除。验收：每颗在新系统上跑通它对应的样板场景；模块校验器能找出一颗故意少导出的插件，报出哪个导入断了。

11. `create-plugin` 提示词重写。验收：用它生成一个最小插件，不手改就能装上用；提示词里包含什么时候做成工具、什么时候用 skill 加命令，以及覆盖模块之后后果自负这条规则。

12. 插件复刻技能。写一颗 `port-plugin` 技能，输入外部插件的仓库或者包名，输出我们的插件加差异表。验收：挑三个 DSH 插件，一个工具类复刻后能直接跑通，一个 UI 类能给出等价方案或明确拒绝，一个依赖专有服务的能把缺口列全。技能先读 LICENSE，不允许衍生就只输出差异说明。

## 目标与完成判据

目标：让第三方能写从几十行到完整应用的全谱插件，宿主只提供一份清单和一套装配，不做权限、不做隔离。

完成判据：

一个从来没用过这套东西的人，照文档能在一小时内写出一个能装的插件。

study 和 workflow 在新系统上跑起来，且代码里不再有专门为它们写的特例分支。

一个插件更新之后，它的数据还在。

一个插件把界面弄崩之后，能用安全模式起回来。

行为表里每一项都有归属，要么是模块，要么是内核，没有漏网的。

## 风险

不隔离加完全开放第三方，意味着任意插件都能改界面和 Agent。这是明确接受的选择，风险落在用户身上，症状是装到坏插件后界面崩掉。缓解只有安全模式和日志。

插件抢同一个区域或同名工具时，冲突规则可能不够用，尤其多个重插件同时启用。

提示词整套接管后，不同插件的体验差异会很大，用户可能分不清现在是哪个身份在说话。现在没有统一的身份提示设计。

study 和 workflow 依赖大量现有能力，重写工作量大，且它们的功能边界本身还不确定。

市场本版不做，只留索引格式。审核、评分、自动更新要等市场开始做才有意义。

打包版没有源码级覆盖。想改一个没被做成可替换节点的行为，只能改源码重新构建。所以插件作者遇到的第一道墙不是能力，是可替换名单够不够长。
