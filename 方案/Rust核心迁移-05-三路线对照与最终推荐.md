# 三条路线对照与最终推荐

前置：`方案/Rust核心迁移-03-目标架构独立推导.md` 定义目标，`方案/Rust核心迁移-04-现有Rust-Core架构质量审计.md` 提供现有代码的度量。

本文只做一件事：在同样目标下，比较三条路线的未来总成本与风险，然后给出一个明确推荐。

---

## 1. 评分框架

权重按"未来三年这件事有多要紧"定，不按"做起来有多爽"定。

| 维度 | 权重 | 为什么这个权重 |
|---|---|---|
| 正确性与可靠性 | 25% | 需求里最硬的门槛全在这，幂等、未知态、恢复、权限 |
| 维护成本 | 20% | 单人长期维护，这是决定项目能不能活下去的主因 |
| 未来功能实现难度 | 20% | 需求明确要求持续演进，不能做一次就锁死 |
| 修改影响范围 | 15% | 决定每次改动的心理成本与实际风险 |
| 跨平台复用程度 | 10% | 双端共用是核心目标之一 |
| 测试与调试成本 | 5% | 影响迭代速度但可通过纪律补偿 |
| 迁移期风险 | 5% | 一次性成本，但要防止迁移中途烂尾 |

---

## 2. 三条路线的定义

**路线 A：就地修复并改造现有 Rust Core。**
保留 `runtime-rs` 作为唯一 crate 与 `lib.rs` 作为契约，逐步改造成目标架构。原地把 `RuntimeError` 换成枚举、给审批加参数摘要与过期、把回合状态接上存储、把 Study 与 Workflow 抽出去、修掉 Python 路径耦合、拆 Provider。

**路线 B：重新设计一个最小但完整的 Rust Agent Core。**
新写一个核心，不带任何现有代码。目标架构按 `03` 号文档落地。现有 Rust Core 整体废弃，产品功能要么重写要么暂时下架。

**路线 C：保留经过验证的优秀模块，重建其余架构。**
先按 `03` 号文档定义新核心契约，核心四件全部新写。然后把现有代码按 `04` 号文档的 A、B、C 三类处理：A 类原样搬走，B 类改签名接入，C 类丢弃。产品域独立成 crate，不进核心。

## 3. 成本模型与依据

### 3.1 实测锚点

这不是拍脑袋。我在隔离目录写了一个参考原型并跑通测试：

| 项 | 实测值 |
|---|---|
| 生产代码行数 | 793 行 |
| 测试代码行数 | 227 行 |
| 测试数量 | 10 个，全部通过 |
| 编译时间 | 8.59 秒，含 SQLite 从源码编译 |
| 直接依赖 | 3 个（rusqlite、serde、serde_json） |
| 传递依赖 | 32 个 |

原型覆盖的能力：命令幂等、事件序号单调、工具阶段机、非幂等结果未知、幂等重排队、审批参数绑定、审批过期、审批一次性、取消、队列、完整回合写日志。

**这说明目标架构里"最难的那部分"在 1 千行以内可以做出来并且可测。** 这是 C 与 B 的核心成本可以被压低的依据，也是 A 路线"改比写贵"的判断基础。

### 3.2 成本换算口径

统一换算成"等效新写行数"，便于横向比较。换算规则：

- 新写 1 行 = 1.0
- 原样搬走 1 行 = 0.05，只需移动与接线
- 改签名接入 1 行 = 0.33 到 0.50
- 修 bug 式改造（要理解旧结构再改）1 行 = 0.5 到 0.8

后两条系数没有实测，属于估计，置信度中等。这是本报告最大的不确定来源，我在第 8 节单独标注。

### 3.3 现有代码的分类基数

来自 `04` 号文档第 13 节，已核对无重复：

| 类别 | 行数 | 占比 | 内容 |
|---|---|---|---|
| A 类可原样搬 | 10,297 | 33.0% | hooks 923、profiles 851、forensics 513、study_notes 2,185、study_exams 1,955、workflow_document 2,435、workflow_store 774、workflow_data_packet 661 |
| B 类改签名可复用 | 17,300 | 55.5% | provider 4,493、study 3,607、workflow_ops 1,472、sub_agent 1,108、其余工具与扩展 |
| C 类必须重写 | 3,583 | 11.5% | lib 2,388、plugin_catalog 474、update_manifest 388、tool_catalog 333 |

## 4. 逐维度对照

### 4.1 正确性与可靠性，权重 25%

| 路线 | 分 | 理由 |
|---|---|---|
| A | 2 | 12 条不变量要一条条塞进一个 60% 代码都依赖的契约里。每塞一条都要保证 16 个模块同时编译通过。中途出现"一半新一半旧"的状态是大概率事件，而那个状态最难验证 |
| B | 5 | 新结构从第一天就带全部不变量，没有旧状态干扰 |
| C | 5 | 同 B，核心是新写的，不变量在同一份契约里一次到位 |

A 的失分不在能力，在过程。它要求在一个强耦合系统里做 12 次外科手术，每次都全量验证。

### 4.2 维护成本，权重 20%

| 路线 | 分 | 理由 |
|---|---|---|
| A | 2 | 改造后核心会同时有旧痕迹与新结构。Study 与 Workflow 虽然抽出，但 `lib.rs` 的历史包袱仍在，因为它是"原地长大"的文件 |
| B | 4 | 结构最干净，但产品域要重新维护一遍，回归风险落在自己身上 |
| C | 5 | 结构干净且产品域原样保留，没有把已验证的产品逻辑重新写一遍 |

### 4.3 未来功能实现难度，权重 20%

| 路线 | 分 | 理由 |
|---|---|---|
| A | 2 | 新增一个工具要改 `tool_catalog` 这个单点扇出，还要通过根契约。需求的"扩展能力"直接受制于此 |
| B | 4 | 结构支持扩展，但从零补齐已有能力期间，新功能要排队 |
| C | 4 | 同 B，且已有扩展逻辑可参考，前缀成本更低 |

B 与 C 在这项打平，因为扩展机制都是新写的。

### 4.4 修改影响范围，权重 15%

| 路线 | 分 | 理由 |
|---|---|---|
| A | 1 | 实测 16 个模块、59.9% 代码依赖同一契约。改动影响范围的结构性上限就在这里 |
| B | 5 | 新结构依赖方向单向，改外围不动核心 |
| C | 4 | 同 B，但 B 类模块在迁移期还需要一次改签名，迁移完成后才达到 B 的隔离度 |

### 4.5 跨平台复用，权重 10%

| 路线 | 分 | 理由 |
|---|---|---|
| A | 3 | 现在基本无平台耦合，jni 零、tauri 一处，这是它的优点。但 Python 路径耦合 33 处未解决，且新平台能力仍要塞进同一个 crate |
| B | 4 | 平台能力独立 trait，但首批没有现成的 Android 适配可参考，要从零写 |
| C | 5 | 平台 trait 新写，且 Android 宿主现有的 6 个 Kotlin 插件与命令面可以直接参考与迁移，Agent 命令面只有 684 行 |

C 在这项超过 B，因为 B 主张不带任何旧代码，等于把已经调通的 Kotlin 插件与 Android 构建链也一并放弃。那些代码的分层问题远小于核心，没有理由丢。

### 4.6 测试与调试成本，权重 5%

| 路线 | 分 | 理由 |
|---|---|---|
| A | 2 | 246 个现有测试集中在"已实现行为"，改造期间它们会大面积失效，且无法证明新不变量 |
| B | 3 | 全新测试，但产品域也要重建测试，重复劳动 |
| C | 4 | 核心测试新写，产品域测试大多可保留，因为代码没动 |

### 4.7 迁移期风险，权重 5%

| 路线 | 分 | 理由 |
|---|---|---|
| A | 2 | 长期处于半改造状态，每一步都可能引入新的不一致 |
| B | 2 | 一次性推翻。产品功能在核心完成前处于缺失状态，是产品风险 |
| C | 4 | 可以按模块推进，产品域先搬走不受影响，核心完成后再切换 |

### 4.8 加权结果

> **本节数字已被 `方案/Rust核心迁移-08-第一批验证报告.md` 更正。**
> 下表用于说明评分骨架，但第 3 节的成本区间基于未经实测的系数。第一批试迁移后重算的三条路线一次性成本为 A 14,111、B 21,236、C 15,169，A 实际上略低于 C。
> 结论仍然是推荐 C，但理由改为"两者一次性成本相差在 7% 以内，A 留下 13,232 行结构债，C 留下 0"，而不是"C 最便宜"。详见 08 号报告第 3 与第 6 节。

| 路线 | 加权分 |
|---|---|
| A | 1.95 |
| B | 4.25 |
| C | 4.55 |

加权分只用于排序，不能当成精确值。单项分全部是判断，不是测量。分数由权重与第 4 节的单项分直接算出，可复算。

## 6. 最终推荐

**推荐路线 C。**

### 6.1 为什么不选 A

不是因为 A 修不好，是因为**要改的那个东西恰好是耦合中心**。实测 16 个模块、59.9% 代码依赖 `lib.rs` 的契约，而本次要改的正是这份契约本身：

- 错误从 3 个字符串变体变成 11 个枚举
- 审批加上参数摘要与过期
- 回合状态要接上持久化
- 模型端口要支持流式

这四项没有一项是局部改动。A 路线要求在这 4 项改动的全过程中，让 16 个模块始终保持可编译、可测试、语义一致。这不是不能做，是**每一次中间态都难以验证**，而难以验证的中间态是长期维护事故的来源。

A 还有一项独有的成本：Study 与 Workflow 的 14,043 行必须抽出去，因为你不可能在一个"核心"里留着 45% 的产品逻辑然后声称核心干净。抽出去在 A 和 C 里都要做，但 A 还要同时改造契约，两件事叠在一起。

### 6.2 为什么不选 B

B 在结构和 C 几乎一样好，核心都是新写的。B 输在**多花的钱买不到结构收益**。

具体说，B 主张不带任何旧代码，于是 A 类的 10,297 行也要重写。这 10,297 行里：

- 8,010 行是 Study 与 Workflow 的产品逻辑，它们本来就不引用核心契约，没有任何架构缺陷，重写等于重做一遍已经验证过的产品功能，还要重做测试
- 2,287 行是 hooks、profiles、forensics，同样不引用核心契约，重写没有收益

这多出来的 9,000 到 12,000 行等效成本，换来的结构收益是零。因为这部分代码在 C 里也不进核心，而是原样住在自己的 crate 里。

**只有在一种情况下 B 更优：你决定放弃或彻底重写 Study 与 Workflow 这两个产品。** 如果这两个产品本来就要重做，那 B 与 C 的成本会收敛，B 的纯粹性就值得。这一点需要你确认，我在第 9 节列了。

### 6.3 为什么不选 A 与 B 的折中，比如先 A 再 B

那会把两份成本都付一遍。A 的改造产物在转向 B 时大部分要丢弃。没有证据显示两段式比直接 C 更省。

### 6.4 推荐路线的执行顺序

C 能成立的关键是**先把产品域搬走，再动核心**。顺序反了就会变成 A。

1. 把 Study 与 Workflow 的 A 类代码原样搬进独立 crate，验证产品功能不受影响。这一步不碰核心，风险最低，收益立竿见影，因为核心立刻从 31k 降到 21k。
2. 定义新核心契约与存储，用原型代码生产化，跑通最小闭环。
3. 把 B 类模块逐个接上新契约，每个模块独立验证。
4. 切换 Windows 与 Android 宿主到新核心。
5. 删除 C 类模块。

第 1 步之后，无论后面走哪条路，都已经赚到了。这是 C 相对 B 的另一个实际好处：它可以在中途停下而不浪费。

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 改签名成本估算偏乐观 | 总成本上浮 | 先做 `provider.rs` 一个模块的试改，用实测系数替换估计值 |
| 产品域搬走后出现隐性耦合 | 编译或行为异常 | 第 1 步单独成一次改动，只搬不改逻辑，用现有 55 个 Study/Workflow 集成测试当验收 |
| 新核心与 Android 生命周期配合不好 | 手机端崩溃或状态丢失 | 核心完成后先做 Android 探针，再改 UI |
| 两条路线并行期间数据不一致 | 用户数据损坏 | 严格单写者加只读校验，Rust 首批只读旧库 |
| 迁移中途停摆 | 长期半成品 | 第 1 步与第 2 步都能独立交付价值 |

## 8. 置信度与未知

| 结论 | 置信度 | 依据 |
|---|---|---|
| 现有代码 45% 是产品域、60% 耦合同一契约 | 高 | 脚本实测，可复算 |
| 现有代码无循环依赖但无分层 | 高 | 脚本实测 |
| 目标架构的最小核心可在 1 千行内实现并测试 | 高 | 原型已跑通 10 个测试 |
| 三条路线的相对排序 C 优于 A 优于 B | 中高 | 成本模型基于实测行数与明确系数 |
| 具体等效行数区间 | 中低 | 系数是估计，未做完整试改 |
| A 路线中途状态难以验证 | 中 | 基于耦合度推断，未实测改造过程 |
| C 的第 1 步能独立验证 | 中高 | 取决于 Study/Workflow 是否真的只依赖自身 |

**未验证项，明确列出：**

1. 没有对任何一条路线做完整试改，所以成本区间不能当承诺。
2. 没有在 Android 真机验证新核心，平台适配全部未测。
3. 没有测性能，1 万事件量级的追加日志与索引写放大未知。
4. 没有验证 `FileAccess` 抽在 SAF 上是否成立，Android 侧 SAF 代码目前不存在。
5. 没有验证产品域是否真的零核心依赖，只按类型引用判断。

## 9. 需要你决定的四件事

**决定一：路线。** 我推荐 C。如果你倾向于放弃或重做 Study 与 Workflow，那 B 更合适。

**决定二：产品域的归属。** C 要先把 Study 与 Workflow 搬成独立 crate。这两个产品当下是否稳定，决定了第 1 步的风险。如果它们正在频繁改动，搬家要等一个稳定点。

**决定三：是否先做一次试改来校准成本。** 我建议挑 `provider.rs` 一个模块，按新契约试改，用实测时间替换估计系数。代价是几天，收益是整份成本模型从估计变成测量。

**决定四：允许的推进方式。** 是允许我按第 6.4 节的五步连续推进，还是每一步都停下来给你看结果再继续。考虑到这是架构级改动，我建议每步停下来验证一次。
