# Sunday · 方案体系建设与改造 PRD V1.0

> 来源：用户 2026-11-27 直接下发（原文完整保存，未改写、未摘要）。
> 状态：已实施（2026-11-27）；实施与验收见 `方案/Sunday-方案体系与改造-01-实施与验收报告.md`。

## 1. 背景与目标

Sunday 已经积累了大量产品方案、技术设计、实验计划、审查报告及实施记录，但尚未形成统一的方案体系。

本次改造旨在让 Sunday 具备原生的方案编写、管理、讨论、实施与验收能力，使方案成为连接用户意图与 Agent 实际工作的有效载体。

主要建设方向：

- 统一方案分类与编写规范。
- 建立面向方案的 Skill。
- 改造 Library 中现有的「方案」模块。
- 优化方案相关 UI 与交互体验。
- 建立方案与 Agent、项目、会话之间的联系。
- 实现从方案提出到实际交付的闭环。

## 2. 基本原则

1. 第一性原则：所有设计围绕实际使用需求展开，不照搬传统企业的项目管理流程。
2. 最小必要复杂度：简单需求可以使用简单方案，不强制拆分文档，不强制经过完整生命周期。
3. Agent Native：方案既是供用户阅读的文档，也是 Agent 理解目标、开展工作与验证结果的依据。
4. 文件优先：优先使用 Markdown 与现有 Library 存储机制，保持文档的可读性、可编辑性和可迁移性。
5. 复用优先：充分利用现有 Agent、Skill、Library、文件管理、会话及预览能力。
6. 结果导向：方案的最终价值取决于实际解决了什么问题，而非文档的数量或形式完整性。

## 3. 方案分类体系

### 3.1 一级分类

| 类型 | 中文名称 | 核心职责 |
| --- | --- | --- |
| PRD | 产品需求文档 | 定义为什么做、做什么、达到什么效果 |
| SPEC | 技术规范 | 定义机制、接口、协议、行为与技术约束 |
| DESIGN | 设计方案 | 定义视觉、交互、布局与用户体验 |
| RESEARCH | 调研方案 | 调查事实、分析现状、建立认知 |
| EXP | 实验方案 | 验证假设、比较方案、寻找最优解 |
| PLAN | 实施方案 | 定义实施路径、步骤、依赖及交付要求 |
| AUDIT | 审查方案 | 检查现有实现、识别问题与风险 |
| REPORT | 结果报告 | 记录实际成果、证据、结论与遗留问题 |

### 3.2 扩展分类

根据实际需要支持以下类型：

| 类型 | 中文名称 | 建议归属 |
| --- | --- | --- |
| ARCH | 架构设计 | SPEC |
| ADR | 架构决策记录 | SPEC |
| RFC | 提案与讨论 | DESIGN / RESEARCH |
| POC | 概念验证 | EXP |
| TEST | 测试方案 | PLAN |
| MIG | 迁移方案 | PLAN |
| SOP | 标准操作流程 | PLAN |
| RCA | 根因分析 | AUDIT |

扩展分类不必全部作为 UI 一级入口。

允许一份方案承担多种职责，根据主要目标确定其分类。不得为了满足分类规范而人为拆分文档。

## 4. 方案编写规范

不同类型的方案应具有各自的核心内容要求，而非共用一套僵化模板。

| 类型 | 核心内容 |
| --- | --- |
| PRD | 背景、问题、目标、范围、需求、约束、验收标准 |
| SPEC | 设计目标、技术机制、接口、行为规范、边界条件 |
| DESIGN | 设计目标、使用场景、交互流程、视觉与体验要求 |
| RESEARCH | 调研目标、调查范围、事实依据、发现、结论 |
| EXP | 实验目标、假设、变量、评价指标、实验方法、停止条件 |
| PLAN | 实施目标、现状、实施步骤、依赖、验收要求 |
| AUDIT | 审查目标、审查范围、问题、证据、影响、改进建议 |
| REPORT | 实际成果、验证证据、结论、差异、遗留问题 |

上述内容属于指导性规范，不是强制章节清单。

Agent 应根据方案复杂程度自行决定篇幅、结构与表达形式。

方案应重点保证：

- 准确理解用户意图。
- 明确目标及范围。
- 区分事实、假设、建议与已确认决策。
- 具有足够的可执行性或研究价值。
- 对需要实施的目标提供可验证的完成标准。

避免套话、重复内容、无意义的背景介绍及未经验证的技术承诺。

## 5. 方案 Skill

### 5.1 建设目标

让 Agent 主动理解不同类型方案的用途，并具备正确处理方案的能力。

优先建设统一的方案 Skill，根据任务需要加载不同类型的编写规范，而非为每一种文档机械创建独立 Skill。

### 5.2 核心能力

| 能力 | 职责 |
| --- | --- |
| Create | 根据用户意图创建适当类型的方案 |
| Discuss | 围绕方案进行讨论、分析与完善 |
| Review | 审查方案的合理性、完整性与可行性 |
| Revise | 根据新需求、反馈或事实修订方案 |
| Execute | 根据方案开展调查、开发或实验 |
| Verify | 验证方案目标是否得到满足 |
| Report | 记录实际成果与验收证据 |
| Organize | 分类、关联与归档方案 |

上述能力为逻辑划分，不要求分别实现为工具或 Skill。

### 5.3 自然语言调用

Agent 应能够理解类似指令：

- 写一份 PRD。
- 给这个功能补一份 SPEC。
- 审查这个方案。
- 将刚才讨论的内容整理为设计方案。
- 根据这个 PRD 开始实施。
- 检查这个方案还有哪些没有落实。
- 将实验结果整理为 REPORT。
- 更新现有方案，不要重复创建。

用户无需学习额外命令或专用语法。

### 5.4 实施行为要求

当用户要求根据方案开展实际工作时，Agent 应：

- 理解方案目标及已确认约束。
- 核实当前实际情况。
- 复用已有能力，避免重复建设。
- 自主完成必要的技术设计与实施。
- 根据实际结果进行验证。
- 如实记录未完成项及方案偏差。

不得将编写实施计划视为完成实施任务。

不得将代码存在、编译成功或模拟测试通过直接视为实际功能验收通过。

## 6. Library－方案模块改造

### 6.1 产品定位

保留 Library 中现有的「方案」入口，将其改造为专门用于管理各类方案文档的工作区域。

不建立独立于 Library 的新产品模块。

### 6.2 基础管理能力

支持：

- 创建、阅读、编辑、搜索方案。
- 按类型、项目、专题及状态筛选。
- 按最近修改时间等常用条件排序。
- 重命名、移动、归档及删除。
- 查看方案关联的项目、会话与其他文档。
- 从现有文件导入方案。
- 以普通文件形式打开、复制及导出方案。

### 6.3 最小元数据

| 字段 | 说明 |
| --- | --- |
| 标题 | 方案名称 |
| 类型 | PRD、SPEC 等 |
| 所属项目 | 可选 |
| 专题 | 可选，用于组织相关方案 |
| 状态 | 当前方案状态 |
| 修改时间 | 自动维护 |
| 关联项 | 可选，关联文档或会话 |

优先复用现有 Library 元数据能力。

仅在确有必要时扩展数据结构，不建立复杂的方案对象模型。

### 6.4 专题组织

允许将相关方案归入同一专题。

例如：

```
Sunday Memory
├── PRD · 主动记忆与认知系统
├── SPEC · 记忆检索机制
├── EXP · 记忆注入效果实验
└── REPORT · 实施与验收报告
```

专题主要用于组织与检索，不意味着必须具备完整的一套文档。

简单需求可以只有一份 PRD。

### 6.5 历史方案迁移

对现有 Library 方案及相关历史文档进行调查与整理：

- 识别现有方案的类型与专题。
- 尽可能保留已有文件名称、内容、路径及引用关系。
- 识别重复、失效及已被替代的方案。
- 建立必要的分类与关联信息。
- 保留无法自动判断的历史方案，允许后续人工或 Agent 整理。

不要求批量重写历史方案。

不擅自删除历史文件，不根据文档中的自述推断功能已经完成。

迁移过程应可追溯，并避免影响现有文件的正常使用。

## 7. UI 与交互设计

### 7.1 整体要求

延续 Sunday 与 Library 现有视觉体系，以内容阅读和 Agent 协作为核心。

避免将方案模块设计成复杂的 Jira、Notion 或企业项目管理平台。

### 7.2 方案首页

方案首页提供：

- 新建方案。
- 搜索。
- 类型筛选。
- 项目及专题筛选。
- 状态筛选。
- 最近使用或修改的方案。

默认以易于浏览、快速定位的列表为主。

### 7.3 方案阅读与编辑

方案详情支持：

- Markdown 阅读及编辑。
- 标题与基本信息展示。
- 文档目录导航。
- 关联方案快速跳转。
- 关联会话快速跳转。
- 查看已有实施及验收报告。

优先复用 Sunday 现有编辑器、预览器与工作区布局能力。

### 7.4 Agent 交互入口

在方案详情或上下文菜单中提供常用操作：

- 与 Agent 讨论。
- 审查方案。
- 修订方案。
- 开始实施。
- 检查落实情况。

这些操作本质上是向 Agent 发起带有方案上下文的任务。

无需为每个操作单独建立执行系统。

### 7.5 工作区联动

用户可以在阅读方案的同时与 Agent 对话。

复用 Sunday 现有主内容、辅助内容、浮层与分屏能力，实现方案和会话之间的快速切换与并行使用。

具体布局应根据现有 UI 结构设计，不为方案模块单独建立一套窗口管理体系。

## 8. 方案生命周期

### 8.1 设计状态

| 状态 | 含义 |
| --- | --- |
| 草案 | 尚在讨论或编写 |
| 生效 | 当前有效方案 |
| 已归档 | 不再活跃维护 |
| 已废弃 | 不再作为有效依据 |

### 8.2 实施状态

对于具有实施目标的方案，额外支持：

| 状态 | 含义 |
| --- | --- |
| 未实施 | 尚未开始 |
| 实施中 | 正在推进 |
| 待验收 | 实施完成声明尚待验证 |
| 已验收 | 约定目标已经得到验证 |

研究、审查、报告等不适用实施状态的文档可以省略。

方案设计状态与实施状态相互独立。

状态主要用于帮助用户与 Agent 理解当前情况，不作为强制工作流门禁。

不要求所有方案经过全部状态。

## 9. 方案与 Agent、项目及会话的关联

遵循 Sunday 现有的环境、项目、会话体系。

方案可以关联所属项目，并与一个或多个相关会话建立联系。

### 9.1 从方案发起任务

用户选中方案并发起 Agent 任务时：

1. 选择适当的项目与会话。
2. 将方案及必要上下文提供给 Agent。
3. Agent 根据用户选择开展讨论、审查或实施。
4. 保留方案与会话之间的关联。
5. 根据实际任务结果更新方案状态或生成报告。

### 9.2 从会话创建方案

用户可以直接要求 Agent 将讨论结果整理成方案。

创建时应尽可能保留相关决策、用户意图与必要的上下文关联。

### 9.3 跨会话连续性

新的 Agent 会话可以通过已有方案理解任务目标及历史成果，并继续开展工作。

不得要求 Agent 每次加载全部历史会话或全部关联文档。

关联信息用于按需检索，而非无条件增加上下文负担。

## 10. 方案版本与关联

### 10.1 版本管理

优先复用现有文件历史、版本管理或 Git 能力。

对于重要方案变更，应保留必要的修改理由和历史决策。

不在本阶段建设独立版本控制引擎。

### 10.2 方案关联

支持以下常见关系：

- 同一专题。
- 补充与细化。
- 实施与验收。
- 替代旧方案。

普通文件链接或轻量元数据能够满足需求时，不引入专用关系数据库。

不强制维护复杂的依赖图谱。

## 11. 质量与验收

区分两个不同的验收对象。

### 11.1 方案质量

判断方案是否：

- 准确表达用户意图。
- 解决实际问题。
- 具备合理的范围与约束。
- 没有明显的遗漏、矛盾或过度工程化。
- 具有足够的可执行性。

### 11.2 实施质量

判断实际工作是否实现方案目标。

根据任务性质使用代码审查、真实运行测试、UI 交互测试、实验数据或其他有效证据。

对于需要实施的方案，报告应明确区分：

| 结果 | 含义 |
| --- | --- |
| PASS | 已验证满足要求 |
| PARTIAL | 部分满足要求 |
| FAIL | 验证未通过 |
| UNVERIFIED | 尚未验证 |
| BLOCKED | 存在阻塞 |

不要求每份方案都生成独立验收报告。

简单任务允许直接在原方案或相关会话中记录结果。

## 12. 本期非目标

本期明确不主动建设：

- 独立的项目管理平台。
- 强制性的审批流。
- 复杂任务编排引擎。
- 方案知识图谱。
- 多级权限管理系统。
- 独立版本控制系统。
- 专用方案数据库。
- 强制性的多 Agent 审查流水线。
- 复杂的进度统计与管理 Dashboard。

如果现有 Sunday 基础设施能够提供相关能力，可直接复用。

## 13. 实施要求

实施 Agent 应首先调查：

- 现有 Library－方案模块。
- 现有方案文件及存储方式。
- Skill 加载与调用机制。
- 文档编辑、预览及搜索能力。
- 项目、会话及工作区机制。
- 已有版本管理与元数据能力。

在完成调查后，以现有架构为基础实施本 PRD。

优先完成以下四个方面：

P0：方案规范与 Skill

- 建立统一分类、编写规范及 Agent 方案处理能力。

P0：Library－方案改造

- 完成现有方案的兼容、分类、检索、管理及必要迁移。

P0：UI 与 Agent 联动

- 完成方案创建、阅读、编辑、讨论、审查与发起实施的基础体验。

P1：生命周期与历史追踪

- 完善状态、关联、历史记录及实施结果管理。

不得仅交付设计文档、静态 UI 或未接入实际能力的功能入口。

## 14. 最终验收场景

| ID | 场景 | 预期结果 |
| --- | --- | --- |
| A01 | 用户要求 Agent 编写 PRD | 生成符合规范的真实方案文件 |
| A02 | 用户要求编写 SPEC 或 EXP | Agent 根据类型采用适当结构 |
| A03 | 用户打开 Library－方案 | 可以浏览、搜索及筛选现有方案 |
| A04 | 用户打开历史方案 | 原始内容及必要引用保持有效 |
| A05 | 用户选择方案并发起讨论 | Agent 正确获得方案上下文 |
| A06 | 用户要求修订方案 | 修改已有方案而非无故重复创建 |
| A07 | 用户根据 PRD 发起实施 | Agent 在适当项目及会话中执行任务 |
| A08 | 用户检查方案落实情况 | 获得基于实际证据的结果 |
| A09 | 用户在新会话继续工作 | Agent 能够检索方案及必要历史成果 |
| A10 | 用户导出方案 | 获得独立于 Sunday 可正常阅读的文件 |
| A11 | 用户创建一个简单方案 | 无需填写大量字段或经过复杂流程 |
| A12 | 用户关闭并重新启动 Sunday | 方案内容、分类及必要关联保持有效 |

## 15. 交付要求

最终交付：

1. 方案分类与编写规范。
2. 可实际使用的方案 Skill。
3. 改造后的 Library－方案模块。
4. 方案管理与 Agent 协作 UI。
5. 历史方案整理与兼容结果。
6. 实施及验收报告。

所有功能应建立在实际调查和运行验证的基础上。

最终目标：用户可以提出一个想法，与 Agent 讨论形成方案，随时查阅、修改、实施和验收，并在未来的任意会话中继续推进。整个过程自然、连续，不需要用户学习一套额外的项目管理方法。
