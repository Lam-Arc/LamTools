# 网络插件的引擎选型与集成边界

日期：2026-10-25
产品定位：Sunday 的网络插件是一个**本地编排器**，把成熟的代理、下载、加速引擎接进来，用一个界面和一套生命周期管理它们。

## 一、当前已经“吃掉”的部分

| 能力 | 引擎 | 状态 | 许可证 | 集成方式 |
| --- | --- | --- | --- | --- |
| 代理 / 订阅 / 节点 | Mihomo | 已内置 | GPL-3.0 | 独立进程，插件私有控制端口，JSON 协议 |
| 快速下载 | aria2 | 已内置 | GPL-2.0-or-later | 独立进程，私有 RPC，任务持久化 |
| 界面与编排 | 自研 Vue + Rust | 已内置 | 仓库自身 | 四页 UI + 单一 Rust 控制器 |

这已经覆盖了 FlClash 的核心价值：订阅、分组、节点、测速、选择。FlClash 本身是 Flutter 桌面 GUI，底层同样使用 Mihomo；把 FlClash 整个塞进来不会增加能力，只会多一层 GUI 和一套状态。**代理这一块继续用 Mihomo 就够了。**

aria2 就是“快速下载”部分：多连接、分段、队列、限速、断点续传。插件现在做的是把它包装成“粘贴/拖入链接 → 开始下载 → 进度”，不再让用户碰命令行。

## 本机加速已按 FastGithub 的方式实现（2026-10-25）

Watt Toolkit 的 GitHub 处理者继承自 `TcpReverseProxyHandler`，注释直接指向 FastGithub 2.1.4。其核心不是 MITM：

- 本地 HTTP 代理接 `CONNECT host:443`；
- 命中加速域名时，用 DoH 解析 A 记录，按候选 IP 逐个/并发直连，TLS 原样透传；
- 非命中域名交给普通解析或上游代理；
- Hosts/DNSIntercept/PAC 是另外的透明模式，需要改系统设置；System 模式只需要系统代理。

本仓库按这个流程实现了 `controller/src/accelerator.rs`：

- `is_common_acceleration_host` 使用与 FastGithub 相同的精确域名/子域名匹配；
- `parse_authority` 支持 IPv4、IPv6、默认 443；
- `resolve_doh` 并发查询阿里 223.5.5.5、DNSPod、Cloudflare、Google；过滤 `127.0.0.1`、`0.0.0.0`、组播、链路本地等不可用答案；
- 候选 IP 并发连接，4 秒超时，首个 TCP 成功即隧道；
- TLS 首包 2 秒内没有返回（常见于 DNS 污染到错误 IP）时，改走正在运行的 Mihomo 线路；常用域名加速失败也继续走线路/系统解析；
- 非命中域名优先交给正在运行的 Mihomo（17890），否则按系统解析直连；
- 不动 hosts、不装 CA、不做证书中间人。
- `system.apply` 接受任意 `127.0.0.1:<port>`；加速页与首页只负责本机加速，线路选择在代理页。

真实测试（2026-10-26）：Modrinth 200；`files.nexus-cdn.com` 302；`mod.io` 经线路回退 200；GitHub 经线路回退 200；NexusMods 可建立连接，但 Cloudflare 风控间歇返回 403 人机验证。当前网络会拦截 Cloudflare/Google DoH，所以国内可达的 DoH 必须放在查询列表里。

仍未实现：Hosts/DNS 拦截/PAC/透明模式、Git/SSH 独立端口、需要证书的完整反向代理、外部 Watt Toolkit 进程接入。本机加速不是 VPN：网络层直接阻断目标 IP/SNI、或站点按 IP 做 Cloudflare 人机验证时，本机加速无法绕过，需要在代理页选一条可用线路。

## 二、Watt Toolkit 不能直接当库吃

Watt Toolkit（SteamTools）按公开仓库信息是 GPL-3.0 的 .NET/Avalonia 桌面应用，不是稳定的无头 CLI/SDK：

- 它面向桌面 GUI，没有对外承诺的稳定 headless 接口。
- 它的 Steam/GitHub 加速依赖它自己的加速服务/端点，不只是本地改 hosts。
- 它是 GPL-3.0。独立进程 + 未修改二进制可以按“聚合”处理，但仍要附带许可证和源码获取方式；把它的代码链接进我们的程序则会让整个组合落入 GPL 义务。
- 它的能力边界和我们的系统代理会互相抢设置，必须只允许一个系统代理所有者。

所以“直接把 Watt Toolkit 吃掉”不是加一个依赖，而是三种选择之一：

### 方案 A：可选外部引擎

检测用户自己安装的 Watt Toolkit，通过它公开的接口调用；不随插件分发。优点是合规压力小、用户自己负责；缺点是没有稳定接口时做不了，且依赖用户安装。

### 方案 B：自研本地加速层

用 Rust 做一个本地反向代理/加速器：

- 维护域名 → 替代 IP / DoH 选路 / 直连规则。
- 只对支持直连优化的目标生效；遇到 IP/SNI 层阻断时无能为力。
- 不需要第三方账号，但需要证书与本地端口管理，安全面较大。

这适合 GitHub 静态资源、部分游戏 CDN；**不能承诺“所有 GitHub 都加速”**。

### 方案 C：自建/第三方中转

真正接近 Watt Toolkit 体验的方式，是插件自带或对接加速中转服务。它需要服务器、带宽、滥用防护、隐私说明和用户同意，是产品/基础设施决策，不是插件内的一行配置。

## 三、推荐架构

```text
Vue 四页 UI
  └─ Rust Controller（唯一状态所有者）
       ├─ ProxyEngine    → Mihomo（内置，独立进程）
       ├─ DownloadEngine → aria2（内置，独立进程）
       └─ Accelerator    → 本地加速层（方案 B）
                            └─ 可选外部引擎（方案 A）
```

每个引擎都必须：

1. 独立进程，不链接进主程序；
2. 有版本化的 JSON/CLI 契约；
3. 生命周期、日志、崩溃回收由 Rust 控制器统一管理；
4. 只监听 `127.0.0.1` 的私有端口，不开放无认证网络端口；
5. 在“关于/许可证”里列出许可证和源码地址。

UI 上的分工：

- **加速页**：只开关本机加速层，显示 DoH 选路、系统改动范围与运行状态。
- **代理页**：订阅、连接开关、节点分组、测速与选线路；本机加速遇到被阻断的域名时借用这里的线路。
- **外部加速**：检测到 Watt Toolkit 等外部引擎（方案 A，可选，尚未实现）。

没有对应引擎时，按钮不假装成功。

## 四、下一步建议

1. 本机加速继续只覆盖能直连优化的域名，明确标注“不保证绕过被网络层阻断的目标”。
2. 如果确实需要 Watt Toolkit 级体验，再评估方案 C 的基础设施成本；方案 A 只在对方提供稳定无头接口时考虑。
3. 许可证清单和“关于”页面随第一个外部引擎一起交付。

## 五、结论

- FlClash 的代理能力：已经通过 Mihomo 吸收。
- 快速下载：已经通过 aria2 吸收。
- Watt Toolkit 的本地加速：**不能简单当库吃**，需要单独的加速引擎/外部进程/中转服务；当前插件没有这一层，也不会把普通直连说成加速成功。
- 这个插件最合理的形态就是你说的：一个本地编排器 + 四页界面 + 三个可替换的引擎适配器。
