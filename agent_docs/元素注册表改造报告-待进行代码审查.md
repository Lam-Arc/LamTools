# 可编辑元素注册表改造报告：待进行代码审查

状态：**待进行代码审查**
日期：2026-10-29
范围：`core/ui` 的可编辑元素身份与清单，为后续可视化主题编辑器打地基
不涉及：视觉效果、布局、业务逻辑、主题存储

## 一、结论

本轮只做了一件事：给允许被主题编辑器修改的界面元素建立稳定身份与清单。代码是纯增量，现有界面没有任何视觉或行为变化。

自测口径：类型检查三套配置通过，构建通过，直接相关的六个测试文件一百六十三项通过；全量测试与改动前基线逐文件比对，只多出既有的网络插件页面失败，与本次改动无关。

## 二、为什么先做这一层

可视化编辑器不能从任意 DOM 推断可编辑能力。若按类名或层级去抓元素，一次重构就会让用户存下来的主题错位到别的元素上。所以先定身份，再谈编辑。

这一层同时解决三件事：

1. 编辑器知道哪些元素可以改、能改到什么程度。
2. 运行端知道每条样式覆盖该落到哪个节点。
3. 重构时如果标识被删或改名，测试会先报错，而不是等用户主题坏掉才发现。

## 三、设计决定

| 决定 | 取值 | 理由 |
|---|---|---|
| 标识格式 | `区域.名称`，如 `shell.composer` | 可读、可排序、能看出归属 |
| 挂载位置 | 组件根节点 | 挂内部子节点会把布局结构焊死，后续调整即失效 |
| 可编辑属性 | 十类有限枚举 | 避免属性面板无限膨胀 |
| 保护级别 | 可编辑、仅外观、受保护 | 业务入口不能被隐藏，否则用户回不到设置 |
| 清单位置 | 源码内的类型化数组 | 与组件同仓库版本，重构时一起评审 |
| 校验方式 | 四条自动化断言 | 唯一性、父级无环、组件确实挂载、级别与属性不矛盾 |

可编辑属性枚举：尺寸、间距、圆角、描边、颜色、背景、文字、透明度、层级、可见性。

## 七、审查建议清单

1. 确认标识命名是否贴合产品语义，特别是“会话抽屉”与“会话列表”的父子关系。
2. 确认保护级别是否恰当，尤其主区域、输入栏、设置页定为仅外观是否符合预期。
3. 确认可编辑属性枚举是否够用，后续是否会很快需要位置、锚点等新类别。
4. 确认标识挂载点都在组件根节点，没有挂到会被条件渲染替换的节点上。
5. 确认新增的 `data-ui-id` 不会与现有选择器或测试冲突。
6. 确认校验测试能覆盖重构风险，是否需要补一条“标识不得在发布后改名”的迁移说明。

## 八、风险

- 标识一旦对外发布就不能随便改名，改名属于主题迁移，需要版本升级与兜底。
- 目前只登记了根节点，行、按钮、卡片等子部件尚未登记；编辑器要做元素级编辑时必须继续补，补齐时不能改变已发布标识的含义。
- 清单与组件在同一仓库，组件删除而清单未删会导致测试失败，这是有意的保护，不是缺陷。

## 九、回滚方式

- 删除 `core/ui/src/uiRegistry/` 目录与 `core/ui/tests/ui-registry.test.ts`。
- 移除十四个组件根节点上的 `data-ui-id` 属性。
- 移除说明书新增的一节。

以上三步互不依赖，可以整体回滚，也可以只回滚测试保留清单。
